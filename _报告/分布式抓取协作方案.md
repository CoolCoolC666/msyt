# 民生e网通「分布式抓取协作平台」设计方案（不落地版）

> 本报告只做设计，**不写一行落地代码**。
> 文中所有关于站点的结论，都是 `msyt` 程序在 2026-10-22 实测得到的（证据链见 `02 民生e网通\_报告\方案报告.md` 证据 1–9）。
> 关于开源项目的描述，均来自各项目官方仓库/文档，链接见 §7。

---

## 0. 一句话结论

**可以做，而且不该套用现成的爬虫平台。**

理由很直接：本机 **没有 Docker、没有 Redis**，而 Crawlab 要 Docker + MongoDB + SeaweedFS 三件套；
而**要的东西本机已经全装好了** —— FastAPI、uvicorn、PyJWT、cryptography 都是现成的，
`msyt` 本身就是 Python 包且**已经用原生 sqlite3**（不是 SQLAlchemy），
风格与"用 SQLite 当任务队列"完全一致。
所以推荐 **自研一个极薄的控制面（FastAPI + SQLite + 内置成员账号表 + JWT）**，
把 `msyt` 的采集器原样复用为成员端 agent，**增量依赖为零**。

同时建议：**先用"人工协作"跑通协作流程本身（阶段 1），再谈写程序**——
`msyt detail --tid` 和 `msyt export` 已经能用，人工协作当天就能试，
能提前暴露"成员到底愿不愿意干、干了怎么回传"这类流程问题，比先写 800 行控制面再返工划算。

## 1. 现状盘点：msyt 现在能干什么，缺什么

### 1.1 已经具备的（都是实测结论，不是设想）

| 能力 | 现状 | 对分布式化的意义 |
|---|---|---|
| 两条链路分离 | `msyt list`（元数据，1 请求/帖）/ `msyt detail`（正文，N×2 请求/帖） | **列表几乎不需要分摊**，真正要分摊的是 detail 的请求量 |
| 先旧后新 | 按 `pub_ts` 升序取帖 | 分发顺序天然可定义：越老越先 |
| 断点续传 | 粒度=页，落库=每页一事务；`running` 归位 `pending` 后从 `pages_done+1` 续 | ★ **这是分布式协作的地基**：成员中途关机，任务可以原样退回池子 |
| 完整性判据 | 逐页 pid 集合**精确相等** + 跨页头/尾 + 页数齐全 + 无空正文 | ★ **判据可以在成员端闭环执行**，这是让协作不"信成员"的关键 |
| 去重 | pid 是天然主键，`upsert` 幂等 | ★ 回传天然幂等，重复提交不会脏数据 |
| 水位线 | 全局视图末页最早一贴的发帖时间，早于它的详情标 `skipped` | 分发时不必给成员派"必然被跳过"的活 |
| 多维标签 | 七条轴既做采集源又做入库标签 | 任务可以按「部门/类别/时段」切分，分摊粒度可讨论 |
| 检索层 | FTS5 + trigram，短词整体退 LIKE | 管理员端统一检索，成员端不碰 |

### 1.2 缺什么（分布式化的真实缺口）

| 缺口 | 现状 | 分布式化必须补的 |
|---|---|---|
| 单一执行端 | 只有管理员这台设备在跑 | 多个异构成员设备 |
| 单一权威库 | `程序\data\msyt.db` 一个 SQLite 文件 | 需要"谁的数据算数"的仲裁规则 |
| 无任务池 | `detail_queue` 表有 463 条 pending，但只被本地 `detail` 命令消费 | 跨机的任务分发与领取 |
| 无身份 | 无账号体系 | 成员登录 + 权限 + 审计 |
| 无留痕 | `fetch_log` 只记本地执行 | 谁在什么时候采了什么 |
| 无配额 | 本地 `interval=1.2s` 是全局唯一的节流阀 | 多节点共同施压，站方视角会变 |

**最后一条是本报告最需要讲清楚的风险**，见 §5.1。

## 2. 角色与"以我的设备为准"的准确含义

### 2.1 角色定义

| 角色 | 拥有什么 | 负责什么 |
|---|---|---|
| **管理员**（你） | 权威数据库、代码仓库、域名与服务器、成员账号表 | 定任务池、仲裁数据、抽样复核、对外交付报告 |
| **成员**（小组成员） | 自己的设备、自己的 IP、`msyt` 客户端副本 | 登录、领任务（或提协助请求）、本地采集、回传证据 |
| **站方**（bbs.cnnb.com.cn） | 全部数据 | 被读取方，**不参与我们的协作** |

### 2.2 "以我的设备为准"的三层含义

这句话容易被读成"数据存在我这儿"，但技术上有三层，必须分开：

1. **权威性**：只有管理员设备上的 `msyt.db` 是**权威副本**。
   成员回传的数据先进入"待仲裁区"，通过校验后才 merge 进权威库。
   任何时候删掉权威库，理论上都能从"任务日志 + 站方"重建。

2. **唯一真值**：同一 `tid` 被多个成员采到时，**以管理员库为准**。
   站方内容在"已回复"之后基本静态，所以理论上应该一致；
   不一致就是异常信号（见 §5.3 的抽样复核），**不是"取最新的"**。

3. **归档与交付**：对外的报告、CSV、图表，一律从管理员权威库导出，
   成员**不得**持有导出版本、不得二次分发（见 §8 合规）。

> ⚠️ 需要明确的边界：**成员设备上的本地库只是暂存**。
> 任务回传成功即清；回传失败则保留本地结果，任务退回池子等重领。
> 成员本地库永远不是"第二个权威库"。

## 3. 关键语义：「抓取协助请求」到底指什么

用户原话是"其他小组成员登录发布抓取协助请求，可以分摊我这边的抓取请求"。
这句话里其实有两种不同语义，**不是二选一，是两个侧面**：

### 3.1 两种模式

| | **Pull 认领制**（管理员出题） | **Push 需求制**（成员出题） |
|---|---|---|
| 谁发起 | 管理员把待采的 `tid` 放进任务池 | 成员说"我想采这一段" |
| 成员动作 | 打开任务列表 → 认领 → 采 → 回传 | 提交一条协助请求 → 等批准 → 采 → 回传 |
| 适合 | 管理员已经知道要采什么（当前就是：全量补详情） | 管理员不知道该优先采什么；或成员想认领自己关心的部门/时段 |
| 风险 | 成员被动，可能干得敷衍 | 成员提的需求可能与全局优先级冲突，需要管理员仲裁 |
| 实现成本 | 低（任务池 + 领任务 + 回传） | 中（多一张申请表 + 批准流程） |

### 3.2 推荐：**混合，但以 Pull 为主**

- **主体走 Pull**：管理员维护一个待采 `tid` 池（来源就是现有的 `detail_queue`），成员直接认领。
  这条路径最短，且与 `msyt` 现有的 `claim_next_detail()` 几乎一一对应。
- **Push 作补充**：成员可以在看板上看到"全局还差哪些部门/时段"，直接**发布协助请求**，
  例如"我要认领住建局 2020-2022 的详情"。管理员只需点"批准并入池"。
- **仲裁规则**：批准时入池**不一定立刻可领**——按 `pub_ts` 升序排，
  避免成员抢着采新帖（新的容易、旧的有价值），
  同时保证"先旧后新"这条已被验证的顺序不被协作打乱。

> **这个取舍值得在小群里先投票**：如果成员其实更想要"自己挑活"（Push），
> 那么 Pull 只是个兜底；反之如果大家只想"领到啥采啥"，Push 可以先不做。
> **建议用 §11 的阶段 1（人工协作）去探这个**，而不是先写代码。

## 4. 架构设计

### 4.1 全景

```
              成员浏览器                      成员设备（Agent 主机）
          ┌──────────────┐                 ┌─────────────────────────────┐
          │  登录 / 看板  │                 │  msyt-agent                 │
          │  领任务       │                 │   ├─ 从控制面拉任务          │
          │  发布协助请求 │                 │   ├─ 复用 DetailCollector    │
          └───────┬──────┘                 │   │   (先旧后新/断点续传/校验) │
                  │                        │   └─ 回传结果包 + 证据        │
                  │ HTTPS                  └──────────┬──────────────────┘
                  │ (cloudflared tunnel,                │ HTTPS 回传
                  │  已有域名 + 自动 TLS)                 │
                  ▼                                        ▼
        ┌──────────────────────────────────────────────────────────┐
        │           控制面（管理员设备，FastAPI + SQLite）          │
        │  ┌────────────┐  ┌──────────┐  ┌────────────────────┐  │
        │  │ 认证/会话   │  │ 任务池    │  │ 仲裁 + 审计          │  │
        │  │ 成员账号表  │  │ 租约/心跳  │  │ 校验 → 待仲裁 → merge │  │
        │  │ JWT        │  │ 全局配额闸 │  │ fetch_log / 冲突记录  │  │
        │  └────────────┘  └──────────┘  └────────────────────┘  │
        │                          │                                │
        │                          ▼                                │
        │              ┌────────────────────────┐                   │
        │              │ 权威库 msyt.db         │                   │
        │              │ threads/posts/flows/   │                   │
        │              │ thread_tags/…          │                   │
        │              └────────────────────────┘                   │
        └──────────────────────────────────────────────────────────┘
```

### 4.2 节点模型：同节点互斥、跨节点并行

这是本方案最需要先定死的一条，因为它决定了**协作能不能真正跑起来**。

| | 同一个节点 | 不同节点 |
|---|---|---|
| 能否同时跑同类任务 | **不能**（互斥拒绝） | **能**（各采各的） |
| 原因 | 两个任务会**重复请求同一批页**，请求量翻倍，还会互相踩水位线 | 成员各采各的部门段，靠 `tid` 幂等去重汇总 |
| 举例 | 管理员本机误点两次「开始采集」→ 第二个被拒 | 管理员采 A 组部门、成员甲采 B 组、成员乙采 C 组 |

**实测教训（本轮真的踩了）**：管理员误启动了两个"109 部门全量"任务，
它们把同一个源 `dept:726` 的 23,000 行**重采了一遍**，并且同时在采 `dept:730` ——
请求量直接翻倍，而站方是**我们正在小心对待的对象**（§8 风控纪律）。
所以本地实现把互斥域定成 **(任务类型, 采集节点)**：

```
节点标识 node：现在只有管理员本机 = "admin"
              将来每个小组成员 = 一个自己的 node id
互斥检查：同 kind + 同 node + running → 拒绝启动（409，并说明该停哪个）
          不同 node → 放行
```

> ★ 这个设计**现在就要留**，不能等到 Beta 那天再改 ——
> 因为"并行"不是"多开几个任务"，而是**跨节点**并行；
> 如果互斥域做成了全局的，小组成员一接入就会被自己的管理员挡住。

**看板上的体现**：任务列表显示节点徽标；「开始采集」在同节点已有同类任务时给出明确拒绝理由
（而不是"按钮灰着不说为什么"）。

### 4.3 分层职责

| 层 | 放哪 | 干什么 | 不干什么 |
|---|---|---|---|
| **接入层** | 已有域名 + `cloudflared` tunnel（**本机已装**） | TLS 终止、域名入口 | 不做业务 |
| **认证层** | 控制面内置 | 成员账号表、密码哈希、JWT 会话、审计留痕 | 不引第三方 IdP |
| **控制面** | 控制面进程 | 任务池、租约、心跳、配额、协助请求审批、版本闸 | **不碰站方**（控制面自己一个站方请求都不发） |
| **执行面** | 成员设备 | 跑 `msyt` 采集、做完整性校验、打包回传 | **不碰管理员库**（回传走 HTTP） |
| **存储面** | 管理员设备 | 权威库 + 仲裁区 + 任务表 + 审计 | 成员本地库只是暂存 |

> ★ **控制面不碰站方**是刻意的设计：
> 控制面只发"去采第 X 号帖"这种任务指令，**由成员设备自己取 token、自己发请求**。
> 原因见 §5.1 第 2 条 —— token 有效期 < 30 秒，中心预取必然过期；
> 而且这样站方看到的全是"分散的普通用户各自在读"，而不是"某台服务器在集中爬"。

## 5. 关键难点与解法

这一节是本报告的主体。以下每一条都从 `msyt` 的实测教训推出来，不是通用爬虫理论。

### 5.1 难点一：站方风控 —— 多节点并发会共同改变站方看到的流量形态

**风险描述**：现有 `msyt` 的节流阀是**单机全局**的（`interval=1.2s`）。
单机实测列表连续 12 次 12/12 HTTP 200、无 403/429（证据 8）。
但一旦有 N 个成员同时开跑，**总请求速率 = N × 单机速率**，
而且这些请求**来自 N 个不同 IP** —— 这恰恰是风控系统最难识别的形态：
既不是"一个 IP 高频"（好识别），也不是"一个 IP 低频"（正常），而是"很多 IP 都在读同一个帖子区"。

**解法（三层）**：

1. **配额从中心发，不各自为政**。
   控制面维护一个**全局速率闸门**（令牌桶），成员领任务时**批量领**若干令牌
   （比如一次给 10 个），节点自己慢慢消耗。
   → 好处：整体对站方的压力恒定可控；且**不用每次领任务都往返中心**（往返会引入延迟，
   而延迟对 token 时效是致命的）。
   → 节点崩溃不带走配额（令牌已消耗的部分作废即可，不必回收）。

2. **限速键必须是"节点"而不是"IP"**。
   站方按 IP 限，成员天然是不同 IP，**这反而是分散优势**。
   真正的危险是：多个成员设备在**同一个网络**（同一实验室 WiFi / 同一宿舍宽带），
   那就是"同 IP 多倍速率"，等于放大攻击特征。
   → 所以配额按**成员节点**发放，且要记录各成员的出口 IP；
   管理员要能一眼看出"这几个成员在同一个 IP 下"并下调配额。

3. **站点级熔断**。
   任一节点收到 403/429 或验证码 → **立刻上报并全局暂停**（不只是自己停）。
   理由已在实测中反复验证过：**"权威复核"这种低成本健康检查本身是最贵的操作**，
   所以熔断信号要**一次命中、全网生效**，而不是让每个节点各自去"再打一次确认"。

> **这条要单独立一个"站方压力预算"**：在 §11 阶段 1 人工协作时，
> 先量一量"3 个成员同时采详情，站方有没有异常"。这个数现在**没有**，是已知空白。

### 5.2 难点二：不能只信成员说"我采好了"

**风险描述**：回传数据来自别人的设备。管理员若直接 merge，
一个 bug 或一次串帖就会污染权威库，而"完整性体检"跑在权威库上，会把别人的错判成"我们漏采"。

**解法：回传包必须自带证据，且管理员端复算**。

回传包（每个 tid 一个）至少带：

| 字段 | 用途 |
|---|---|
| `tid` / `pages_total` | 主键与页数 |
| `head_pid` / `tail_pid` | 跨页头尾 |
| `page_pids`: `[[pid,...], ...]` | **逐页有序 pid 集合**（不是并集！并集会丢掉"哪一页有哪些"） |
| `anchor_digest`: 每页锚点原文的 SHA-256 | 成员端"我看到的锚点"的指纹 |
| `posts`: 每楼 pid/floor/author/time/content/chars/images | 正文本体 |
| `integrity`: 成员端自检结果（problems/warnings 分开） | 成员端也跑同一套判据 |
| `agent_version` / `msyt_version` | 版本闸（§5.4） |
| `fetched_at` / `elapsed` | 时间线 |

管理员端收到后**必须自己复算**（不是相信成员给的 `integrity` 字段）：

- `set(page_pids[p])` 必须等于该页期望的锚点集合 → 成员端已做过一次，管理员再做一次作为交叉校验
- `head_pid` 必须是 `floor==1` 的那楼；`tail_pid` 必须是最大楼层号那楼
- 每楼 `chars>0`
- 页数与 `page_pids` 长度一致

**任一条不过 → 整帖退回，不 merge，理由入 `fetch_log`。**

> ★ 这条与 §5.3 的抽样复核是**两道不同的闸**：
> 前者是**结构闸**（自洽性），后者是**内容闸**（与站方真相是否一致）。
> 结构闸能挡住 bug 和串帖，挡不住"结构正确但内容是错的"。

### 5.3 难点三：结构对但内容错 —— 需要事后抽样复核

**风险描述**：站方内容对已回复的帖基本静态，但**列表页的元数据会漂**（新帖插入、回复数变化）。
成员在不同时间采同一帖，列表元数据可能不同。
更麻烦的是：**万一有成员版本的解析逻辑有 bug**（比如把 `来自 N#` 误判成 floor=0），
结构闸可能照样通过。

**解法：抽样复核（content gate）**。

管理员随机抽 N 个已回传的 tid，**自己重采一遍**，比对正文哈希：

- 一致 → 记录"该成员此批可信度 +1"
- 不一致 → 该成员此批**全部标记待查**，并进入人工复核

站方已回复帖的内容稳定，所以复核技术上可行。
**但成本要算清楚**：复核 N 帖 = 管理员多采 N 帖的请求量。
→ 所以必须**按批次抽**，而不是每帖都验（比如每批抽 5%）；
→ 且抽的是**最可能出错的**那批（比如成员首次运行、版本刚升级、涉及置顶楼的帖）。

> ⚠️ **这是本设计里成本与收益最不平衡的一环**。
> 未决问题见 §12：复核比例定多少，需要用阶段 1/2 的实际数据来定，不宜现在拍死。

### 5.4 难点四：成员端的版本漂移

**风险描述**：`msyt` 的解析逻辑**深度绑定站点结构**，
而这轮开发里我们已经踩过三个坑：
① pid 判据从"子集"收紧到"精确相等"；
② 单页帖请求 `page=2` 会**回绕**返回第 1 页；
③ 楼层号是 `N#` 形态、置顶楼在首页显示「顶 来自 #」**无号**。

如果成员跑的是旧版本：
- 旧版用子集判据 → 串帖**放行**，回传的是串了的帖
- 旧版不封顶 → 多采一页重复内容
- 旧版 floor 取 0 → 置顶楼楼层号错

这些错误**结构闸都挡不住**（旧版自洽，只是自洽得不对）。

**解法：版本闸（version gate）**。

- 控制面存当前 `msyt` 版本号（如 `msyt/1.0.0`）
- 领任务时**必须带版本号**，与控制面比对；**版本不符 → 拒绝领任务**，返回升级指引
- 升级包就是 `msyt` 包本身，成员跑一条 `pip install -U` 或换 git 目录
- 回传包里的 `agent_version` 也要再核一次（防止中间升过级）

> ★ **这条是 §5.3 的前置**：版本闸保证"所有成员用同一套判据"，
> 抽样复核才是在这个前提下查"这套判据本身对不对"。

### 5.5 难点五：token 时效 < 30 秒 —— 任务下发到实际请求之间不能有延迟

**风险描述**：`ajax_getpost.php` 的 `token` **有效期实测 < 30 秒**，
过期后服务端返回 `code=0`「数据不存在，请刷新整个页面重试。」——**不告诉你真实原因**。

由此推出两条硬规则：

1. **token 必须在成员端现取**，不能在中心预取后随任务下发。
   任务指令里只放 `tid`，成员拿到后自己走「取页 → 立刻 ajax」。
   （`msyt` 的 `Client.get()` / `Client.get_nowait()` 已经把这条纪律编码进去了。）

2. **限速必须加在"对象之间"而非"逻辑步骤之间"**。
   现有 `msyt` 已经区分：`get()` 会限速（取新帖时），
   `get_nowait()` **绝不**限速也**绝不**重试（token 即用，重试用的是同一个过期 token，必然还是失败）。
   → 成员端 agent **必须复用这个区分**，不能图省事统一成一个带 sleep 的请求函数。

> 这条在分布式下更容易踩：中心下发任务 → 成员领任务 → 成员起进程 → 才发第一个请求，
> 中间只要 token 是在中心取的就已经过期了。**架构上必须让 token 只存在于成员端内存里。**

### 5.6 难点六：成员设备不可靠（关机、断网、跑一半、被叫去吃饭）

**风险描述**：这是协作场景的常态，不是异常。

**解法：租约 + 心跳 + 死信**。

| 机制 | 做法 |
|---|---|
| 领任务 | 控制面发任务时带 `lease_until = now + 15min` |
| 续租 | 成员每完成一页就 POST 一次心跳，延长租约；**续租同时上报"已完成到第几页"** |
| 超时回收 | 租约过期 → 任务回池，状态 `requeued`，并记录回收原因 |
| 重领续传 | 成员重领到同一 tid 时，**带上自己本地的 `pages_done`** → `msyt` 现有 `collect_one(tid, pages_done=...)` 直接续 |
| 死信（DLQ） | 同一 tid 连续失败 N 次（超 `detail_max_attempts`）→ 进 `fetch_log` 的死信区，**不再自动重试**，等人工处理 |

> ★ **"重领时带 pages_done"是本设计里最漂亮的一处复用**：
> `msyt` 的断点续传本来就是按页的，成员端本地 SQLite 记着"我采到第 2 页了"，
> 任务回到池子再被领走时，从第 3 页继续 —— **已采过的楼层不重复请求**。
> 这条直接省掉了协作场景里最大的一块重复流量。

### 5.7 难点七：数据一致性 —— 同一帖被两个人采了怎么办

**解法：三层仲裁**。

1. **幂等 merge**：pid 是主键，`upsert` 语义 → 同一份结果回传 N 次，结果一样。
2. **合并并覆盖 + 留痕**（★ 2026-10-23 定稿的口径）：
   成员回传的楼层里，**同一帖同一楼层（pid）用成员版覆盖本地版**；
   成员多采到的楼层**直接加进来**（这就是增量）；本地有、成员没采到的楼层**保留**
   （不因成员少采而丢数据）。覆盖与新增都记进 `assist_conflicts`，
   界面「合并记录」里能查到：谁回的、覆盖前是什么、覆盖后是什么。
   **不跳过。**
   - 为什么敢覆盖而不担心写脏：
     · 楼层号有 CASE 兜底（置顶楼 `floor=0` 不会覆盖真楼层号，见第 3 条）；
     · 内容质量判据在**成员端就已闭环**（同一套完整性判据），成员传回来的东西本身是过判据的；
     · 覆盖前的值留在冲突表里，**事后可回溯**。
   - 计数（楼层数 / 字数 / 头尾 pid / 页数）**一律现算**合并后的真实值，
     不用成员报上来的数字 —— 那只是它自己那一份。
3. **楼层号兜底**：置顶楼在首页渲染无号 → 成员端可能拿到 `floor=0`。
   入库沿用现有写法：`CASE WHEN excluded.floor>0 THEN excluded.floor ELSE posts.floor END`。
   → **两边的兜底逻辑必须一致**，这也是版本闸的另一个理由。

### 5.7b 难点七之二：站方会追加回复 —— 已采过的帖**可能有增量**

站方不是静态的：一帖被采完之后，它可能又被人回复了，楼层数变多。
「上次采完就当采完了」是不成立的。

**增量的权威信号是站方自己给的数字**：列表页每一行都带「回复数」。

| 环节 | 做法 |
|---|---|
| **识别** | 列表采集时，同一个 tid 的 `replies` **比上次采集时变大了** → 判定站方又回复了 |
| **标记** | `threads.detail_state = 'stale'`（内容过时，待更新），并把该 tid 丢回 `detail_queue`（`pending`，attempts 归零） |
| **补齐** | 下一次详情采集任务自动把它捡走重采；新楼层按 §5.7 的规则合并进来（覆盖 + 新增） |
| **可见** | 体检页「已识别的增量」栏列出这些帖，可勾选后一键「重跑所选」 |

**实测（2026-10-23）**：重采 `dept:1098` 时打出了
`↻ 1 帖站方有新回复（#7477636 1→4）→ 已标记待重采`，
该帖随即变成 `stale` 且队列里 `state=pending` —— 链路跑通。

> ★ **只有"变大"才判增量**。变小可能是站方删楼，也可能是列表行解析抖动 ——
>   宁可不报，也不能把好数据误判成要重采（重跑是要花站方请求的）。
> ★ 顺序不能反：**必须在 `upsert_threads` 之前比**，否则回复数已经被覆盖成新值，
>   永远比不出变化。

> ★ **别把增量与"站方计数不自洽"混为一谈**（§5.8）：
>   「站方称 N+1 楼、本地实收 N 楼」是**站方自己的计数问题**（常见，差 1），
>   既不算我们漏采，也**不算增量**。界面把两者分列在不同栏里，就是防止混淆。

#### 5.7b-2 增量还要认「**受理状况**」（2026-10-23 补）

上面只比了「回复数」。但站方列表行里还有**受理状态**，而它是**独立**的一条信号：

| 站方的动作 | 回复数变了吗 | 只比回复数能检出吗 |
|---|---|---|
| 群众留言被**受理**（未受理→已受理） | **不变**（还没回复） | ❌ **完全检测不到** |
| 站方**回复**（已受理→已回复） | 变大 | ✅ 能 |

★ 「被受理」是舆情分析里**最关键的状态推进**（群众等的就是这一步）。
  只看回复数，等于**只看得见"被回复"，看不见"被受理"**。
★ 而且受理状态一变，本地数据**确定**过时：详情页里有一份**受理流程时间线**
  （`flows`），站方受理 = 流程上多一步 → 本地那份少了新的一步 → **必须重采**。

**判据**：`old_state` 与 `new_state` **都是有效状态**（已回复/已受理/未受理）且不同
→ 判为增量 → 标 `stale` 丢回队列。
「变空」**不判**（老帖在某些列表页有状态、某些页没有，那是渲染差异），
但会**记进列表变更留痕**，需要时查得到。

#### 5.7b-3 列表采集阶段也要**留痕**

列表采集是 **upsert 覆盖** —— 旧值一被盖掉就**永远查不到了**，
增量检测只能在覆盖前那一瞬间比一次，比完就没了。
新增 `list_changes` 表把「覆盖前那一瞬间」**存下来**：

| kind | 含义 |
|---|---|
| `new` | 该 tid 第一次出现在这个源 |
| `state` | **受理状态**变了 |
| `replies` | 回复数变了 |
| `title` | 标题被改了 |

（浏览数不记 —— 每趟都涨，全是噪音。）
界面在体检页多一栏「**列表阶段的变化（站方动过哪些帖）**」；
`fetch_log` 里也同步记，列表阶段从此有日志可查。

**实测**：真实采 `dept:1113` 一页，当场抓到
`tid=8343926 未受理 → 已受理`（回复数没变，正是只比回复数会漏掉的那类）。

### 5.7c 体检页的两个动作：**重跑** 与 **自行清除**

体检（管理员专属）发现不一致时，给两条路：

| 动作 | 行为 | 适用 |
|---|---|---|
| **重跑** | 丢回队列重新采一遍（软失败）—— **数据保留**；采到的新楼层按 §5.7 合并进来 | 大多数情况（只是没采全 / 过时了） |
| **自行清除** | 楼层 / 分页凭据 / 受理流程 / 队列项**全部删光**，计数归零，状态回 `pending` | 怀疑本地这份是**脏的**（内容被改坏、串帖） |

- 两者都**按批**做（勾选多条一起做），不一帖一帖点。
- 「清除」是破坏性操作 → 界面**二次确认**，并把「删了多少楼层、多少页凭据、多少条流程」显示出来。
- 两个端点都 `require_admin`；成员调 → 403（实测）。

### 5.8 难点八：站方计数不自洽 —— 协作后更不能拿它当判据

**实测**：tid=8332684 列表页写"回复 5"，实际就 5 个楼层（楼层标签最大 `5#`）。
成因未查明（删楼未减计数 / 置顶回复被重复计数）。

**结论**：站方回复数**只能当旁证**。现有的处理已经是"硬判据只留头/尾/页数/pid 集合，
回复数降级为软警告"——**分布式后这条不变**。
成员回传的 warnings 也要**和 problems 分开统计**，否则站方计数问题会被算成"我们漏采"。

> ★ 附带纠正一条容易踩的：**置顶回复会让"锚点出现次数"比"楼层数"多**。
> 实测 tid=8339985：锚点 34 次 → 去重 33 楼。
> 所以"数楼层"一律按 **pid 去重**，不要按锚点出现次数。
> 人工复核件见 `复核\postmsg锚点_人工复核.csv`。

### 5.9 难点九：站方**不公开历史帖正文** —— 协作池的活有一半是「采不出来的」

**实测（2026-10-23）**：站方详情页对**历史帖子**只给一个「提示信息」页，
页面里明写 **「历史帖子仅限作者本人查看」**。

| 观测 | 结果 |
|---|---|
| 三个不同 tid 的详情页 HTML 长度 | **完全相同（22,705 字节）** —— 同一个模板 |
| 页面里的楼层锚点 `id="post_N"` | **0 个**（正常帖 1–33 个） |
| 可见边界（用**库里真实存在的 tid** 逐个试） | tid **8074362 可见** / tid **8074198 不可见** |
| 边界附近（tid 8.1M–8.34M）抽样 30 个 | **全部可见** |
| 老帖（tid 6.26M–6.69M）抽样 6 个 | **全部不可见** |

> ★ **探边界必须用库里真实存在的 tid**：随手编的 tid 会拿到 **404**
> （帖子不存在），与「帖子存在但正文不公开」是两回事。
> ★ 这个边界是**滚动的时间窗**，会随时间往后挪 → **不能写死在代码里当判据**，
> 必须**运行时识别提示页**。

**这一条对协作是致命的**，因为它同时打掉了两个前提：

1. **「先旧后新」的建池顺序会产出全是白跑的活** ——
   越老越采不到正文。协作池**必须改成「先新后旧」**。
2. **「回传为空」不等于「成员失败」** ——
   老帖在站方那边对非作者就是不给正文，成员采一百条也是空。
   记成 `failed` 会让成员看着自己的失败数一路涨而完成数永远是 0。

**口径（用户 2026-10-23 明确）**：**标记、写入正文，但不计入「已采详情帖」**。
落地为独立状态 `restricted`（详见《方案报告》§9.9）：

- 帖状态 `detail_state='restricted'`；正文插一条 `pid=-tid` 的**标记行**
  （负数，不与真实楼层撞号），`posts_n=0`
- 协作活状态记 `restricted`（**不是** `failed`），界面**独立一栏**
- 体检页单列一栏，**不提供勾选重跑**（重跑多少次都是同一个提示页）
- 「已采详情帖」**不含**受限帖；「楼层总数」**不含**标记行

### 5.10 难点十：协作池会被「领了不干」的人占死

成员的机器**不可靠**（§5.6 已经讨论过）。在协作场景下，
「领了活就关机」不只是丢一帖，而是**把整池子占死**：
活卡在 `taken`，别人领不到，而界面上显示的是「各节点贡献 5000」——
看着像在采，其实一条没做。

三条修法（缺一不可）：

| 修法 | 作用 |
|---|---|
| **主动退活** `POST /api/assist/return` | agent 退出前把手里**还没回传**的活还给池子 |
| **启动时先退自己上次遗留的活** | 上轮可能被 Ctrl+C / 被 kill / 窗口直接关掉 → `finally` 没跑成 → **本节点把自己堵死**（领活 SQL 只取 `pending`） |
| **回收看「节点是否还在线」** | agent 活着就每 12 秒发心跳；心跳断了 2 分钟 → 它不可能还在采那条活 → **立刻退回**，不必等 30 分钟超时 |

★ 配套：**agent 领不到活时必须说话**。旧实现里空转一声不吭，
界面上只看得到「运行中但很久没动静」，用户分不清是「卡住」还是「**没活可领**」。
现在 agent 自报状态（`collecting` / `idle`），通过**日志标记行**与**心跳**两条路传给界面。

> ★ 附带一条自己写出来的 bug，值得记：**SQLite 的 `AND` 优先级高于 `OR`**。
> 回收条件写成 `WHERE state='taken' AND (A) OR (B)` 时，第二段 `B` **不受**
> `state='taken'` 约束 → 某节点心跳断了 2 分钟，它名下 **438 条已采完的活**
> 被退回池子，完成数从 466 掉回 56。**OR 组必须整体括起来**。

### 5.11 难点十一：成员的采集**不能在服务器上**跑 —— 必须走本机 agent

2026-10-23 用户问「组员使用这个功能应该也需要 Agent 吧」，问出一条比界面更严重的漏洞。

**漏洞**：`/api/jobs/list` 等三个采集端点用的是 `require_auth` 而非 `require_admin`
→ 成员在网页点「开始采集」，任务 spawn 在**管理员的服务器进程**里
→ **用管理员的机器和 IP 去刷站方**。实测：成员点一次，一个源的水位线被推进，
管理员的 IP 真的去请求了站方。

**为什么这条致命**：整个方案的价值主张是「站方看到的是**多个分散的普通用户**」。
服务器端采集一开，成员越多、站方看到的**集中度越高** ——
等于自己把「分布式」这个卖点抹平了，还白耗管理员的机器与带宽。

**而且它本来就只能在成员机器上**：

| 事实 | 含义 |
|---|---|
| 站方**不提供 CORS**（一个头都不给） | 浏览器里的网页**不能**直接采站方 → 成员的采集**必须**跑在自己机器的程序里 |
| 站方按 IP 看流量形态 | 分散在 N 台成员机器上采，才是「多个普通用户」 |

**落地**（一条「本机采集」通路）：

```
成员在网页选目标 → 网页 POST 127.0.0.1:8766/start（带 token + 目标）
  → 本地助手拉起 agent（--local --sources/--tids/--pages）
  → agent 在成员自己机器上采 → 回传：
       列表元数据 → /api/agent/ingest-list（幂等入权威库）
       详情正文   → /api/assist/submit（与协作同一条合并路径）
```

三条设计要点：

1. **服务器端采集端点收成管理员专属**（成员 403 + 提示语说清要本机 agent）。
2. **元数据回传不推水位线** —— 水位线是**权威续采状态**，
   多机共推会让管理员的续采从被推高的位置开始 → **中间的页被静默跳过**（漏采且无痕）。
3. **本机续采要先问水位线**（`GET /api/agent/watermarks`），
   从 `last_page+1` 接着采 —— 否则会把管理员已采过的页又请求一遍，白耗站方。

**实测**：全新源 `dept:1099` 由成员本机采 2 页 → 采到 177 帖、回传 177 帖入库，
**该源在服务端仍无水位线**；详情正文定点补采 → 权威库楼层 0→1、状态 `done`。
回归 `_tools/test_local_collect.py` 14 项全过。

### 5.12 协作任务要能**撤销** —— 且「已完成的不废弃」

2026-10-23 用户提的：「协作任务应该需要可以撤销，已经完成的不废弃」。

**撤销 ≠ 砍掉**。它是「**停止派活**」：

| 那些活 | 处置 | 为什么 |
|---|---|---|
| 已完成 / 失败 / 站方限制 | **原样保留** | 正文已进权威库 —— 撤任务不该把**已采到的东西**一起废掉 |
| 未完成（pending / taken） | 标成 `cancelled`（**不删**） | 留痕可查，也能**恢复** |
| 权威库里的正文 | **一个字不动** | 正文独立于任务存在 |

★ 正在被成员领着的那几条：成员采完回传时状态会改回 `done`
→ **数据不浪费**。撤销不是砍，是停止派活。

★ 为什么撤销**要能恢复**：撤销常常是"发错了任务 / 部门选错了"的补救，
不可恢复的撤销会把"补救"变成"事故"。

★ 一个容易漏的计数坑：完成数若直接读 `assist_tasks.done` 那一列，

### 5.16 抗抖动：一次瞬时断连不该让组员的活停在半路

2026-10-23 晚上，组员在公网上跑 agent 时贴了实测日志：

```
19:23:18  已启动 agent
19:23:59  ⚠ 连接失败：ReadTimeout ... (read timeout=40)（连续第 1 次）
19:24:52  ⚠ 退活失败（不影响采集）：... (read timeout=40)
19:25:21  ⚠ 连接失败（连续第 2 次）
19:25:46  ✗ 连续 3 次联系不上控制面 —— 判定为失联，自动停止采集。
```

**107 秒**就判死、停了采集。用户反馈：「连接超时似乎设置长了，感觉以网络连接，
个人觉得可以 30s 以上一次，不然可能容易连接超时」。

#### 5.16.1 病根：三条全是「太急」

| # | 旧值 | 问题 |
|---|---|---|
| ① | `timeout=40` | 网络不通时**每个**请求白等 40 秒，连「取身份」「退活」也等满 |
| ② | 失败后等 **1~5 秒**重试 | 网络还没恢复就连撞 |
| ③ | 连续 **3 次**判失联 | 107 秒容忍，**一次瞬时抖动就够** |

★ 还有个隐藏问题：**心跳与主请求共用一个失败计数** ——
  采一帖要几十秒，主请求不发出、只有心跳在跑，两者同时失败计数翻倍，
  「连续 3 次」其实只有 **1.5 轮**。

#### 5.16.2 改法

```python
HTTP_TIMEOUT    = 20                  # 单次请求（旧 40）
HTTP_TIMEOUT_AUX = 10                 # 辅助请求：取身份 / 退活
RETRY_BACKOFF   = (30, 45, 60, 60, 60)  # 失联重试间隔，≥30 秒
FAIL_LIMIT      = 4                   # 主请求连续失败几次判失联（旧 3）
HB_FAIL_LIMIT   = 6                   # 心跳连续失败几次单独判失联
```

| 改动 | 理由 |
|---|---|
| timeout 40 → 20 秒 | 实测公网正常延迟 **1.4~2.3 秒**，20 秒有近 10 倍余量 |
| 辅助请求 10 秒 | 失败不影响主流程，不值得占 20 秒 |
| **重试间隔 ≥30 秒** | 用户明确要求。给隧道/网络恢复时间，别急着放弃 |
| 阈值 3 → 4 | 配合新间隔，总容忍 **≈215 秒（3 分 35 秒）** |
| **心跳独立计数** | 不再与主请求混算；任一方成功都清零另一方 |
| 票据兑换不计失败 | 票据一次性，兑换失败重试也没用 |
| 日志说清等多久 | 「等 30 秒后重试（网络/隧道恢复需要时间，别急着放弃）」 |

★ 思路不是「多等一会儿」，而是「**更快发现失败 + 更慢放弃**」。

### 5.19 隧道协议可配，QUIC 不通时自动换 http2

2026-10-23 晚上实测踩到：公网一直 **502**，而本地服务完全正常。
隧道日志：

```
ERR failed to dial to quic connection
    error="failed to dial to edge with quic: timeout: no recent network activity"
```

★ 根因：**QUIC（UDP）到 Cloudflare 边缘不通** —— 某些网络环境对 UDP 限速或丢弃。
  迷惑性极强：本地一切正常，只有公网挂。

#### 5.19.1 改法

新增配置 `程序/data/tunnel-protocol.txt`：`quic` / `http2` / `auto`（默认 auto）。
`auto` = **先试 quic，不通自动换 http2**（走 TCP —— UDP 被限时 TCP 通常不受影响）。

实测：手动加 `--protocol http2` → **立刻通**（agentapi 401 = 到了源站）。

#### 5.19.2 这一节正好印证 §5.16

★ 隧道闪断是**真实场景**：20:00 它断了一次（QUIC 超时），
  组员 19:23 也遇到过一次 ReadTimeout。

所以两层都要有：
- **隧道层**：让它不容易断（协议自动回退）
- **agent 层**：断了也别慌（§5.16 的 ≥30 秒退避 + 3.5 分钟容忍）

★ 但别误解：**agent 挺过去 ≠ 隧道修好了**。两层都在，
  才不至于一次网络抖动就让组员的活停在半路。

### 5.20 回传失联要重试；组员侧参数要比本机宽松

2026-10-23 晚上，用户三条：
①「服务不要停修一下分发包机制」（**组员正在采集，不能重启服务**）
②「我这边与 Cloudflare 的连接有优化，不过组员不一定有，组员比我这边更加容易触发失联」
③「另外回传后失联就断开，不重试不大合理」

#### 5.20.1 病根：回传一次超时 = 一帖白采 + 整个 agent 停

组员实测日志：
```
20:52:11 ✓ 2 页 / 212 字              ← 已采 21 帖，都正常
20:52:33 ⚠ 连接失败：ReadTimeout (read timeout=20)（连续第 1 次）
20:52:33 ✗ tid=8342251 回传时失联，本帖丢弃（数据只在内存里，不会残留）
20:52:36 结束：完成 20 帖，失败 1 帖（因与控制面失联而自动停止）
```

旧实现里那一句 `break` 跳出整个采集循环 → 剩下 **29 帖全不采了**。

#### 5.20.2 改法一：回传带退避重试，失败只放弃那一帖

| 情形 | 旧 | 新 |
|---|---|---|
| 回传时一次超时 | 本帖丢弃 + **整个 agent 停** | 退避 30/45 秒后**重试** |
| 重试成功 | — | 正常计入完成，**数据没白采** |
| 重试 3 次仍失败 | — | 只放弃**这一帖**，**继续采下一帖** |
| 连续 4 帖都失败 | — | 才判定控制面不可用，停止 |

★ **重试是安全的**：回传走「合并覆盖」语义 → **幂等**。
★ 一个坑：`submit()` 成功后会**清空 payload**（传完即删），
  所以重试前要确认正文还在，计数/摘要要在每次尝试前重新取。

#### 5.20.3 改法二：组员侧参数比本机宽松

★ 管理员本机走 `127.0.0.1` 直连，组员走**公网**
  （agent → Cloudflare 边缘 → 隧道 → 源站），多好几跳、延迟高得多。
  同一套参数对两边不公平。

| 参数 | 上一版 | 现在 | 为什么 |
|---|---|---|---|
| `HTTP_TIMEOUT` | 20 秒 | **45 秒** | 公网慢，组员实测连续 ReadTimeout 20 |
| `HTTP_TIMEOUT_AUX` | 10 秒 | **15 秒** | 辅助请求也经公网 |
| `FAIL_LIMIT` | 4 | **6** | 组员更容易触发失联，阈值低会误杀 |
| `HB_FAIL_LIMIT` | 6 | **8** | 同上 |
| `PROBE_TIMEOUT` | 8 秒 | **20 秒** | 选址探测走公网 |

★ 45 秒对本地也够用（本机 1.4~2.3 秒），所以不用做「按来源分参数」那套。

#### 5.20.4 ★ 全程没有重启服务

组员当时正在采集（957 条回传痕迹，最后一条 21:11:20），
所以改动**全部落在 agent.py（组员端）**，服务端零改动。
且启动包是**每次下载现场生成**的 → 改完 agent.py 不需要重启，
组员重新下载包就拿到新代码。

★ 隧道层（§5.19）让它不容易断，agent 层让它断了别慌 —— 两层都要。

### 5.21 分发包机制：助手**自动更新**，组员不用反复重下包

### 5.23 数据缺口：「少贴」的帖保留原帖 + 标记 + 作增量补采

2026-10-23 晚上，用户：
「另外，就是数据缺口的情况
  建议如果有少贴的情况下，保留原贴并且标记
  主要是作增量的补采」

#### 5.23.1 现状问题

「完整性体检」里，「站方称 N+1 楼、本地实收 M 楼」被归成
「软警告（**不算漏采、也不算增量**）」→ **缺口永远留在库里，不会被补采**。

#### 5.23.2 先分清两种「少」（实测 400 个 done 帖）

| | 楼层号 | 结论 |
|---|---|---|
| **尾部少** | 连续（[1,2,3,4,5]） | 站方**还有楼我们没采到** → **增量，该补采** |
| **中间缺** | 有缺口（[1,3,4]） | 站方**删楼/置顶** → 补采没意义 |

实测：392 个「站方称 replies+1」是对得上的（replies 不含楼主，+1 是楼主）；
少数对不上且楼层连续 → 尾部少 → 该补采。

判据抽成可测函数 `is_short_and_retryable(expect, got, floors)`。

#### 5.23.3 处置：保留 + 标记 + 入队

复用 §5.12 的 `db.mark_detail_stale()`：
`detail_state='stale'`（界面显示「待更新」）+ `detail_queue` 置 pending（自动重采）
+ **原帖数据一条不删**。

#### 5.23.4 ★ 三个坑

| 坑 | 后果 | 正解 |
|---|---|---|
| 只在**采集时**标记 | 「少贴」的帖是 done，采集只捡 pending/stale → **永远不会被重采 → 死锁** | **体检时也标记**（体检是管理员主动触发的找问题动作） |
| 标记写在 `set_thread_detail(state='done')` **之前** | 标记被覆盖回 done → **白标一次** | 先算标志，**写完 done 之后再动作** |
| 补采次数没写进 `detail_warn` | 读出来永远 0 → **上限失效 → 无限重采** | 标记时把 `reason + 「已补采 N 次」` 写进 `detail_warn`，**读在写之前** |

上限 `GAP_RETRY_MAX = 2`：补两次还对不齐 → 判为站方计数口径差异，只留告警不再自动补采。

#### 5.23.5 界面分类

| | 改前 | 改后 |
|---|---|---|
| 少贴（尾部少） | 软警告「不算增量」 | **增量栏**「已标记待补采」 |
| 楼层号缺口（中间缺） | 软警告 | 软警告（明说「不补采——那楼已经不存在了」） |

| **[Crawlab](https://github.com/crawlab-team/crawlab)**（BSD-3-Clause） | Go 写的 Master/Worker 分布式平台；Master 与 Worker 之间用 **gRPC**；任务队列存在 **MongoDB**；用 **SeaweedFS** 同步爬虫代码；节点在线靠 Redis 的 hash 判定 | ★ **架构范式最贴**：主控/工作节点分离、节点在线判定、任务与代码同步 | **借鉴架构，不装**（要 Docker+Mongo+SeaweedFS；且 `msyt` 不是 Scrapy，得包成 shell 脚本调用） |
| **[Scrapyd](https://scrapyd.readthedocs.io/)** | Scrapy 官方调度服务，Twisted 异步，HTTP API 启停，`.egg` 包分发 | 极简 HTTP 调度 API 的思路 | 借鉴思路；`.egg` 分发对 `msyt` 不适用 |
| **[Gerapy](https://github.com/geekan/gerapy)** | 基于 Scrapyd 的 Django + Vue 可视化面板 | 节点分组、指标看板、任务编排的界面思路 | 借鉴界面；不装（重度依赖 Scrapy） |
| **[Firecrawl 自托管](https://github.com/firecrawl/firecrawl)**（AGPL-3.0） | 7 服务栈：api + playwright + redis + rabbitmq + postgres 队列 + foundationdb | ★ **队列形态参考**（Redis + RabbitMQ + PG queue）；也提醒我们"自托管爬虫平台 = 一堆中间件" | **不装**：太重，且我们不需要浏览器渲染（站方是服务端渲染的） |
| **ScrapydWeb / SpiderKeeper** | Scrapy 生态的轻量面板 | 轻量级取舍的参照 | 不装 |

### 7.2 任务队列类（Python）

| 项目 | 状态（2026 核对） | 对我们的借鉴 |
|---|---|---|
| **[Celery](https://github.com/celery/celery)** | 生态最成熟，但配置面大、依赖树重 | broker/worker 分离、`acks_late` 语义的思路 |
| **[Dramatiq](https://github.com/Bogdanp/dramatiq)** | ★ **默认带死信队列（DLQ）** | ★ **最值得借鉴的一点**：超限失败进 DLQ 而不是无限重试 → §5.6 |
| **[RQ](https://github.com/rq/rq)** | Redis-only，极简 | 极简队列 |
| **[Huey](https://github.com/coleifer/huey)** | ★ **支持 SQLite / 文件后端，零必需依赖** | ★ **最贴近本机约束**（本机没 Redis）——但它做的是**本机** worker，不跨机 |
| **[TaskIQ](https://github.com/taskiq-python/taskiq)** | async 原生，broker 插件化 | 太超前，`msyt` 是同步的 |
| **[arq](https://github.com/python-arq/arq)** | ⚠️ **已进维护模式** | 别选 |
| **[Procrastinate](https://github.com/procrastinate-org/procrastinate)** | 纯 PostgreSQL，`FOR UPDATE SKIP LOCKED` | 用数据库当队列的思路（我们用 SQLite，等价物是 `BEGIN IMMEDIATE`） |

> **队列选型的结论**：本机**没有 Redis**，装 Redis 是为了跑一个队列而引入一个常驻服务。
> `msyt` 已经是 `sqlite3` 原生风格，**任务队列直接用 SQLite 表 + 事务** 即可，
> 零新增依赖、零新增进程、还能跟现有库放在一起备份。

### 7.3 身份认证类

| 项目 | 星标量级（2026-10-21 核对） | 部署代价 | 对我们的借鉴 |
|---|---|---|---|
| **[Keycloak](https://github.com/keycloak/keycloak)** | 37.4K | Java + PostgreSQL | 重 |
| **[authentik](https://github.com/goauthentik/authentik)** | 26K | Docker + PostgreSQL + Redis | 重；但它的 **forward-auth 两阶段**（"能不能进" vs "是谁"）很有启发 |
| **[Logto](https://github.com/logto-io/logto)** | 14.7K | Node + DB | 中等 |
| **[ZITADEL](https://github.com/zitadel/zitadel)** | 15.4K | Go + DB | 中等 |
| **[Ory Kratos](https://github.com/ory/kratos)** | 13.9K | Go + CockroachDB/Postgres | API-first 身份服务 |

> ★ **对 authentik 那篇的实测教训特别认同**（它把 SSO 搞砸两次）：
> ① **身份服务自己的登录路由绝不能放在它自己的鉴权后面**（否则无限循环把自己锁门外）；
> ② forward-auth 是**两个独立阶段**——"准不准进"和"进来的是谁"要分别验证，
> 只验第一阶段会出现"能进但应用里是 guest"的鬼状态。
>
> **映射到我们这里**：控制面必须留一条**不经过登录的应急通道**
> （本机直连 `127.0.0.1` 或一个只有管理员知道的本机命令），
> 否则**域名解析、隧道、账号表任一坏了，管理员自己也进不去**。
> 这条要在设计里显式写出来，不能靠临场发挥。

| 层 | 候选 | **推荐** | 理由 |
|---|---|---|---|
| 接入 | Nginx / Caddy / cloudflared | **cloudflared（已装）** | 已有域名 + 自动 TLS，零新增配置 |

## 8. 合规与边界（必须写进设计，不是附录）

延续 `msyt` 既有纪律，这套系统**一个字都不能破**：

| 边界 | 内容 |
|---|---|
| **只读** | 不注册账号、不做短信认证、**不做任何写操作**（不发帖/回复/点赞/收藏）。成员端同样受此约束 —— agent 的代码里根本不该有写接口 |
| **教学用途** | 站内版权声明要求内容未经授权不得擅自使用或转载 → 数据**仅用于课程分析**，不转载、不公开原帖全文 |
| **成员不得二次分发** | 成员拿到的原始正文**只在协作范围内使用**，不得转发、不得上传到第三方服务 |
| **个人信息** | 作者 uid、昵称属个人信息 → 权威库内保留（分析需要），**导出物一律脱敏** |
| **成员账号不得共享** | 一人一账号，退出协作即吊销；审计日志能追到人 |
| **不绕访问控制** | 站方匿名可读，不存在需要绕过的东西；系统里不写任何绕过逻辑 |
| **配额可回收** | 管理员随时可停某成员、停全局；熔断时一键全停 |

> ⚠️ **一个容易被忽略的风险**：成员设备一旦被入侵或装了恶意插件，
> 理论上可以借我们的任务通道去打任意 URL。
> 对策：**agent 只允许请求站方域名白名单**（`bbs.cnnb.com.cn`），
> 任务包里除了 `tid` 不带任何可控 URL —— 从协议层就消除 SSRF 面。

| | **A. 自研薄控制面**（推荐） | **B. 装 Crawlab 改造** | **C. 纯人工协作** |
|---|---|---|---|

**推荐路线：A 为主，但先走 C。**

理由：C 用现成的 `msyt detail --tid` 和 `msyt export` 就能跑，
**当天可试**，而且能验证三件纯代码解决不了的事：
① 成员到底愿不愿意干、投入多少时间；② 回传用 CSV 够不够、还是需要结构化包；
③ 站方在"多人同时采"下的真实反应（这直接校准 §5.1 的配额参数）。

把这三件事摸清楚再写控制面，不会白写。

## 10. 界面构想（看板要回答的四个问题）

一个页面，四块，每块对应协作里真实会被问的问题：

1. **还差多少** —— 全局覆盖度（按部门/时段/类别的完成率），
   直接用 `msyt stats` 的口径 + `detail_queue` 的 state 分布。
2. **谁能干** —— 成员在线状态、今天各采了多少、额度余量。
3. **我该干什么** —— 可领任务列表（Pull）+ 我发布的协助请求状态（Push）。
4. **哪里要人看** —— 待仲裁的冲突、被熔断的帖、软警告（站方计数不自洽等）。

> 看板的**数据源全部已经在库里**，不需要新表：
> `threads`（覆盖度）、`detail_queue`（任务）、`fetch_log`（审计/警告）、`threads_fts`（检索）。
> 这一点是本设计能"薄"的技术前提。

## 12. 已知局限与未决问题

### 12.1 设计上的已知局限

1. **抽样复核的成本与收益不平衡**（§5.3）。复核比例、抽哪一批，现在没有数据支撑，不宜拍死。
2. **"站方压力预算"是空白**（§5.1）。目前只有单机 12/12 成功的证据，
   多节点并发下站方的实际阈值**完全未知**。P1 就是为了测这个。
3. **成员设备不可控**。P4 的熔断能止损，但控制不了成员在站方网页上手动乱点。
4. **仲裁规则依赖"站方静态"这个假设**。若站方改了已回复帖的正文，
   冲突检测会误报。需要在 P2 时记录时间戳，判断冲突是"站方改了"还是"成员采错"。
5. **单点仍是单点**：管理员设备宕机，整个协作停摆。
   缓解：控制面无状态化（任务表在 SQLite，可备份）+ 权威库定期备份。
   但**真正的多副本主控不在本报告范围内**——对 3–8 人的课程小组是过度设计。

### 12.2 需要小组成员一起拍板的问题

| # | 问题 | 为什么必须问 |
|---|---|---|
| Q1 | 走 **Pull（领管理员派的任务）** 还是 **Push（成员自己提协助请求）**，还是混合？ | 决定控制面要不要做申请表与审批流（§3） |
| Q2 | 任务粒度定 **单帖** 还是 **某部门/某时段的一批**？ | 单帖易仲裁、易续传；批量效率高但一帖出错要整批回滚 |
| Q3 | 成员回传**必须带证据**，还是允许"裸数据"换速度？ | 带证据 = 可仲裁、可复核；裸数据 = 快但不可信。**建议必须带**，但要接受 10–20% 的额外传输量 |
| Q4 | 每批抽样复核比例定多少？ | 需要 P1/P2 的实际数据 |
| Q5 | 全局配额按**成员节点**发还是按**帖数**发？ | 前者控站方压力，后者控工作量公平性 |

> ★ **Q1–Q3 影响架构，建议在 P2 动工前用 `ask_user` 让小组成员投票**，
> 而不是由管理员单方面指定 —— 否则做完了成员不认，返工成本更高。

| **成员端启动包** | 服务端**实时生成** zip，网址按下载者当时访问的地址注入 | 成员解压 → 双击 cmd → 装依赖 → **只问账号密码** → 开跑 |
| **本地助手** | `127.0.0.1:8766`，网页可一键启停本机 agent | 助手只绑本机、只接受启停与查状态 |
| **失联自动停止** | 心跳 + 连续失败阈值 → 不再领活、采到一半中止、不回传半截 | 假控制面关掉后 agent 自己退出并汇报 |
| **增量识别** | 列表页回复数变大 → 标 `stale` + 丢回队列 | 重采 `dept:1098` 打出 `↻ 1 帖站方有新回复（#7477636 1→4）` |
| **重跑 / 清除** | 体检页勾选后批量执行 | 管理员 200 / 成员 403；清除返回删了多少楼层与凭据 |
| **软警告也可重跑** | 体检页三栏（硬问题 / 已识别增量 / 软警告）都是可勾选表格 | 站方计数不自洽的帖重跑一遍，能确认是不是真漏了 |
| **agent 专用 API 子域名** | `agentapi.…` 只开放 `/api/agent/*` | 成员机器上的 agent 没有浏览器会话，过不了 Access 的登录门 → 单独一个子域名给它，Access 对它 bypass；主域名的网页 UI 照旧受 Access 保护 |

**★ agent 为什么需要单独的子域名（2026-10-23 实测踩出来的）**

成员机器上的 agent **没有浏览器、没有 Access 的会话 Cookie**。它直接打主域名时：

| 请求 | 结果 |
|---|---|
| 无 UA（Python 默认 `Python-urllib/…`） | **403 error 1010** —— Cloudflare 的「浏览器完整性检查」拦的 |
| 带 `msyt-agent/1.1` UA | **200，但返回 46 KB 的 HTML** —— Access 的**登录页**，不是 JSON |
| 带 Access 会话 Cookie | 浏览器里才有的，agent 拿不到 |

★ 最阴险的一环：旧版 agent 拿到 HTML 后，**把"拦截"当成了"登录成功"**
（`r.json()` 失败就返回 `{"ok":True,"text":…}`）→ 于是日志显示「登录成功 · 角色 None」，
而实际上**领活也永远领不到东西** —— 看起来在跑，实际什么都没干。

两处修正：
1. `_req()` 遇到非 JSON 响应**直接报错**（"服务端返回的不是 JSON（可能被网关/登录页拦截）"），
   绝不把拦截伪装成成功；
2. 给 agent 单独开 `agentapi.<zone>`：Cloudflare Tunnel 加一条 ingress、DNS 加一条 CNAME、
   Access 建一个 `path=/api/agent/*` 且 `decision=bypass` 的应用；
   程序再按 Host 把该域名收紧成**只开放 `/api/agent/*`**（中间件，其余路径 403）。

★ 顺带两个坑：
- Cloudflare 的 Universal SSL 只覆盖 zone 本身与**一级**通配（`*.example-tld`），
  **两级**子域（`api.msyt.…`）要单独等签证书，可能一直等不到 → 所以要用**同级**子域名。
- 同一个 domain 下**只能有一个** Access 应用（path 不同也报
  `application_already_exists`）→ 同域拆路径这条路走不通，只能换域名。

**★ 「端口开着会不会被攻击」—— 怎么把门锁上**

`agentapi.…` 在 Access 那一层是 bypass（agent 没有会话 Cookie，过不了登录门），
所以端口本身是可达的。真正的门在**程序层**：

| 机制 | 说明 |
|---|---|
| **启动凭证** | 成员**在网站登录之后**（Access 邮箱验证码 + 程序账号密码）才能签发；30 分钟有效、**用一次作废**、绑定本人 |
| **免密开跑** | 凭证写进启动包的 `agent-ticket.txt`，agent 启动时自动读它换 JWT → **组员不用输密码** |
| **凭证失效有兜底** | 凭证过期/已用 → agent 明确报「启动凭证不可用」并要求账号密码（`*` 回显），**不会卡死** |
| **未登录签发 → 401** | 凭证**必须**配合网站登录，没有网站签发的凭证就换不到 JWT、领不到活、回传不了 |
| **登录限流** | `/api/agent/login` 按 IP 限流（5 分钟 10 次） |
| **域名收紧** | `agentapi.…` 上除 `/api/agent/*` 外一律 403（中间件按 Host 判定） |
| **在线可见** | 成员名单里能看到谁在跑（心跳）、谁领了多少活 |

★ 结论：**端口开着不等于门开着** —— 攻击者能打进来，但拿不到凭证就什么也干不了；
真要再紧一档，就得让 agent 也带 Access 凭证（实测 `any_valid_service_token`
在这个账号下不放行；可行的是复用浏览器的 `cf_clearance` cookie，
但它 HttpOnly，程序拿不到 —— 除非改成「网页代转」那条更绕的路）。

**★ 浏览器侧的「信任一天」**

Access 的 `session_duration = 24h` → 在浏览器登录（邮箱验证码）之后，
**这台机器一天内访问同域的任何路径都不用再输验证码**，API 也一样
（cookie 是 zone 级的，跨子域有效）。这正是「输入验证码的机子信任一天」。

★ 试过但走不通的路（避免以后重复踩）：
- `any_valid_service_token` 策略：策略写得对、token 有效，curl 带
  `CF-Access-Client-Id/Secret` 头**仍然 302**（在主域名与 agentapi 上各试一次）。
- `include: [{service_token: {id: ...}}]`：API 直接报
  `invalid 'include' configuration`。
- 同 domain 两个 Access 应用（一个 `/*` 一个 `/api/agent/*`）：`application_already_exists`。

**★ 一个关键的实测结论：浏览器不能直接采站方。**
实测站方**一个 CORS 头都不给**（`Access-Control-Allow-Origin = None`，预检也没有），
浏览器普通跨域 fetch 直接 `Failed to fetch`，`no-cors` 只能拿到 **opaque** 响应读不出内容。
所以正文采集必须由**成员机器上的 agent** 发请求 ——
好处是站方看到的是**多个分散的普通用户**，而不是一台服务器在集中爬。
**这条同时决定了"数据只在浏览器"这个原始设想不可行**，
实际落地为"数据只在成员机器的**内存**里"（同样是传完即删、从不落盘）。

**★ 另一个关键结论：给成员一条命令行是没用的。**
成员的机器上没有 `msyt` 这个包，`python -m msyt agent …` 只会报 `No module named msyt`。
所以「命令」必须变成**下载物**：网站实时生成启动包（网址动态注入、包里不带密码），
成员解压运行，装完依赖只问账号密码即可开跑。
