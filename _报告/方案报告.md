## 0. 结论摘要

**先看这六条，其余章节是展开。**

| # | 结论 | 依据 |
|---|---|---|
| 1 | **能做，而且完全不需要登录。** 列表页、详情页、楼层正文三层，访客态（`discuz_uid=0`）全部 200 可取。 | 证据 1/2/6/7 |
| 2 | **所谓"登录问题"是误判。** 真正需要登录的只有"我要发帖"（我们不做）。而让人以为"要登录"的，是正文由 `ajax_getpost.php` 异步注入、首屏 HTML 里 `#postmsg_<pid>` 是**空容器**，页面还挂着 `<noscript>` 提示"您需要启用 JavaScript 才能查看帖子内容"。 | 证据 2 |
| 3 | **token 有时效（< 30 秒）。** token **不**绑定会话、**不**绑定 Cookie、可重复使用，但**取到后必须立即用**。解法就一句：取 token 与用 token 放进同一个请求序列，中间不做任何等待。 | 证据 3 |
| 4 | **⚠️ 最危险的坑：`tid` 不参与校验，token 才是内容钥匙。** 用 A 帖的 token 配 B 帖的 tid（甚至不存在的 tid），返回的仍是 **A 帖的正文**，且 `code=1` **不报错**。串帖会静默发生、直接污染分析结论。**必须用详情页的楼层 pid 集合做一致性校验**。 | §3.5 |
| 5 | **cacx 可参考，但不能直接套用。** `Fetcher`/`html_to_text`/`decode_response` 等基建可直接抄；**通用采集器（`rules.py` 规则推断）在这站必然失败**，因为它从 HTML 找正文，而正文根本不在 HTML 里。必须另写站点专用采集器。 | §2 |
| 6 | **本项目应做成独立包，但设计对齐 cacx 协议**，保留将来合并回 cacx 的可能。规模上：全量 ≈ 500 页列表（5 万条级）+ 按需详情页。 | §5、§6 |

**建议的下一步**（按优先级）：

1. 先跑 `_tools/probe_evidence.py` 复核本报告结论（约 2 分钟，零依赖）；
2. 按 §5.4 的"两阶段采集"落地：先扫完 500 页列表拿全量元数据（500 个请求，约 12 分钟），
   用这份元数据确定分析口径（时间窗、是否只要有回复的帖、要不要图片附件）；
3. 再按需补详情页正文 —— 这是唯一的大头请求量，务必等口径定了再放；
4. **写正文抓取时第一件事就是实现 pid 一致性校验**（§3.5），否则串帖无从察觉。

### 1.2 页面架构：三层数据，三个不同入口

```
① 列表页  forum.php?mod=forumdisplay&fid=1176
   └─ 服务端渲染的 <table>，每行一个 <tbody id="normalthread_{tid}">
      含：标题 / 类别 / 受理状态 / 主办部门 / 留言箱 / 楼主 / 发帖时间
          / 回复数 / 浏览数 / 最后回复时间 / 最后回复方 / 有无图片
   ⇒ 绝大多数分析字段在「这里」就能拿全，不必进详情页

② 详情页  forum.php?mod=viewthread&tid={tid}
   ⇒ 服务端渲染的壳：标题、楼主信息、受理流程时间线、附件图片
      但正文位置是空的：<span id="postmsg_{pid}"></span>

③ 楼层正文  ajax_getpost.php?token={token}&tid={tid}&src=pc
   ⇒ 真正的帖子正文与各部门回复，按 pid 分条返回 JSON
```

第 ③ 层的存在是站方（`tyxg` 插件）刻意设计的：把正文从服务端渲染里摘出去走 AJAX，
降低被纯 HTTP 抓取直接拿走的概率。这是"看起来抓不到正文"的根因。

### 1.3 关键实现细节（踩过的坑，务必照抄）

| 细节 | 说明 |
|---|---|
| **正文入口** | `GET https://bbs.cnnb.com.cn/ajax_getpost.php?token=..&tid=..&src=pc`，返回 `{"code":1,"data":{"{pid}":"<html>"}}`；`code=0` 时 `msg` 为"数据不存在，请刷新整个页面重试。" |
| **token 从哪来** | 详情页 HTML 内联 JS：`jQuery.ajax({url:'ajax_getpost.php',data:{token:'<32位hex>',tid:'…',src:'pc'},…})`。正则取 `token:'([0-9a-f]{16,})'` |
| **token 是内容的唯一钥匙** | **`tid` 参数不参与内容选择**。实测：用 A 帖的 token 请求 B 帖、甚至请求一个不存在的 `tid=9999999`，返回的都是 **A 帖的楼层**，且 `code=1` 不报错。详见 §3.5 |
| **token 时效** | **< 30 秒**（实测 0 秒可用、30 秒失效） |
| **token 不绑定什么** | 不绑定会话、不绑定 Cookie（清空 Cookie 仍可用）、可重复使用（同一 token 连用 4 次均成功） |
| **图片附件真实地址** | 在 `zoomfile=` 属性上，**不是** `src=`。`src` 是懒加载占位图 `static/image/common/none.gif` |
| **详情页标题** | `<span id="thread_subject">` 或 `<h1 class="ts">`；另有 `<meta name="description">` 含正文摘要，可作交叉校验 |
| **受理流程** | 详情页内联 `<ul><li><strong>&nbsp;已发帖</strong><p>2026-10-19<i>09:42:03</i></p>…`，5 个节点：已发帖 → 已分类 → 已受理 → 预回复 → 已回复 |
| **手机版** | `&mobile=2` 参数可拿到更小的详情页（21 KB vs 123 KB），同样走 `ajax_getpost.php`；**但字段更少**，建议仍用 PC 版 |
| **归档页是死路** | `/archiver/?tid-{tid}.html` 返回 200、35 KB，看着像有戏，实为**空壳**：无 `postmessage`、无 `t_f`、无 `postmsg`、无任何 >20 字的容器。**不要在这上面浪费时间**（证据 4） |

### 1.4 目录与筛选维度（分析用）

站点自带一套结构化标签，采集时应全部带下来，它们是舆情分析的主坐标轴。
**这些轴彼此不互斥** —— 一条留言同时落在好几条轴上。

**轴一：帖子类别**（7 类）：投诉、建议、咨询、追问、求助、点赞、其他

**轴二：受理状态**（3 类）：已受理、已回复、未受理

**轴三：主办部门**（站点自称"107 家部门与企事业单位在线"）：列表页实际解析出 **109 个 `typeid` 映射**，
按站方 5 个 tab 分成 **4 个真实分组**（tab1 是全集，不算分组）：

| 分组（tab） | 成员数 | 举例 |
|---|---|---|
| 职能部门和群团组织（tab2） | 64 | 市公安局 495、市住建局 511、市人社局 508、市交通运输局 499 |
| 区（县、市）及开发园区（tab3） | 14 | 海曙区 736、江北区 727、鄞州区 737、北仑区 728、奉化区 731、镇海区 734、宁海县 732、象山县 730、余姚市 733、慈溪市 735 + 开发区管委会 |
| 民生企事业单位（tab4） | 25 | 宁波银行、市轨道交通集团、市综合枢纽建设中心、宁波公交集团 1117 |
| 其他（tab5） | 10 | 含「综合」512 |
| ~~107 家部门与企事业单位在线（tab1）~~ | 109 | **全集**，不是分组 |

一个部门可同时属于多个分组（「综合」512 四个分组都有），所以分组是**集合**不是单值。

#### 目录完整性核查：这 5 个 tab 到底有没有漏？（专门复核）

"站方自称 107 家、我们解析出 109 个"——**差的 2 个到底在哪**，是本项目一个必须交代清楚的问题。
为此做了四项独立核查（证据 10）：

| 核查项 | 方法 | 结果 |
|---|---|---|
| ① 5 个 tab 的成员集合 | 逐个 pane 抽 `a[href*=typeid=]` | tab1 **109** / tab2 64 / tab3 14 / tab4 25 / tab5 10 |
| ② tab1 与 tab2..5 的并集是否相等 | 集合求交/求差 | **完全相等**：交集 109，只在任一方的 **0 个** |
| ③ 有没有"渲染了但隐藏"的条目 | 查 `display:none` / 隐藏 class | tab2–5 整体是 `display:none`（前端切页），**每个 pane 内隐藏条目 = 0** |
| ④ 整页还有没有第 3 份名单 | 全页 `typeid=` 去重 | 整页 446 处引用、去重 **109** 个；`#rankingwz` 内 222 处、去重也是 **109** |

另外查了**页面上存在的第二份部门目录** `ul#thread_types`（Discuz 经典"按部门筛选"列表，
带留言数、默认 `display:none`）：**也是 109 个，与 5 个 tab 的集合完全相同**。
还查了右上角的部门搜索框 —— 它是**纯前端**过滤
（`jQuery("#listranking1 a")` 逐条 `matchPinyin`），**数据源就是那 109 个链接本身**，
不存在第三份更大的名单。

> **结论：程序一个部门都没漏。109 是站方目录的真实规模。**
> "107" 只是 tab1 标题里的一句**写死的文字**——全页搜索 "107" 只在标题处出现，
> 另外两处 107 是帖子里的无关数字。

**那多出来的 2 个是谁？**（高置信推断，非站方公开说明）

先验了一条假设并**把它否掉**：标题写的是"**在线**"，若"在线 = 当前有留言"，
那 109 家里应有 2 家没有留言。于是对全部 109 个部门**逐个取一次筛选列表页**核查
（109/109 HTTP 200，0 失败）：

- **108 家**首屏确有帖子；**仅 1 家**完全没有留言：**typeid=1140「宁波老年大学」**
- 站方目录给每个部门带一个留言数（`span.xg1.num`），108 家有、1140 连计数都没渲染
- 另一个留言最少的：**typeid=1142「市委社会工作部」，仅 2 条**

→ 所以"有留言的部门数"是 **108，不是 107**，**这条假设不成立**。

真正对得上的是另一条线：

- 这两个恰好是**全部 typeid 里最大的两个**（1140、1142），其余部门 typeid 最大只到 1119
- 109 − 2 = **107**，与标题数字严丝合缝
- 反向验证：**typeid ≤ 1119 的恰好 107 家，且这 107 家全部有留言**
  （最少的平安银行宁波分行也有 44 条）
- 而被排除的两家，一个 **0 条**、一个 **2 条** —— 正是"刚上线、还没什么留言"的特征

→ **推断：站方在写下"107家"这个标题之后，又新增了「市委社会工作部」和「宁波老年大学」两个单位，
但没有回改标题。**

> ⚠ 这是**基于证据的推断**，不是站方声明。站方并未在任何地方解释这个 107 的口径。
> 本节已把**被否掉的假设**（"在线 = 有留言"）一并记下，因为两者都指向 107，
> 单看数字分不出是哪种 —— 必须靠"逐个部门核查"才能定案。
> 对本项目的影响：**分析时以 109 为准**（它是目录的真实规模，也是程序的解析结果）；
> 引用站方"107家"这句话时必须注明"站方自称"，不能当成实测值。

复核件：
- `复核\部门目录_5个tab_成员清单.csv`（222 行，tab / 分组 / typeid / 部门名 / 站方留言数 / link class / url）
- `复核\部门在线核查_109家.csv`（109 行，逐部门的 HTTP / 首屏帖子行数 / 站方总页数 / 判为）

脚本 `_tools\probe_tabs.py` ~ `probe_tabs4.py` 可全部复算。

**轴四：区县市**（10 个）：页面另给出 10 个区（县、市）的"上月留言总量 / 上月受理总量"统计。

**轴五：留言箱**（`sortid`）：市委书记留言箱 23、市长留言箱 24

**轴六：时效灯**（4 档）：`green`（3 个工作日内回复）、`yellow`（5 个工作日内回复）、
`grey`（5 个工作日外回复）、`warn`（24 小时未受理）。
⚠ **只对已回复的帖存在** —— 已受理 / 未受理的帖在列表页 `th` 里根本没有图标（只有两个空 `span`）。
所以"没有灯"是**正常的未点亮状态**，采集时要显式记成"未点亮"，不能留空，
否则分不清"还没点亮"和"解析失败"。

**轴七：多标签部门**（`span.typewrapmulti`）：一帖可同时挂多个部门，例：`[综合] [市公安局] [市公交集团]`。

> ⚠ 列表行 `th` 里的方括号标签**混着"帖子类别"和"部门名"两类**。
> 做分布统计时**必须先摘掉 `span.typewrap` / `typewrapmulti` / `sortwrap`**，
> 否则 `[海曙区]` 之类部门名会被当成帖子类别混进类别维度。

#### 区县市的统计数字要单独取一个脚本

页面 HTML 里区县市的数字是 `document.write(ms_hs);` **占位**，

## 2. cacx 可参考使用的方案

### 2.1 cacx 的采集器架构（读源码得出）

```
cacx/collector/
├── base.py      SiteCollector 抽象基类  ← 协议在这
│                Fetcher（Session + 重试 + 限速）/ html_to_text / decode_response
│                / clean_title / absolutize / charset_note
├── cac.py       中国网信办采集器（专用类）
├── zjwx.py      浙江网信网采集器（专用类）
├── generic.py   通用采集器（配置驱动，读 rules.py 里的选择器规则）
├── rules.py     规则推断：从 HTML 反推 item/title/link/date/content 选择器
├── classify.py  条目分类（article / external / wechat / index_page / dirty）
└── runner.py    编排：sync（列表→时间窗→正文→写库）/ doctor（接口自检）
```

`SiteCollector` 协议只有四个方法，子类实现即可挂进 `runner`：

```python
class SiteCollector(ABC):
    code, name, base_url
    def columns(self)        -> List[Dict]      # 栏目定义
    def list_articles(self, column_code) -> List[Dict]   # 列表 → [{url,title,date,...}]
    def fetch_article(self, url, fallback) -> Optional[Dict]  # 详情 → {title,pub_date,content_html,...}
    def health_check(self)   -> Dict             # doctor 自检
```

`runner.sync()` 已经实现：`mode=incremental / full / list-only`、时间窗过滤、跨站去重、
空正文显式标记（`content_empty`）、FTS 重建、进度回调。

### 2.2 逐项对照：能抄什么、要改什么、不能用什么

| cacx 构件 | 判定 | 说明 |
|---|---|---|
| `Fetcher`（Session/重试/限速） | ✅ **直接抄** | 语义完全匹配：Session 复用、指数退避、请求间隔。本站限速要求比 cacx 默认的 0.35s 更保守，见 §5.4 |
| `html_to_text` / `TextCollector` | ✅ **直接抄** | 纯 HTML→文本，与来源无关 |
| `decode_response` / `charset_note` | ✅ **直接抄** | 本站响应头带 `charset=utf-8`，但该函数的自适应逻辑更稳 |
| `clean_title` / `absolutize` | ✅ **直接抄** | 通用工具 |
| `SiteCollector` 协议 | ✅ **直接抄（作为设计蓝图）** | 四个方法正好映射本项目 |
| `runner.sync()` 的编排骨架 | ✅ **抄结构，改判定** | "存在性只读判断 → 再抓正文 → 写库"的顺序必须保留；但增量判据要换成 tid + 回复签名（§5.3） |
| `classify.py` 条目分流 | ⚠️ **部分可用** | 本站条目类型单一（都是帖文），`external/wechat/dirty` 分支基本用不上；但"脏数据也要留痕"的原则要保留 |
| `db.py` / `web/app.py` / `mcp_server.py` | ⚠️ **按需** | 本项目若要出检索界面可直接复用；但 cacx 的 schema 是"政务发文"模型（栏目/来源/摘要），**留言板模型不同**，需另设表（§4.4） |
| `zjwx.py` / `cac.py` | ❌ **不可用** | 那是 jpaas 建站平台的 JSON 接口站点，与 Discuz 论坛架构无关 |
| **`generic.py` + `rules.py`（通用采集器）** | ❌ **必然失败** | 见 §2.3 |
| `probe.py` / `diagnose.py` | ⚠️ **思路可借** | "先探后采、给出 issues 列表"的交互值得抄；具体探测逻辑要重写 |

### 2.3 为什么通用采集器（`rules.py`）在这站一定会失败

`rules.py` 的 `infer_article_rule()` 最后一步是：

```python
body = guess_content(soup)          # 找"文字最多、链接最少"的块
if not body:
    out["issues"].append("定位不到正文块，必须手工指定 article.content 选择器")
```

而本帖正文**不在详情页 HTML 里**（在 `ajax_getpost.php` 的 JSON 里）。
`guess_content` 在详情页上永远找不到有实质文字的块 → 必然报"定位不到正文块"。

即便手工补上 `article.content` 选择器，也只会选中**空容器**
（`<span id="postmsg_113574465"></span>`），抓到 0 字正文。

**结论：通用采集器的"配置驱动 + 选择器推断"范式，在这条链路上不成立。**
必须写站点专用采集器，像 `zjwx.py` 那样直接调 JSON 端点 —— 只是这里的"JSON 端点"
需要先从详情页 HTML 里取 token。

### 2.4 结论

**cacx 提供的价值是"架构与基建"，不是"开箱即用的规则"。**

- 值得抄：HTTP 层、正文清洗、编码判定、采集器协议、sync 编排的分层纪律
- 必须自己写：`list_articles`（Discuz 表格解析）、`fetch_article`（token + AJAX 取正文）、
  `health_check`（探测 token 链路是否还通）
- 明确不行：通用采集器 / 规则推断

## 3. 登录问题：定性、证据与解法

这是本报告最需要说清的一节。**先给结论，再给证据。**

### 3.1 结论

> **采集这个论坛不需要登录。**
> 全程访客态（`discuz_uid = 0`）即可取到：列表页 → 详情页 → 楼层正文 → 受理流程 → 附件图片。
> 唯一需要"额外动作"的是**取 token 并立即使用**，这不是登录，是"一次性票据有时效"。

### 3.2 四个"看起来像登录"的现象，逐个定性

| # | 现象 | 真实定性 | 证据 |
|---|---|---|---|
| ① | 页面上有登录框、"请登录后使用快捷导航" | **正常**。Discuz 所有页面都有登录框，访客态也一样显示。它不影响任何读操作。 | 证据 1/2：`discuz_uid = 0` 但三层数据全 200 |
| ② | 详情页 `#postmsg_<pid>` 是空的，页面提示"您需要启用 JavaScript 才能查看帖子内容" | **误判源**。这不是登录墙，是站方把正文挪到 AJAX 加载。**换成 requests 拿 HTML 必然是空的**，但正文确实公开可取。 | 证据 2 |
| ③ | 首次拿到的 token 调 `ajax_getpost.php` 返回"数据不存在，请刷新整个页面重试" | **token 过期**，不是权限不足。 | 证据 3：0 秒可用、30 秒失效 |
| ④ | 列表页顶部有"我要发帖（需要登录账号）/ 我要留言（需要短信认证）" | **与采集无关**。发帖是写操作，采集是读操作。**我们不做任何写操作，也不需要账号或短信。** | §3.5 |

### 3.3 唯一真障碍：token 的时效约束

**实测矩阵**（完整脚本见 `_tools/probe_evidence.py` 证据 3）：

| 场景 | 结果 |
|---|---|
| 取 token → 立即使用 | ✅ `code=1`，正文正常返回 |
| 取 token → 等待 30 秒 → 使用 | ❌ `code=0`，"数据不存在，请刷新整个页面重试。" |
| 等待 60 秒 / 120 秒 / 300 秒 | ❌ 三档全部 `code=0`，与 30 秒一致 |
| 同一 token 连续使用 4 次 | ✅ 4 次全部 `code=1`（**不是单次票据**） |
| 会话 A 取 token → 会话 B 使用 | ✅ `code=1`（**不绑定会话**） |
| 清空 Cookie 后使用 | ✅ `code=1`（**不绑定 Cookie**） |
| **A 帖的 token + B 帖的 tid** | ⚠️ `code=1`，**返回 A 帖的正文**（`tid` 不参与选择，见 §3.5） |
| **A 帖的 token + 不存在的 tid=9999999** | ⚠️ `code=1`，**仍返回 A 帖的正文** |

**推论：**

- token 是**短时效的一次性通行参数**，与服务端状态无关；
- 因此**不需要维持登录态、不需要保存 Cookie、不需要账号**；
- 唯一的硬规则是：**取 token 与用 token 必须紧挨着，中间不能有任何等待**；
- 另有一条更隐蔽的规则：**token 才是内容的唯一钥匙，`tid` 不参与校验**（见 §3.5）。

### 3.4 解法（代码级）

```python
# 错：先批量拿 token 存起来，稍后再用 —— 30 秒后全废
tokens = [fetch_token(tid) for tid in tids]   # ❌ 必然大面积 code=0

# 错：把 A 帖的 token 配 B 帖的 tid —— 不报错，静默串帖（见 §3.5）
ajax(token=tokens[i], tid=tids[i + 1])        # ❌ 拿到的是 tokens[i] 对应那帖的正文

# 对：取 token 与用 token 在同一个请求序列里，中间不 sleep
def fetch_body(session, tid):
    page = session.get(f"{BASE}/forum.php?mod=viewthread&tid={tid}", timeout=25)
    page.encoding = "utf-8"
    m = re.search(r"token:'([0-9a-f]{16,})'", page.text)
    if not m:
        return None, "no_token"
    # ↑ 拿到 token 后立即发下一个请求，中间不得插入任何 sleep / 重试
    resp = session.get(
        f"{BASE}/ajax_getpost.php",
        params={"token": m.group(1), "tid": tid, "src": "pc"},
        headers={"Referer": f"{BASE}/forum.php?mod=viewthread&tid={tid}"},
        timeout=25)
    data = (resp.json() or {}).get("data") or {}
    if not data:
        return None, "token_expired"        # ← 唯一需要重试的原因
    return data, None                      # ⚠️ 完整版还要做 pid 校验，见 §3.5
```

配套纪律：

1. **限速只加在"帖与帖之间"，不加在"取 token 与用 token 之间"。** 错的做法是每个请求前统一 sleep，
   那会把 token 拖过 30 秒有效期。
2. **`code=0` 时重取整个详情页**（token + 页面一起刷新），不要复用旧 token 重试。
3. **Session 仍然建议全程复用**（不是为了 token 绑定，而是为了减少握手、保持 UA/Referer 一致），
   但要清楚：**Session 复用是"推荐"不是"必需"**。
4. 首次跑若出现大面积 `code=0`，先怀疑两件事：**token 用晚了**、**详情页结构变了（插件升级导致 token 字段改名）**。
5. **必须加 pid 一致性校验**（见 §3.5）——这是唯一能挡住"静默串帖"的手段。

### 3.5 最容易被忽略的坑：`tid` 不参与校验，token 才是内容钥匙

这是本轮实测里**最反直觉、也最危险**的一条。它不会报错，只会静默串帖。

**实测矩阵**（A = tid 8343156「世纪大道高架规划毗邻居民咨询」，2 层；
C = tid 8343903「违停」，1 层）：

| 请求 | `code` | 返回的楼层 pid | 实际拿到的内容 |
|---|---|---|---|
| token(A) + `tid=A` | 1 | `113571947, 113574467` | ✅ A 的正文 |
| token(A) + `tid=C` | 1 | `113571947, 113574467` | ⚠️ **还是 A 的正文** |
| token(A) + `tid=9999999`（不存在） | 1 | `113571947, 113574467` | ⚠️ **还是 A 的正文** |
| token(C) + `tid=A` | 1 | `113574465` | ⚠️ **还是 C 的正文** |
| token(C) + `tid=9999999` | 1 | `113574465` | ⚠️ **还是 C 的正文** |

**结论：服务端以 token 为唯一钥匙去取正文，`tid` 参数完全不参与内容选择。**
也就是说，`tid` 传错、传不存在、甚至漏传，返回的都是**那个 token 对应的那一帖**。

**为什么这是危险的事**：因为它**不报错**。`code=1`、楼层数正常、正文长度正常。
如果采集器出现"token 队列错位""复用了上一个帖的 token""并发时把 token 配错了 tid"
这类 bug，**库里会多出一批张冠李戴的正文，而且没有任何告警**。
在舆情分析里，串帖意味着"某个部门的回复被算到了另一个部门头上"——结论直接失真。

**防御措施（必须实现，成本极低）**：详情页 HTML 里本来就有全部楼层锚点
`<div id="postmsg_{pid}">`（站方 JS 的替换目标就是它：
`jQuery('#postmsg_'+pid).replaceWith(html)`），而 AJAX 返回的 `data` 的 key 正是这些 pid。
两边来自**同一次页面抓取**，所以比对 pid 集合是完整且自洽的校验：

```python
def fetch_body(session, tid):
    page = session.get(f"{BASE}/forum.php?mod=viewthread&tid={tid}", timeout=25)
    page.encoding = "utf-8"

    expect = set(re.findall(r'id="postmsg_(\d+)"', page.text))   # 该页的楼层锚点
    m = re.search(r"token:'([0-9a-f]{16,})'", page.text)
    if not m:
        return None, "no_token"

    resp = session.get(f"{BASE}/ajax_getpost.php",
                       params={"token": m.group(1), "tid": tid, "src": "pc"},
                       headers={"Referer": f"{BASE}/forum.php?mod=viewthread&tid={tid}"},
                       timeout=25)
    data = (resp.json() or {}).get("data") or {}
    if not data:
        return None, "token_expired"

    got = set(data.keys())
    if got != expect:                 # ★ 精确相等（不是子集）
        return None, f"pid_mismatch(got={sorted(got)}, expect={sorted(expect)})"
    return data, None
```

> **本轮复测把判据从"子集"收紧到"精确相等"**（证据 9）。
> 初稿用 `got <= expect`（子集），理由是"部分楼层可能不返回"。
> 但在 3 页帖 tid=8339985 上逐页实测，**每页的 AJAX `data` 键集合与该页锚点集合精确相等**
> （第 1 页 16/16、第 2 页 15/15、第 3 页 3/3），不存在"部分楼层不返回"的情况。
>
> 收紧的理由：子集判据**只能挡串帖，挡不住少收** ——
> 若某页只返回了部分楼层，子集判定会安静地放行，帖子却是不完整的，
> 而库里的正文长度看起来一切正常。既然"精确相等"恒成立，没有理由不用更严的判据。

### 3.6 我们明确**不做**的事

| 不做 | 原因 |
|---|---|
| 注册账号 / 登录 | 无必要。读操作全公开。 |
| 短信认证 | 那是"我要留言"的投稿通道，与采集无关。 |
| 发帖 / 回复 / 点赞 / 收藏 | 写操作。作业只需读取与分析。**不做任何写操作，也不模拟任何写操作。** |
| 绕过任何访问控制 | 本报告未发现任何访问控制被绕过 —— 因为不存在需要绕过的访问控制。 |

### 3.7 详情页的分页机制：一帖 N 页，每页各有一个 token

**这是写程序阶段才发现的，直接改变请求量模型与完整性判据。**（证据 9）

- 一帖的楼层会**分页**（每页 16 楼）。3 页帖 tid=8339985 的锚点分布是
  第 1 页 16 个、第 2 页 15 个、第 3 页 3 个，其中 1 个 pid 在第 1 页与第 3 页**各出现一次**，
  去重后 **33 楼**。
- **成因是「置顶回复」**：Discuz 把置顶楼在第 1 页顶部**额外渲染一次**，
  该次渲染的楼层标签是「顶 来自 #」（**无号**），真楼层号出现在它自己的页上。
  实测 pid=113574604：页 1 序 2 标签「顶 来自 #」（floor 解析为 0），
  页 3 序 3 标签「33 #」（floor=33）；两处 ajax 取回的正文**完全一致**（均为 138 字）。
  → **推论一：锚点出现次数 ≠ 楼层数**，数楼层必须按 pid 去重。
  → **推论二：楼层号必须取「有数字的那次」**，否则置顶楼会被记成 floor=0；
  入库时用 `CASE WHEN excluded.floor>0 THEN excluded.floor ELSE posts.floor END` 兜住。
- **每页有各自的 token**，且 AJAX 只返回**当页**的楼层。
  所以一帖 N 页要 **N×2 次请求**（N 次取页 + N 次 ajax），不是 2 次。
- 因此"头/尾完整"的判据必须**跨页**定义：
  **头 = 第 1 页的楼主楼；尾 = 末页的最后一楼。**
- **单页帖根本没有分页块**（`<div class="pg">` 不存在），
  此时请求 `page=2` 会**回绕返回第 1 页**（pid 集合完全相同、顺序略有差异）。
  所以绝不能盲目往下翻 —— 必须读出站方的分页块来封顶。
- 楼层号标签是 `N#` 形态（`<em>5</em><sup>#</sup>`），不是「N楼」；
  被顶替或置顶的楼层显示为「来自 2#」「顶来自 2#」。
- **站方自己的回复计数可能不自洽**：实测 tid=8332684 列表页写「回复 5」，
  而该帖楼层标签最大是 `5#`（即共 5 楼），差 1。
  差 1 的成因（站方删楼未减计数 / 置顶回复被重复计数）未查明，
  但结论明确：**列表页的回复数只能当旁证，不能当硬判据** ——
  否则会把站方的计数问题误判成我们的漏采（初稿的完整性判据就栽在这里）。

### 4.3 受理流程时间线：白送的舆情分析指标

站方把"发帖→分类→受理→预回复→回复"五个节点的**秒级时间戳**直接渲染在详情页里。
这意味着以下指标**不需要任何人工标注**：

| 指标 | 算法 | 作业价值 |
|---|---|---|
| 分类时长 | `已分类 − 已发帖` | 平台分拨效率 |
| 受理时长 | `已受理 − 已发帖` | 响应速度（核心） |
| 回复时长 | `已回复 − 已发帖` | 闭环效率（核心） |
| 未回复积压 | `now − 已发帖`，且 `已回复` 为空 | 高压线舆情预警 |
| 部门响应排名 | 按 `已受理 − 已发帖` 分组聚合 | 横向对比 109 个部门 |

**这是本站在"舆情分析"上最有价值的一块，务必优先取。** 它比正文本身更适合做量化分析。

### 4.4 建议表结构（SQLite）

```sql

CREATE TABLE threads (
  tid            TEXT PRIMARY KEY,
  title          TEXT, url TEXT,
  category       TEXT, state TEXT,
  dept_typeid    TEXT, dept_name TEXT, dept_extra TEXT,

  reply_count    INTEGER, view_count INTEGER,

  first_seen_at  TEXT, last_seen_at TEXT, last_fetched_at TEXT
);
CREATE INDEX idx_threads_created ON threads(created_at);
CREATE INDEX idx_threads_state   ON threads(state);
CREATE INDEX idx_threads_dept    ON threads(dept_typeid);

-- 楼层（正文）
CREATE TABLE posts (
  pid TEXT PRIMARY KEY, tid TEXT, floor_index INTEGER,
  author_name TEXT, posted_at TEXT, is_author INTEGER,
  content_html TEXT, content_text TEXT, chars INTEGER
);
CREATE INDEX idx_posts_tid ON posts(tid);

-- 受理流程节点
CREATE TABLE flows (
  tid TEXT, seq INTEGER, stage TEXT, happened_at TEXT,
  PRIMARY KEY (tid, seq)
);

-- 部门字典（109 条，随站点更新可刷新）
CREATE TABLE depts (
  typeid TEXT PRIMARY KEY, name TEXT, level TEXT, parent TEXT
);

-- 采集留痕

  run_id TEXT, tid TEXT, ok INTEGER, fail_kind TEXT,

);
```

> `reply_sig` 是增量采集的关键，见 §5.3。
> `fetch_log` 用于"哪些帖抓失败了、为什么"，可查而非静默丢弃 —— 与 cacx 的

### 5.2 抓取链路

```
list_articles()                      fetch_article()
  GET 列表页 ?page=N                   GET 详情页 ?tid=T   ──► 取 token
  解析 <tbody id=normalthread_*>        同时记下页面上的楼层锚点 post_{pid}
  → 帖元数据 (§4.1)                     GET ajax_getpost.php?token=..&tid=T  ← 间隔 0 s
                                         → 楼层正文 (§4.2)
  500 页 ≈ 5 万条元数据                  → 受理流程 (§4.3)
                                         → pid 集合校验 (§3.5) ← 挡住静默串帖
```
> 抓取链路上唯一"额外"的动作，是最后那一步 pid 校验。它来自**同一次详情页抓取**，
> 成本为零，却能把"串帖"这种无声的数据污染变成一条明确的失败记录。

### 5.3 增量策略：**两级增量**，别混为一谈

这是本作业（"增量采集与全量数据"）的实质内容。

#### ① 帖级增量（新帖）

新帖会把旧帖**往下推**，所以**页码会漂移，不能用"上次到第 N 页"当增量水位**。正确做法：

1. 从 `page=1` 顺序往后拉；
2. 每页的 tid 与库内集合求差；
3. **早停判据**：某页内**全部**条目的 `created_at` 都早于「上次采集时点」→ 后面只会更旧，停；
4. 新帖入库，已存在的帖只更新 `last_seen_at`（不重复抓正文）。

> 代价：每轮增量至少要翻几页列表。实测每页约 285 KB，5 页约 1.4 MB、约 5 秒 —— 很便宜。

#### ② 回复级增量（老帖的新回复）

**这是最容易漏、也最容易出成果的一层。** 老帖不新发，但部门追加了回复，列表页的
`reply_count` 与 `last_reply_at` 就会变。于是：

```python
sig_new = f"{reply_count}|{last_reply_at}"
if sig_new != row["reply_sig"]:      # 变了 → 只重抓这一条的详情页
    fetch_detail(tid)                 # 增量楼层（按 pid 去重，只插新的）
```

按此策略，一轮增量通常只需抓**数十到数百条**详情页，而不是全量重抓。

> ⚠️ 这条也解释了为什么 `posts` 表要用 `pid` 做主键：楼层是**追加**的，不是替换的。

#### ③ 全量

`--mode full`：500 页列表 + 全部详情页。这是最大的一笔请求量（见 §5.4），务必留到最后、且在口径确定后再跑。

### 5.4 请求量与限速

| 阶段 | 请求数 | 原始耗时（不限速） | 限速后（贴文间 1.0 s） |
|---|---|---|---|
| 列表 500 页 | 500 | ~3.5 分钟 | ~12 分钟 |
| 详情（1 个详情页 + 1 个 ajax） | 2 × N | N=5 万 → ~11 小时 | N=5 万 → **~25 小时** |
| 增量（一轮） | 列表 5 页 + 数十~数百条详情 | — | 数分钟 |

> 限速口径说明：**限速加在「帖与帖之间」（每条帖结束到下一条帖开始之间 1.0 s）**，
> 不加在「详情页 → ajax」之间（那 0 s 是 token 时效的硬约束，见 §3.4）。
> 单条帖的耗时 ≈ 0.4 s（详情页）+ 0.4 s（ajax）+ 1.0 s（贴文间隔）≈ 1.8 s。
> 全量 5 万条 × 1.8 s ≈ 25 小时 —— **这就是为什么必须先跑列表、定好口径，再按需补详情**。
> 若只做「近 3 个月」或「只取有回复的帖」，请求量会降到 1/5 以下。

**限速建议（保守）**：

| 项 | 取值 | 理由 |
|---|---|---|
| 帖与帖之间 | **1.0 ~ 1.5 s** | 站点 `attackevasive=0`、实测 12 次连续 0.25s 间隔全 200，但作业场景无需冒险 |
| 详情页 → ajax | **0 s（不等待）** | token < 30 秒有效，此处等待是最容易犯的错 |
| 并发 | **1（串行）** | 论坛类站点不建议并发 |
| 重试 | 3 次，指数退避 | 仅对 `code=0`（token 失效）重取详情页 |

> 依据用户既有纪律：**复核/探测动作本身要按最贵操作计价**。这里是读操作，风险低，但站点是
> 地方媒体论坛，频繁抓取可能触发限流，故取保守值。实测 0.25s 间隔 12 次全 200，
> 说明 1.0s 是安全余量很大的取值。

## 9. 采集程序（`msyt`）已实现

程序位置：`2-作业/02 民生e网通/程序/`，包名 `msyt`，独立项目，不依赖 cacx 运行。

### 9.1 两条独立链路

| | 链路 | 命令 | 每帖代价 | 产出 |
|---|---|---|---|---|
| 一 | **列表采集** | `msyt list` | 1 次请求 | 元数据 + 七轴标签 |
| 二 | **详情页采集** | `msyt detail` | **N×2 次请求**（N=帖页数） | 楼层正文 + 受理流程 |

拆成两条是因为代价差一个量级：列表页元数据已足够做分布统计，
正文留给链路二按需补。

**详情先旧后新**：按发帖时间升序取帖。
不能用"上次到第 N 页"当水位 —— 列表页随新帖插入而漂移，页码当水位必然漏采或重采。

**详情范围限制（水位线）**：用户口径"列表先看 500 页，早于第 500 页最早一贴的不采详情"。
水位线 = 全局视图最后一页最早一贴的发帖时间；早于它的队列项标 `skipped` 并记明原因。
**只有全局视图真的采到最后一页才设水位线** —— 试采 5 页就设会把"目前最早"误当截止线，
恰好把刚采到的数据判死。

### 9.2 分类体系：既当采集源，也当标签

站方七条标签轴（§1.4）被同时用作两件事：

- **采集源**：每个切片是一条独立分页列表，有自己的 `list_watermark` 行，
  所以断点续传是"按源"的（采到第 137 页断了，下次从 138 页接着来）。
  支持 `global` / `dept:<id>` / `group:<组>` / `district:<id>` /
  `category:<c>` / `state:<c>` / `mailbox:<c>` / `dateline:<秒>`。
- **入库标签**：`thread_tags` 逐维打标，检索时任意切片。
  筛选参数**编号与名称都认**（`--category 1` ≡ `--category 投诉`，实测同结果）。

**硬判据**（不过 → 不标 done，帖子留在队列里）

1. 每页 AJAX `data` 键集合 **==** 该页 `postmsg_{pid}` 锚点集合（精确相等，§3.5）
2. **头** = 楼主那一楼（`floor == 1`）在库
3. **尾** = 楼层号最大的那一楼在库（一帖 N 页 → 头在第 1 页、尾在末页，跨页定义）
4. 该帖应有的页全部取到，且无空正文楼层

**软警告**（记录但不否决）：楼层号缺口（站方删楼/置顶）；
列表页回复数与实收楼层不自洽（站方计数问题，§3.7）。

**断点续传**：粒度是"页"，落库是"每页一个事务"。
进程被杀 → 队列那条是 `running` → 下次开机归位为 `pending` → 从 `pages_done+1` 继续。
已落库的楼层是校验过 pid 集合的正确数据，不用重采；
帖子在头/尾齐备前不标 done，所以"半截帖子"永远看得见。

### 9.4 检索层（移植 cacx，语义原样保留）

FTS5 外部内容表 + `trigram` 分词器 + 触发器 + `rebuild`；
**短词（< 3 字）整体退回 LIKE**（trigram 索引里 2 字词查不到任何东西，
也不能"一半走索引一半走扫描"，那会漏结果）；
返回 `{total, items, mode, took_ms, scope}`，`mode` 标明走 `fts` 还是 `like`。

与 cacx 的差别都源于模型差异：cacx 是"一篇文章"一层，
本项目是"帖 → 楼层"两层，故拆成 `threads_fts(title, dept_name)` 与 `posts_fts(content)` 两张表，
检索统一在**帖**这一层收敛（`scope=thread/post/all`），避免一条帖在结果里出现十几次。

### 9.5 本地 Web 前端

除了命令行，程序另有一个**本地网页界面**（`msyt web`，或双击 `启动-web.cmd`），
默认只监听 `127.0.0.1`——这是本地工具，不直接暴露公网。

| 页签 | 内容 | 成员可见 |
|---|---|---|
| 总览 | 帖子/楼层/队列/告警等 8 个指标卡 + 类别·状态·分组·时效灯·区县市分布 + 站方自报统计 + 列表源水位表 | ✅ |
| 检索与浏览 | 关键词 + 七条标签轴筛选 + 排序 + 分页；点任意一行开**详情抽屉**（受理流程时间线、**逐页 pid 集合**、全部楼层正文与图片） | ✅ |
| **采集与协作** | 合并页签，内含三个二级页签：①**采集作业**（分类体系/列表采集/详情采集/导出 CSV + 实时日志 + 随时停止）②**协作采集**（发布协助请求/领活/协作任务/合并记录/成员名单/成员端工具）③**我的账号**（身份·改密码·agent 命令） | ✅ |
| 完整性体检 | 硬问题与软警告分开呈现；**可勾选后「重跑所选」或「清除所选」** | ❌ 管理员专属 |
| 采集日志 | `fetch_log` 原始流水 | ✅ |

三个实现要点：

- **长任务不阻塞 HTTP**。`msyt list --pages 500` 要跑几十分钟，不能在请求线程里同步跑。
  采集动作走 `/api/jobs/*`：接口立刻返回 `job_id`，后台线程执行，前端轮询 `/api/jobs/{id}`。
- **日志靠 `Client.log()` 捕获**，不重定向 stdout（重定向是全局的，多任务会串）。
- **SQLite 多线程**：`DB` 默认 `check_same_thread=True`，所以 webapp 用**线程局部连接**，
  每线程各开一个（WAL 模式下读写可并发）。

> ★ **权限两道都做**：界面层按角色裁掉页签与卡片，接口层一律 `require_admin`。
> 缺一道等于没锁（只藏界面 → 改 URL 就能调；只锁接口 → 界面还误导人）。
> 成员可见 总览 / 检索与浏览 / 采集与协作 / 采集日志；**完整性体检与成员管理是管理员专属**。

**「停止」是优雅的**：`DetailCollector.run()` 与 `ListCollector.collect()` 加了可选的
`should_stop` 回调（默认 `None`，CLI 行为不变）。点停止后，采集器**在下一个页/帖的边界**停下——
当前这一帖会采完整再收尾，进度已落库，下次从断点继续。

技术选型：后端 `fastapi` + `uvicorn`（**本机已装，零新增依赖**），
前端是**原生单页**（`index.html` / `app.js` / `style.css`，无框架、无构建链、无 CDN，离线可跑），
改完刷新即可，也方便直接截图进报告。

**采集范围选择器（全量采集用）**：列表采集要按站方的 109 个部门逐个遍历，
手打 `dept:495,972,...` 不现实，所以网页端给了**分组勾选器**：
按站方 4 个分组展示（64 / 14 / 25 / 10，条目数与站方 tab 完全一致），
提供**全选 / 清空 / 反选**与名称搜索，可另勾「同时采全站视图 global」，
并**实时估算工作量**（N 个部门 × 每源 P 页 → 最坏 N×P 次请求 + 预计小时数，超阈值标红并在启动前弹确认）。
一个部门属多个分组时列表里会出现两行（`512 综合` 属 4 组、`1099 甬城泊车` 属 2 组），
与站方行为一致，按 typeid 去重后仍是 109 个。
每个部门是**一条独立的分页列表**，各有自己的 `list_watermark` 行，断点**按源**续。

> ⚠ 顺带修掉一个真 bug：`expand_sources("dept:495,972")` 原本**只会展开出 495** ——
> 旧实现先按逗号切整串，第二段 `972` 丢了维度归属，被 `dim not in _TEMPLATES` **静默丢弃**，
> 不报错、不采到、也没有任何告警。现改为「先按项归属、再拆码表」：
> `dept:495,972` → 2 个源，`group:func,group:enterprise` → 87 个源（含重叠去重）。

**详情采集与列表走同一个源**：详情采集卡里也有一个同样式的部门选择器
（共用同一份部门字典，选中集合各自独立），目标两种给法可叠加 ——
**直接填 tid**（定点补采），或**按部门选**（该部门下所有还没采详情的帖，先旧后新）；
详情侧有「沿用列表的选择」一键复制列表那边的勾选。
选完部门后界面**实打实统计**待采帖数（实测：3 个部门 → 450 帖；全库 36,487 帖待采）。
部门归属的 `extra_dept_ids` 是逗号串，**不能直接 `LIKE '%512%'`**（会误命中 1512），
故归一成「逗号包起来的串」再用 `instr(','||extra_dept_ids||',', ',512,') > 0` 精确匹配。

> ★ **旧进程降级**：服务端未重启到支持该功能的版本时，前端按版本号探测并**禁用**详情选择器，
> 明确提示「服务端尚未重启」。绝不让新前端对旧后端发一个被 Pydantic **静默忽略**的参数 ——
> 那会变成"看着选了部门、其实没按部门采"，是这类系统里最难发现的错。

**协作 Beta（已部署）**：程序另有一个**协作闭环** —— 管理员发布「协助请求」（选部门 → 自动挑出
还没采详情的帖 → 拆成单帖的活），成员用**本地 agent** 领活、在自己机器上采正文、回传，
管理员的权威库自动合并；**双方看的是同一条实时日志**（带节点徽标与任务编号）。
身份层是**邮箱 + 密码（scrypt）+ JWT**。账号来源是**自助注册 + 管理员审核**：
成员在登录页自行注册 → 状态 `pending`（**注册后立刻登不进去**）→ 管理员在成员名单里点「通过」→
状态 `active` 才可登录。**审核这一步就是管理员的控制点** —— 站点已通过 Cloudflare 隧道暴露到公网，
若注册即用，任何拿到域名的人都能开始打站方，把配额与风控预算烧掉。
管理员可在成员名单里**审核 / 停用 / 改配额 / 重置密码 / 删除**，也可改自己的密码。
**非管理员看不到管理界面**：界面层只保留「协作」一个页签（采集作业、完整性体检、采集日志、
发布协助请求、成员名单全部隐藏），接口层所有管理端点一律 `require_admin`，
即使手动构造请求也只会得到 **403** —— **两道都做，缺一道就等于没锁**。
公网访问经 **Cloudflare 隧道**（`msyt.example.com` → 本地 8765），
并在 Cloudflare Access 上加了**邮箱认证**（实测：公网所有路径未登录一律 302 到 Access 登录页）。

> ★ 成员端的关键实测结论：**站方一个 CORS 头都不给**
> （`Access-Control-Allow-Origin = None`，预检也没有），浏览器普通跨域 fetch 直接
> `Failed to fetch`，`no-cors` 只能拿到 **opaque** 响应读不出内容
> → **浏览器不能直接采站方**。所以正文采集由**成员机器上的 agent** 发请求，
> 站方看到的是**多个分散的普通用户**而不是一台服务器在集中爬；
> 采集全程用**内存 SQLite**，**不写任何磁盘文件**，回传后立即释放
> —— 「传完即删」是物理上没有可删的东西。

### 9.6 列表分页漂移（"错位"）：站方实时更新会怎样

列表页按时间倒序，而站方是**活的** —— 新帖会插到最前面，**被新回复顶起来的老帖也会插到最前面**。
于是分页窗口会整体后移，这叫**页码漂移**。必须说清它到底会造成什么损失。

**先把后果分清（三件事，不是一件事）**：

| 后果 | 是否发生 | 说明 |
|---|---|---|
| ① 重复 | **会**，但无害 | 同一帖在相邻两页各出现一次；入库按 `tid` 幂等，重复即覆盖，不产生脏数据 |
| ② 头部漏 | **会**，可补救 | 漂移期间新出现/新被顶帖的，原本在窗口外 → **回扫前几页**即可捞回 |
| ③ **尾部漏** | **只发生在被 500 页顶截断的源** | 漂移把**最老的一批**挤出窗口 → **回扫救不回来**，只能靠 `filter=dateline` 时间窗再往深里取 |

> ★ **关键澄清**：插到最前面时，各页之间**仍然连续**（不重不漏），
> 只是整个覆盖范围**往更老的方向滑**。所以"漂移导致中间漏掉一段"这个说法**是错的** ——
> 真正会丢的只有**尾部最老的一批**，而且只在触顶的源上。

**实测（109 部门全量采集，真实数据）**：

| 指标 | 数值 | 含义 |
|---|---|---|
| 发现关系数 / 唯一 tid | 254,876 / 254,422 | **重复发现率 0.18%** → 漂移造成的重复极小，幂等去重后无害 |
| 采集源 14 个 | 已采完 **9** 个 | 未触顶的源（`last_page == max_page`）**不漏** |
| 触到 500 页顶 | **2** 个 | `dept:726`（23,000 行，最早 2013-08-01）、`dept:736`（50,000 行，最早 2016-11-22）—— **只有这两个源的尾部有风险** |
| 探到最深 | `dept:558` 最早 **2011-11-06** | 按部门遍历能摸到 2011 年，远深于全站视图的 2025-11-19 |

**程序里的三道防线**：

1. **页边界连续性检测**：每页记下首尾 `tid` 存进 `list_watermark.last_tid`；
   续采时比对"本批首行 tid"与"上批末行 tid"，**接不上**说明中间被删帖或重排 → 记 `drift_hits` 并写日志。
   （注意：正常插入**不会**触发这个检测 —— 它抓的是更罕见的真异常。）
2. **补漏回扫**：每个源采完后**回扫前 2 页**（2 次请求），把漂移期间插到前面的帖捞回来，
   补回条数记进 `list_watermark.rescan_rows`。
3. **幂等入库**：`tid` 是主键，重复只覆盖不脏库 —— 这是前两条能成立的前提。

> ⚠ **剩下的那 2 个触顶源**（`dept:726` / `dept:736`）的尾部最老一批，
> 本程序**采不到**，需要用 `filter=dateline` 时间窗分段再取（§8② 已验证该手段可行）。
> 这是**已知缺口**，不是漏采 bug。

### 9.7 协作 Beta（已部署，可让小组成员真的用起来）

详见《分布式抓取协作方案》。这里只记**已落地并实测**的部分。

#### 9.8.1 闭环

```
管理员                          控制面（管理员机器）                  成员设备
发布协助请求（选部门）  →   assist_tasks + assist_picks
                            任务编号 A1 / A2 …
                            ├─ 成员 agent 领活 → 分到具体 tid（先旧后新）
                            ├─ 成员本地采集（内存 SQLite，不落盘）
                            └─ 回传 → 并入权威库（走同一套完整性判据）
                            实时日志 → 双方同看（带节点徽标 + 任务编号）
```

#### 9.8.2 成员端怎么跑起来（这一条最实际）

成员的机器上**没有** `msyt` 这个包，直接敲 `python -m msyt agent …` 只会报
`No module named msyt`。所以走**下载**这条路：

```
网页（成员已登录）
   │  GET /api/agent/bundle.zip      ← 服务端**实时生成**这个 zip
   │     · --server 用的是**下载者此刻访问的地址**（网址是动态的）
   │     · 包里**没有密码**
   ▼
msyt-成员端启动包.zip
   │  解压 → 双击「启动采集.cmd」
   │     · 自动装依赖（requests、beautifulsoup4）
   │     · 然后**只问邮箱和密码** → 就地开跑
   ▼
本机 agent → 领活 → 采集 → 回传
```

另一种玩法：双击「启动助手.cmd」→ 本机开一个 `127.0.0.1:8766` 的小助手，
之后回到网页点「启动本机 agent」即可（网页把当前 JWT 递给助手，**连密码都不用输**）。

#### 9.8.3 三条关键语义

| 语义 | 规则 | 落在哪 |
|---|---|---|
| **合并** | **不跳过，采取并覆盖**：同 pid 用成员版覆盖本地版；成员多采到的楼层（增量）直接加进来；本地有而成员没采到的**保留**。覆盖与新增都留痕（`assist_conflicts`，界面「合并记录」可查） | `msyt/assist.py: submit()` |
| **增量** | 列表页的「回复数」比上次采集时**变大** → 站方又回复了 → 该帖标 `stale` 并丢回队列重采 | `msyt/db.py: detect_reply_growth()`、`msyt/listpage.py: _upsert_with_growth()` |
| **不一致** | 体检页可勾选后**「重跑所选」**（软失败，数据留着）或**「清除所选」**（硬清空，从零开始） | `msyt/db.py: retry_details() / purge_details()` |

> ★ 「站方称 N+1 楼、本地实收 N 楼」是**站方自己的计数不自洽**（常见，差 1），
> 既不算我们漏采，也**不算增量**。界面把两者分列在不同栏，防止混淆。

#### 9.8.4 失联自动停止

控制面是协作的**唯一出口**（领活要问它、回传要给它）。断了联系还继续采，
采到的东西送不回来 —— 白采，也是白打站方。所以 agent 有后台心跳，
连接连续失败达阈值即判定失联 → 不再领活、正在采的那帖**在下一个页的边界中止**、
不回传半截数据、退出并汇报。

#### 9.8.5 账号与权限

- 自助注册 → `pending`（**注册后立刻登不进去**）→ 管理员审核 → `active`
- 管理员重置密码只是给一个**能登进去的临时口令**；成员登录后**必须能自己改掉**
  （右上角「改密码」是正式表单：强度条 + 显示切换 + 两次一致性校验）
- 协作**不限配额**，在线即可

### 9.9 「进度显示不出来」的完整因果链（2026-10-23 下午）

用户反馈：**「进度显示有些问题，无法确认是否被采集」**。
这句话背后其实压着**六层互相叠加的原因**，其中一层是站方的、其余五层是我们的。
下面按「先定性、再修」的顺序记清楚，因为**每一层单独看都像小毛病，叠起来就完全没法用**。

#### 9.9.1 第一层：站方的可见性策略（**不是 bug，绕不过去**）

站方详情页对**历史帖子**只给一个「提示信息」页，页面里明写：

> **历史帖子仅限作者本人查看**

实测证据（`_tools/probe_visible.py`）：

| 观测 | 结果 |
|---|---|
| 三个不同 tid 的详情页 HTML 长度 | **完全相同（22,705 字节）** —— 同一个模板 |
| 页面里的楼层锚点 `id="post_N"` | **0 个**（正常帖是 1–33 个） |
| `<title>` | `提示信息 - 民生e点通-天一论坛` |
| 可见边界（用**库里真实存在的 tid** 逐个试） | tid **8074362 可见** / tid **8074198 不可见** |
| 边界附近的帖（tid 8.1M–8.34M） | 抽样 30 个，**全部可见** |
| 老帖（tid 6.26M–6.69M） | 抽样 6 个，**全部不可见**（提示页） |

★ **判据里有个坑**：随手编一个 tid 去试会拿到 **404**（帖子不存在），
和「帖子存在但正文不公开」是两回事 —— 必须用**库里真实存在的 tid** 去探，
否则会误以为「站方把老帖删了」。

★ 站方给的**可见边界会随时间往后挪**（它是滚动的时间窗，不是固定规则），
所以**不能把这个 tid 写死在代码里当判据**。正确做法是**运行时识别提示页**。

#### 9.9.2 第二层：口径（用户 2026-10-23 明确拍板）

> 「的确有这种情况，可以标记，放入正文，不过不计入已采详情贴」

落地为一套**独立状态**，不与「采到」「失败」混在一起：

| 落点 | 实现 |
|---|---|
| 帖的状态 | `threads.detail_state = 'restricted'`（新增状态） |
| 写入正文 | `posts` 表插一条**标记行**：`pid = -tid`（负数，绝不与真实楼层撞号）、`floor=0`、`author='站方提示'`、正文写明站方原话 |
| 楼层数 | `posts_n = 0` —— 它**不是一层楼** |
| 「已采详情帖」 | `detail_state='done'` 的计数 → **不含**受限帖 |
| 「楼层总数」 | 只算 `pid > 0` 的真实楼层，标记行单列 |
| 协作回传 | 成员回传为空但带 `restricted` 标记 → 活记 `'restricted'`（**不是** `'failed'`） |
| 界面 | 「站方限制」**独立一栏**（协作任务表 / 在线节点表 / 体检页 / 总览卡片各一栏） |
| 体检页 | 受限帖**单独一栏**，不进硬问题、不进软警告、**不提供勾选重跑**（重跑多少次都是同一个提示页） |

#### 9.9.3 第三层：建池顺序错了（池子里全是采不出东西的帖）

原实现按 `pub_ts ASC`（**先旧后新**）选帖 —— 而老的帖恰恰是**站方不给正文**的那批。
于是成员领到的活全是空回传 → 「完成 0 / 失败 500」→ 界面像坏了。

**改为 `pub_ts DESC`（先新后旧）**，并排除已判受限的帖。
实测：新池 500 帖 → 成员采到 **499 帖真正文**、1 帖失败。

#### 9.9.4 第四层：池子被「领了不干」的人占死

`test_beta_permissions.py` 用 `limit=999` 验证「协作不限配额」，
**那一领就是整个池子**，测完又没退回 → 活一直卡在 `taken` → **真实成员无活可领**。

修法（三条一起）：

1. **新增退活接口** `POST /api/assist/return`（agent 别名 `/api/agent/return`）：
   把本节点领走但**还没回传**的活退回池子。
2. **agent 启动时先退掉自己上次遗留的活** —— 上一轮可能是被 Ctrl+C / 被 kill /
   窗口直接关掉的，`finally` 里的退活根本没跑成，
   而领活 SQL 只取 `state='pending'` → **本节点把自己堵死了**。
3. **回收看「节点是否还在线」**：agent 活着就每 12 秒发心跳，
   心跳断了 2 分钟 → 它不可能还在采那条活 → 立刻退回，不必等 30 分钟超时。
4. **测试脚本领完必须退活**（`_tools/test_beta_permissions.py` 里已加断言）。

#### 9.9.5 第五层：agent 领不到活时**一声不吭**

旧实现里 `if not picks: continue` —— 空转。界面上只看得到「运行中但很久没动静」，
用户完全分不清是「卡住了」还是「**没活可领**」。

修法：**agent 自报状态**（`collecting` / `idle`），通过两条路传给界面：

- 日志标记行 `[[state]] idle · 池子里暂时没有可领的活…` → 本机助手摘出来 → 网页显示
- 心跳带上 `state` → 服务端存进 `meta` → 「在线节点」表多一列**状态**（在采 / 在等活）

#### 9.9.6 第六层：界面自己的两个「假数字」

| 现象 | 根因 | 修法 |
|---|---|---|
| 本机面板「已领 0 帖 · 已完成 0 帖」恒为 0 | 面板从 agent 的**日志里正则数**，而 agent **压根没打**这两类行 | agent 补打 `领走 N 帖` 与 `tid=N ✓ 页/楼/字`；面板改用助手**累计**的计数（不从可见窗口数，窗口会滚动 → 数字忽大忽小） |
| 「已采详情帖」被算高 | 标记行被算进了楼层 | 「楼层总数」只算 `pid>0`；标记行单列 |

#### 9.9.7 顺带查出的两个「我们自己写的」硬 bug

**① SQL 括号 bug（SQLite 的 AND 优先级高于 OR）**

回收条件写成：

```sql
WHERE state='taken' AND (taken_at IS NULL OR taken_at < ?) OR node IN (离线节点)
```

SQL 会解析成 `(state='taken' AND …) OR node IN (…)` ——
**第二段不受 `state='taken'` 约束** → 某节点心跳断了 2 分钟，
它名下 **438 条已经采完的活**被退回池子，完成数从 466 掉回 56
（正文还在库里，只是状态乱了，成员得重复劳动）。
修法：OR 组整体括起来 → `WHERE state='taken' AND ((…) OR (…))`。
已加回归测试 `_tools/test_pool.py`（14 项）钉死它。

**② 并发写把 agent 打成「失联」**

服务端是多线程、**每个线程一条 SQLite 连接**（`get_db` 是 thread-local）。
`/api/assist/tasks` 这个**读接口里带了写操作**（顺手回收一下），
撞上正在回传的 agent 的写锁 → `database is locked` → HTTP 500 →
agent 把 5xx 当成「可能失联」→ 连着几次就**自己停了**。

修法三条：

1. 回收**先只读探测**（没有要回收的就不开写事务，不占写锁）
2. 显式 `PRAGMA busy_timeout=30000`（「读事务中途升级为写」不会走 busy handler，
   必须显式设）
3. 写路径（submit / pick）遇锁冲突**退避重试**，不让成员白跑

#### 9.9.8 顺带查出的一个「身份」问题

隧道重连时身份接口返回过 **520** → agent 拿不到节点号 → **用空节点去领活**
→ 活记在一个不存在的节点名下 → 界面上「各节点完成数」全对不上。

修法：**从令牌里本地解出身份**（JWT payload 本来就带 email/role/node，不联网）；
并且**节点号为空时拒绝领活**。

| 在线节点表 | `member:test@example.com` → 在线 · **状态=在采** · 已完成 160 · 进行中 25 · 失败 2 · 站方限制 0 |

#### 9.10.1 漏洞：成员点一次「开始采集」，是**管理员的机器**在刷站方

`/api/jobs/list`、`/api/jobs/detail`、`/api/jobs/taxonomy` 三个端点用的是
`require_auth`（**不是** `require_admin`）→ 成员在网页上点「开始采集」，

实测（`_tools/probe_member_jobs.py`，成员账号 `test@example.com`）：

★ 为什么这条比"界面不好看"严重得多：整个协作 Beta 的**核心前提**是

### 9.11 协作任务可以**撤销**（已完成的不废弃）

用户 2026-10-23 提的：「协作任务应该需要可以撤销，已经完成的不废弃」。

#### 9.11.1 撤销的语义：三块分别处理

| 那些活 | 处置 | 为什么 |
|---|---|---|
| 已完成 / 失败 / 站方限制 | **原样保留** | 正文已经进权威库了 —— 撤掉一个任务不该把**已经采到的东西**一起废掉 |
| 未完成（pending / taken） | 标成 `cancelled` | 不再有人领它们；但**不删** —— 留痕可查，也能事后恢复 |
| 权威库里的正文 | **一个字不动** | 正文本来就独立于任务存在 |

★ **正在被成员领着的那几条怎么办**
成员手里那几条在他采完回传时，`_mark_pick` 会把状态改回 `done`
→ **数据不浪费**，已采到的正文照常入库。
这是「已完成的不废弃」最实在的一种情形：**撤销不是砍掉，是停止派活**。

★ 为什么给未完成的活一个新状态，而不是直接删
删了就没法回答「这个任务当初派了多少活、干了多少、剩多少」。
留一条 `cancelled` 的痕迹，问题就还能问清楚 —— 而且能**恢复**。

#### 9.11.2 实现

| 位置 | 内容 |
|---|---|
| `AssistService.cancel(code, by)` | 任务 → `cancelled`；未完成的活 → `cancelled`；已完成的**不碰**；记实时日志 |
| `AssistService.restore(code, by)` | 撤销**不是终局**：作废的活重新放回池子，任务回到 `open` |
| `POST /api/assist/cancel` / `/api/assist/restore` | **管理员专属**（成员 → 403） |

### 9.12 增量要认「受理状况」，列表采集要留痕（2026-10-23 下午补）

用户看着「受理状态分布」问的：增量采集对受理状况的处理对不对？列表采集有没有留痕？
查下来**两处都有缺口**。

#### 9.12.1 缺口一：增量只比「回复数」，看不见「被受理」

原实现只比列表页给的 `replies`（回复数）。但站方给的列表行里还有**受理状态**，
而这两件事是**独立**的：

| 站方的动作 | 回复数变了吗 | 原实现能检出吗 |
|---|---|---|
| 群众留言被**受理**（未受理→已受理） | **不变**（还没回复） | ❌ **完全检测不到** |
| 站方**回复**（已受理→已回复） | 变大 | ✅ 能 |
| 站方删楼 | 变小 | ❌ 故意不判（可能是解析抖动） |

★ 为什么第一行是硬伤
「被受理」是舆情分析里**最关键的状态推进** —— 群众等的就是这一步。
只看回复数，等于**只看得见"被回复"，看不见"被受理"**。

★ 而且受理状态一变，本地数据就**确定**过时了，不只是「可能有新楼」：
详情页里有一份**受理流程时间线**（`flows` 表，见 §4.3），
站方受理 = 流程上多了一步 → 本地那份流程少了新的一步 → **必须重采**。

**改法**（`detect_reply_growth`）：

| 判据 | 条件 | 动作 |
|---|---|---|
| 回复数变大 | `new > old` 且详情已 `done` | 标 `stale` 待重采 |
| **受理状态变了** | **两边都是有效状态**（已回复/已受理/未受理）且不同，且详情已 `done` | 标 `stale` 待重采 |
| 受理状态变空 | — | **不判**（老帖在某些列表页有状态、某些页没有，那是渲染差异不是站方动作）—— 但**会记进留痕**，需要时查得到 |

#### 9.12.2 缺口二：列表采集几乎没留痕

查 `fetch_log` 里 `phase='list'` 的记录，一共只有 **8 条**，且只有三种 kind：
`drift`（页边界不连续）/ `detail_growth`（回复数变大）/ `rescan`（回扫补漏）。
**「这一趟列表采集看到了什么、和上次比变了什么」什么都没记**。

根因：列表采集是 **upsert 覆盖** —— 旧值被新值盖掉之后就**永远查不到了**。
增量检测只能在**覆盖前那一瞬间**比一次，比完就没了。

**改法**：新增 `list_changes` 表，把「覆盖前那一瞬间」**存下来**。
记四类变化（浏览数不记 —— 它每趟都涨，记下来全是噪音）：

| kind | 含义 | 为什么值得记 |
|---|---|---|
| `new` | 这个 tid 第一次出现在这个源 | 新帖，是舆情流量的源头 |
| `state` | **受理状态**变了 | ★ 受理流程随之变化 → 详情待重采 |
| `replies` | 回复数变了 | 站方追加了楼层 → 正文过时 |
| `title` | 标题被改了 | 站方可能合并/重命名帖子 |

落点：`db.record_list_changes(source, rows)` —— **必须在 `upsert_threads` 之前**调用；
界面在「完整性体检」页多一栏「**列表阶段的变化（站方动过哪些帖）**」，
含时间 / 采集源 / TID / 变化 / 旧值 / 新值 / 说明；
`fetch_log` 里也同步记一条（`changed_state` / `changed_new` / …），列表阶段从此有日志可查。

★ 顺带修掉一个界面缺陷：受理状态有 **2,232 条空值**（都是 2011–2014 年的老帖，
  站方列表页不给状态），图表里画成了**没有名字的空行**。现在标为「**(站方未标)**」。

### 9.13 启动器要自带「开放公网」这一步（2026-10-23 下午补）

用户一句「包含开放公网的启动器没有对接」，指向一个**一直在手动绕过去的坑**。

#### 9.13.1 原来的状态：公网是「手工参数」才能起来的

| 入口 | 原来干了什么 | 后果 |
|---|---|---|
| 双击 `程序\启动-web.cmd` | 只调 `web.ps1 start`（**不带** `-Tunnel`） | **只开本地，公网是断的** —— 组员连不上 |
| 手工 `web.ps1 start -Tunnel -TunnelDomain "msyt.…"` | 才带公网 | 这一整轮所有公网操作都得我手动敲参数 |

也就是说：**启动器跟「开放公网」这两件事没接上**。

#### 9.13.2 改法一：公网域名做成**配置**，启动器自动读

新增 `程序/data/tunnel-domain.txt`（内容 `msyt.example.com`）。

- **为什么不做成写死**：域名会变（换域名、换机器、测试域名），
  写死意味着每次换域名都要改脚本、还要记得改薄壳。
- **为什么启动器必须读它**：成员端就是从公网地址连进来的，
  启动器不带这一步 → 双击启动后公网是断的 → 组员连不上。

`web.ps1` 的新规则：

| 参数 | 行为 |
|---|---|
| 都不给（**双击启动器就是这个**） | **自动**读配置 → 有域名就一并拉起公网 |
| `-TunnelDomain xxx` | 用指定域名（覆盖配置） |
| `-NoTunnel` | **只开本地，不暴露公网** |

配套加了 `程序\启动-web-本地.cmd`（薄壳，只开本地）——
想「只在本地跑、不暴露公网」时双击它。

#### 9.13.3 改法二：把「隧道就绪」的**判据**换掉（这才是根上的 bug）

原判据是「打一下公网主域名，**有 HTTP 响应**就算通了」。

★ 这个判据**是错的**：主域名挂着 **Cloudflare Access**，匿名访问会拿到
  **Access 登录页**（状态码 **200**）——
  哪怕源站根本没连上，边缘也照样返回 200。
  实测：隧道早断了，脚本照样报「隧道已连接」；
  我自己写探针时也栽在同一个坑里（把 Access 登录页当成了后端响应）。

**新判据**：打 **agentapi 子域名**的 `/api/agent/me`。
它在 Access 里是 **bypass** 的 → 请求**一定转发到源站**；
我们的程序对它只开放 `/api/agent/*`，
所以会返回 **401**（未带令牌）或 **403**（路径不在白名单）
—— 这两个状态码**只可能来自我们的程序**（Cloudflare 自己出错是 5xx/530）。

| 情况 | 旧判据 | 新判据 |
|---|---|---|
| 隧道通 | 200（Access 登录页） | **401** ✓ |
| 隧道断 | 200（Access 登录页）✗ **误报通了** | **530** ✓ 正确报不通 |

★ 附带修掉一个 PowerShell 兼容性坑：
  `Invoke-WebRequest` 抛异常时，**PowerShell 7** 的 `Response` 是
  `HttpResponseMessage`（**没有** `GetResponseStream`），
  5.1 才有 —— 读 body 的代码在 7 上会静默失败。
  现在按状态码判据为主、body 为兜底，两套 shell 都能用。

#### 9.13.4 改法三：隧道已在跑就别再起一个

同一个 tunnel token 起两个 cloudflared 会**互相抢连接**，
表现是「公网时好时坏」。双击启动器时最容易踩（服务本来就在跑）。
现在 `Start-Cloudflared` 先查 PID 文件，活着就只报地址。

| 双击启动器（**不带任何参数**） | 服务起 + **隧道自动拉起** + 打印公网地址 |
| 启动后公网（真判据） | **401**（到了源站 = 通）✓；主域名 → Access 登录页 ✓ |

### 9.15 并发写 500：病根是「锁根本没锁住」（2026-10-23 下午补）

#### 9.15.1 症状

`test_beta_permissions.py` 整脚本崩溃：`AttributeError: 'NoneType' object has no attribute 'get'`。
往上追，是**心跳 500 → 改密码 500 → 重置密码 500** 的连锁反应。

#### 9.15.2 病根：`db.lock` 是一把**根本没锁住**的锁

webapp 的 `get_db()` 是**线程局部**的：

```python
_tls = threading.local()
def get_db(cfg):
    ...  # 每个线程各开一条 SQLite 连接
```

而 `DB.__init__` 里写的是：

```python
self.lock = threading.RLock()      # ★ 每个实例一把
```

于是**每个线程各有一把锁**。
`with self.db.lock:` 只能防住「同一线程重入」，
**完全挡不住两个线程同时写** —— 它看着像有锁，其实等于没锁。

并发写全靠 SQLite 自己扛，而「读事务中途升级为写」这种情形
**SQLite 不走 busy handler**，会直接抛 `database is locked` → HTTP 500。

★ 为什么最开始会漏掉：单线程测试全过，
  只有「多个节点同时心跳 + 管理员同时改密码」这种**并发场景**才炸。

#### 9.15.3 改法：锁按**库文件路径**共享

```python
_shared_locks: Dict[str, threading.RLock] = {}

@classmethod
def _shared_lock(cls, path):
    key = os.path.abspath(path)
    with cls._shared_locks_guard:
        lk = cls._shared_locks.get(key)
        if lk is None:
            lk = threading.RLock()
            cls._shared_locks[key] = lk
        return lk
```

同一进程内**指向同一个库文件的连接共用一把锁** → 写事务真正串行化。
读不占这把锁（WAL 下读可以并发）。

改之前先验过两件事，避免把锁变成新的故障源：

| 检查项 | 结果 |
|---|---|
| 锁块内有没有网络 IO（持锁发请求会把整个服务卡住） | **没有** ✓ |
| 锁块内有没有等别的线程（跨线程等待 → 死锁） | **没有** ✓ |

#### 9.15.4 补一层：写端点加退避重试

共享锁解决**进程内**并发；跨进程（比如 CLI 正好在跑）仍可能撞 SQLite。
所以改密码 / 重置密码这两个**最不该出错**的接口都套了 `_retry_locked`
（撞 `database is locked` 就退避重试 4 次）。

★ 为什么这两个接口要特殊对待：「改密码失败」对成员来说就是
  「我登不进去了」，是最不该出错的一个接口。

#### 9.15.5 顺带修掉：心跳不该每次都写库

心跳原来**每次**都写一次 meta（agent 每 12 秒一次，几个节点一起来写锁抢得凶）。
状态本来就是「变了才需要记」的东西 → 改成**只在 state 变化时**才写。

#### 9.15.6 顺带修掉：静态资源版本号写死 → 浏览器吃旧缓存

`index.html` 里原来是 `style.css?v=1.1.0` —— 版本号是**手写的常量**。
改了 CSS/JS 之后版本号没跟着变，浏览器就继续用旧缓存：
**服务端返回的是新文件，页面加载的还是旧的**，
症状是「我明明改了，怎么界面没变」。

★ 这个坑只在「改完前端、又没重启浏览器」时显形，**极难自查**。

改成**按文件 mtime 现算**（`__CSSV__` / `__JSV__` 占位符由服务端替换）：

| 情况 | 旧 | 新 |
|---|---|---|
| 改了 CSS | URL 不变 → **吃旧缓存** ✗ | URL 变 → 必然重取 ✓ |

#### 9.15.7 实测（2026-10-23 约 15:00）

| 项 | 结果 |
|---|---|
| `test_beta_permissions.py` | 修复前**崩溃** → 修复后 **50 / 50 通过** ✓ |
| 全量回归（11 个脚本） | **全绿**（194 项 + 漂移 12 项）✓ |
| 改密码（并发心跳下） | 200 ✓ 不再 500 |
| 重置密码 | 200 ✓ 且提示语完整 |
| 静态资源版本号 | `style.css?v=1792738226`（= mtime）✓ |

### 9.16 协作采集页的版面重排 + 合并记录翻页折叠（2026-10-23 下午补）

用户三条要求：

**为什么必须做**：库里合并记录已有 **867 条**（每条成员回传都留一行）。

4. 新增 `_tools/clean_test_residue.py`：一次性清掉 `tid >= 999999000` 的残留

### 9.18 agent 的失联判定：一次瞬时抖动不该让组员的活停在半路（2026-10-23 晚上补）

#### 9.18.1 组员的实测日志

组员在公网上跑 agent，贴了两段日志。第一段：

```
19:23:18  已启动 agent（pid 59908，凭证来源：网页递过来的令牌）
19:23:59  ⚠ 连接失败：ReadTimeout ... (read timeout=40)（连续第 1 次）
19:24:52  ⚠ 退活失败（不影响采集）：... (read timeout=40)
19:25:21  ⚠ 连接失败（连续第 2 次）
19:25:46  ✗ 连续 3 次联系不上控制面 —— 判定为失联，自动停止采集。
```

从启动到停止：**107 秒**。

第二段（另一个节点）：

```
19:23:59  ⚠ 连接失败：ReadTimeout ... (read timeout=40)（连续第 1 次）
19:24:52  ⚠ 连接失败（连续第 2 次）
19:25:21  联系不上控制面（还没到失联阈值），稍后重试…
19:25:46  ⚠ 连接失败（连续第 3 次）
19:25:46  ✗ 连续 3 次联系不上控制面 —— 判定为失联，自动停止采集。
```

用户原话：「连接超时似乎设置长了，感觉以网络连接，个人觉得可以 30s 以上一次，
不然可能容易连接超时」「这个也值得在意」。

#### 9.18.2 病根：三条全是「太急」

| # | 旧值 | 问题 |
|---|---|---|
| ① | 单次请求 `timeout=40` | 网络不通时**每个**请求白等 40 秒 —— 连「取身份」「退活」这种辅助请求也要等满（实测：取身份失败那条等了 41 秒） |
| ② | 失败后等 **1~5 秒** 就重试 | 网络还没恢复就连撞 —— 1 秒的间隔对 Cloudflare 隧道闪断、家里 Wi-Fi 抖动来说太短 |
| ③ | 连续 **3 次**就判失联 | 3×(40+5) ≈ 107 秒的容忍。**一次瞬时抖动就能让组员的活停在半路** |

★ 还有一个隐藏问题：**心跳与主请求共用一个失败计数**。
  agent 采一帖要几十秒，这期间主请求不发出、只有心跳在跑；
  两者一旦同时失败，计数翻倍 ——「连续 3 次」其实只有 **1.5 轮**。

#### 9.18.3 改法

```python
HTTP_TIMEOUT    = 20     # 单次请求（旧 40）
HTTP_TIMEOUT_AUX = 10    # 辅助请求：取身份 / 退活
RETRY_BACKOFF   = (30, 45, 60, 60, 60)   # 失联重试间隔，≥30 秒
FAIL_LIMIT      = 4      # 主请求连续失败几次判失联（旧 3）
HB_FAIL_LIMIT   = 6      # 心跳连续失败几次单独判失联（12 秒/次 → 约 72 秒）
```

| 改动 | 说明 |
|---|---|
| **timeout 40 → 20 秒** | 实测公网正常延迟 **1.4~2.3 秒**，20 秒有近 10 倍余量；40 秒纯浪费 |
| **辅助请求 10 秒** | 「取身份」「退活」失败不影响主流程，不值得占 20 秒 |
| **重试间隔 ≥30 秒** | 用户明确要求。退避 30 → 45 → 60 封顶，给隧道/网络恢复时间 |
| **阈值 3 → 4** | 配合新间隔，总容忍 **≈215 秒（3 分 35 秒）** |
| **心跳独立计数** | 心跳走 `_hb_fail_streak`，不再与主请求混算；任一方成功都清零另一方 |
| **票据兑换不计失败** | 票据是一次性的，兑换失败（过期/用过/网络不通）重试也没用，不该污染失联计数 |
| **日志说清等多久** | 「等 30 秒后重试（第 1 次退避；网络/隧道恢复需要时间，别急着放弃）」 |

#### 9.18.4 为什么 timeout 要**收紧**而不是放宽

用户的直觉是「超时太长容易超时」，实测数据支持这个直觉：

| | 旧 | 新 |
|---|---|---|
| 单次请求最长占用 | 40 秒 | 20 秒 |
| 一次「取身份」失败要等 | 41 秒 | 10 秒 |
| 4 次失败的总时长 | ≈180 秒 | ≈215 秒（**但每次失败更快知道**） |

★ 关键：不是「多等一会儿」，而是「**更快发现失败 + 更慢放弃**」。
  网络不通时快速拿到结论（20 秒而不是 40 秒），
  然后**给足恢复时间**（30/45/60 秒）再试 —— 这才是不误杀的关键。

#### 9.18.5 实测（2026-10-23 约 19:30）

| 项 | 结果 |
|---|---|
| `test_link_tolerance.py`（新增） | **24 / 24 通过** ✓ |
| 退避序列实测 | `[30, 45, 60, 60, 60]` ✓ 每次 ≥30 秒 ✓ |
| 心跳失败不污染主请求计数 | ✓ |
| 任一方成功 → 另一方也清零 | ✓ |
| 连续 3 次不判失联、第 4 次才判 | ✓ |
| 总容忍 | ≈215 秒（3 分 35 秒），比旧实现 107 秒宽裕一倍 ✓ |
| 全量回归 | 见 §9.18.6 |

  组员电脑上跑的是**下载下来的那份包**，不改包就还是旧行为。

### 9.19 启动包的凭证要**按账号**、而且**能反复用**（2026-10-23 晚上补）

用户原话：「msyt-成员端启动包没有根据账号进行更新！」

组员的实测日志（另一台机器）：

```
[agent] 已读取启动凭证（agent-ticket.txt）
[agent] ⚠连接失败：ConnectionError: ...（连续第 1 次）
[agent] 启动凭证不可用（与 ... 的连接失败: ...）
请登录采集网站（用你在网页上登录的同一个邮箱）
邮箱：member4@example.com
```

#### 9.19.1 病根：包里的凭证是「一次性 + 30 分钟」

| | 旧设计 | 后果 |
|---|---|---|
| `used_at` | **用一次作废** | 组员**第二次**运行包 → 401「票据已用过」 |
| `expires_at` | **30 分钟过期** | 组员晚点运行 → 401「票据已过期，请回网页重新下载」 |

★ 启动包是**下载一次、长期使用**的东西，
  给它配一个「一次性 + 30 分钟」的凭证，本质上是**自相矛盾**。
  组员每跑一次就得回网页重新下载一次包 —— 而包里的凭证又只值 30 分钟。

★ 附带一个更隐蔽的坑：agent 把**网络不通**和**凭证失效**混成一句话
  （「启动凭证不可用」）。组员看到的是网络抖动，却被告知凭证坏了，
  于是跑去重新下载包 —— 白折腾一场。

#### 9.19.2 改法一：区分两种凭证

`agent_tickets` 表加一列 `repeatable`：

| `repeatable` | 谁签发 | 有效期 | 能兑换几次 |
|---|---|---|---|
| `0` | 网页 `/api/agent/ticket` | 30 分钟 | **1 次**（防泄露后被复用） |
| `1` | **启动包** `/api/agent/bundle.zip` | **30 天** | **可重复** |

★ 一次性票据**没取消** —— 它防的是「票据泄露后被别人复用」，
  网页「一键启动本机 agent」那条路仍然用它。

#### 9.19.3 改法二：agent 分清「网络问题」和「凭证问题」

```
启动凭证暂时兑换不了（**网络/服务端不通**，凭证本身可能没问题）：…
  → 这多半是网络抖动或隧道闪断，**过一会儿会自动重试**，不用重新下包。
```
vs
```
启动凭证不可用（票据已过期，请回网页重新下载启动包）
  → 回网页重新下载一次启动包即可（包里的凭证跟你登录的账号绑定）。
```

  凭证类 = 401（票据无效/过期/用过）、403（账号不可用）。

  风险可控，因为：① 成员权限很低（看不到成员名单/完整性体检）；
  ② 管理员随时能停用账号，**立即**让凭证失效；
  ③ 凭证只绑定**普通成员**权限，不是管理员。

#### 9.19.5 顺带修掉：登录接口因锁冲突 500

回归时出现 `database is locked` → `api_login` 500 → **谁都登不进去**。
根因是 SQLite 的「**读事务升级为写**」：

```python
members = {r["email"]: dict(r) for r in db.conn.execute("SELECT * FROM members")}   # ← 开读事务
...
db.conn.execute("UPDATE members SET last_login=? ...")                              # ← 升级为写
```

Python 的 sqlite3 默认 deferred：**一条 SELECT 就开一个读事务**，
而「读事务升级为写」是 SQLite **唯一不走 busy handler** 的情形 ——
别的进程正写库时它**不等**，立刻抛 locked。

**根治**：把 `db.lock` 换成一个**写锁**（`_WriteLock`）——
进入写块时先 `commit()` 掉可能存在的读事务，
后面的写就是「开一个新写事务」，会正常走 busy 等待。

```python
class _WriteLock:
    def __enter__(self):
        self._rlock.acquire()
        try:
            self._conn.commit()      # ← 结束读事务
        except Exception:
            self._rlock.release(); raise
        return self
```

★ 用起来跟 RLock 一样（`with db.lock:`），**现有代码一行不用改**。

### 9.21 隧道协议：QUIC 不通时**自动换 http2**（2026-10-23 晚上补）

#### 9.21.1 症状：公网一直 502，本地服务好好的

  这不是代码问题、也不是 Access 配置问题 —— 是 UDP 通路的问题

|---|---|
| `quic` | 只用 QUIC |
| `http2` | 只用 http2（**走 TCP**） |
| 不写 / 写 `auto` | **先试 quic，不通自动换 http2**（默认） |

`web.ps1` 的 `Start-Cloudflared` 改成「起一个 + 等就绪」的复用逻辑，
`auto` 模式下 quic 失败就杀掉重来一遍 http2。

★ 为什么 http2 能通：QUIC 走 UDP，http2 走 TCP ——
  **UDP 被限时，TCP 通常不受影响**。

| 项 | 结果 |
|---|---|

| 主域名 | **302**（Access 正常挡着）✓ |

★ 隧道闪断是**真实场景**，不是假设 ——

#### 9.22.1 病根：回传一次超时 = 一帖白采 + 整个 agent 停

```
20:51:07 开始采 A1 tid=8342294
...
20:52:11 ✓ 2 页 / 212 字          ← 已采了 21 帖，都正常
20:52:33 ⚠ 连接失败：ReadTimeout (read timeout=20)（连续第 1 次）
20:52:33 ✗ tid=8342251 回传时失联，本帖丢弃（数据只在内存里，不会残留）
20:52:36 结束：完成 20 帖，失败 1 帖（因与控制面失联而自动停止）
```

★ 旧实现（`agent.py` 主循环）：

```python
except LinkLost:
    stopped_by_link = True
    self.log("✗ tid=8342251 回传时失联，本帖丢弃")

    break                      # ← 跳出整个采集循环！
```

代价是**双重的**：
1. 那一帖正文**白采了**（数据只在内存里，进程退出就没了）
2. 剩下 **29 帖**（50 领的 − 21 已采）**全都不采了**

★ 用户的话完全对：「回传后失联就断开，不重试不大合理」。

#### 9.22.2 改法一：回传带退避重试，失败只放弃那一帖

新增 `Agent._submit_with_retry()`：

| 情形 | 旧 | 新 |
|---|---|---|
| 回传时一次超时 | **本帖丢弃 + 整个 agent 停** | **退避 30/45 秒后重试** |
| 重试成功 | — | 这一帖**正常计入完成**，数据没白采 |
| 重试 3 次仍失败 | — | 只放弃**这一帖**，**继续采下一帖** |
| 连续 4 帖都失败 | — | 才判定控制面真的不可用，停止 |

★ **重试是安全的**：回传走「**合并覆盖**」语义（§5.13），
  同一帖重复提交只会覆盖成同样的内容 —— **幂等**。

★ 一个坑：`submit()` 成功返回后会**清空 payload**（"传完即删"）。
  所以重试前要确认 payload 里还有正文（`if not payload.get("posts")`），
  且计数/摘要必须在**每次尝试前**重新取 —— 实现里先把它们快照下来。

★ 顺带把「采正文阶段失联」那个 `except LinkLost` 的 `break` 也去掉了 ——
  正文没采完，没有可回传的数据，放弃这一帖继续下一帖即可。

### 9.25 数据缺口：「少贴」的帖**保留原帖 + 标记 + 作增量补采**（2026-10-23 晚上补）

用户原话：
「另外，就是数据缺口的情况
  建议如果有少贴的情况下，保留原贴并且标记
  主要是作增量的补采」

#### 9.25.1 现状：少贴的帖被归进「软警告」→ **永远不会被补采**

截图里「完整性体检」的软警告区：

| 说明 | 含义 |
|---|---|
| 站方回复计数 4 + 1 与实收楼层 4 不自洽 | 站方说 5 楼，我们收到 4 楼 |
| 楼层号缺口 [3]（站方删楼/置顶）；站方回复计数 3 + 1 与实收楼层 3 不自洽 | 楼层号中间缺 |
| 站方回复计数 7 + 1 与实收楼层 6 不自洽 | 站方说 8 楼，我们只收到 6 楼 |

旧实现把这类归成「软警告（**不算漏采、也不算增量**）」→ **缺口永远留在库里**。

#### 9.25.2 先分清两种「少」（实测 400 个 done 帖）

| | 楼层号 | 结论 |
|---|---|---|
| **尾部少** | 连续（[1,2,3,4,5]） | 站方**还有楼我们没采到** → **增量，该补采** |
| **中间缺** | 有缺口（[1,3,4] 缺 2） | 站方**删楼/置顶** → 那楼已不存在，补采没意义 |

★ 实测数据（抽查 400 个 done 帖）：
  · **392 个**「站方称 replies+1 楼」是**对得上的**（replies 不含楼主，+1 是楼主）
  · 少数（8 个）对不上，差 1~2 楼，且**楼层号连续** → 尾部少 → 该补采

判据抽成了**可测的函数** `is_short_and_retryable(expect, got, floors)`：

```python
def is_short_and_retryable(expect_posts, got_posts, floors=None) -> bool:
    if not expect_posts or got_posts >= expect_posts:
        return False
    fl = sorted(set(floors or []))
    if not fl:
        return True
    mx = max(fl)
    gap = [i for i in range(1, mx + 1) if i not in fl]
    return not gap          # ★ 楼层连续（尾部少）才补采
```

#### 9.25.3 处置：保留 + 标记 + 入队（复用 §9.12 的同一套机制）

`db.mark_detail_stale(tids, reason)` 做的正是这件事：

| 动作 | 结果 |
|---|---|
| `threads.detail_state = 'stale'` | 界面显示「待更新」（**不是**「已完成」） |
| `detail_queue` 置回 `pending` | 下次详情采集自动捡走重采 |
| **原帖数据** | **一条不删** ✓ |

#### 9.25.4 ★ 解开一个死锁：必须**在体检时**标记

★ 「少贴」的帖是 `done` 状态，而详情采集**只捡 pending/stale** ——
  done 的帖永远不会被重新采集 → 也就永远不会被标 stale → **死锁**。

所以标记动作放在**体检**里（管理员主动触发的「找问题」动作）：
体检扫到少贴的帖 → 直接标记 + 丢回队列 → 增量栏里也会显示出来。

采集时（`collect_one`）也做同样的标记，覆盖「采完当场发现少贴」的情况。

#### 9.25.5 ★ 顺序 bug：标记会被写 done 覆盖掉

第一版实现踩到：

```python
self.db.mark_detail_stale([tid], ...)     # ← 设成 stale
...
self.db.set_thread_detail(tid, detail_state="done", ...)   # ← 又盖回 done！
```

结果：**白标一次**，帖还是 done，永远不会进补采队列。

★ 修法：**先算标志，写完 done 之后再动作**。
  （顺序不能反：先标 stale 再写 done = 覆盖；先写 done 再标 stale = 生效 ✓）

#### 9.25.6 ★ 再一个 bug：补采次数没落库 → **上限失效 → 无限重采**

`detail_warn` 是空的 —— 而「已补采 N 次」就记在那里。
→ 下一轮读出来永远是 0 → 永远 `< GAP_RETRY_MAX` → **无限重采**。

修法：标记成功时把 `reason + 「已补采 N 次」` 一起写进 `detail_warn`，
并且**读在写之前**（先算 `_tried`，再写新值）。

上限 `GAP_RETRY_MAX = 2`：补两次还对不齐 → 判为「站方计数口径差异」，
只保留告警、不再自动补采（避免无意义的反复重跑）。

| 楼层号缺口（中间缺） | 软警告 | 软警告（明说「不补采——那楼已经不存在了」） |

### 9.26 检索筛选：下拉框选了却**不生效**（2026-10-24 下午补）

**现象**（用户实测截图）：检索页的七组筛选器（类别 / 受理状态 / 留言箱 / 部门分组 /
区县市 / 部门 / 时效灯）都选好了，点「检索」，结果行仍写着
「命中 607,028 条 · 检索方式 无关键词」——**等于没筛**。

#### 病根：前端取值的 id 少了 `f-` 前缀

```js
// 旧写法（错的）
const g = id => { const e = $('#' + id); return e ? e.value : ''; };
['scope','sort','category','state','group','district','dept','light'].forEach(k => {
  if (g(k)) p.set(k, g(k));      // g('category') 找的是 #category → 永远 null
});
```

页面上的真实 DOM id 全都带 `f-` 前缀（`#f-category` / `#f-state` / …）。
`g('category')` 找 `#category` → 取到 `null` → **这个键直接被跳过**，
于是**所有下拉筛选被静默丢掉**，请求里只剩关键词与日期。

| 为什么一直没被发现 | 说明 |
|---|---|
| 后端一直是好的 | `/api/threads` 的 `category/state/group/district/dept/light/mailbox/date_*` 全部支持，SQL 条件也正确（§9.4） |
| 关键词与日期**能用** | 它们写的是 `g('f-q')` / `g('f-from')`，带前缀 → 正常 |
| 界面**看不出错** | 下拉框确实变了，但请求参数里没有它 → 结果仍是全量 |
| 报告里写的是「七条标签轴筛选」 | 那是**设计意图**，实现没跟上（这次才补上） |

★ 教训：**「控件有值」不等于「值被用上了」**。
前端把「取不到元素」和「值为空」都当成同一件事（`e ? e.value : ''`），
于是一个 id 拼错会被**静默吞掉**，没有任何报错。

#### 修法与补齐的功能

1. **取值补上 `f-` 前缀**（`g('f-' + k)`）—— 这是本次唯一的真 bug。
2. **补上「留言箱」这一轴**：后端与 `/api/meta` 一直支持 `mailbox`，
   但页面上**没有这个下拉框**（`#f-mailbox` 从未写过进 HTML）→ 补上，
   七条标签轴这才真正凑齐。
3. **点标签即筛**：表格里的 部门 / 类别 / 状态 / 时效灯 都做成可点，
   点一下就按它筛（虚线下划线提示），并 `stopPropagation` 避免误开详情抽屉。
4. **生效条件可见**：结果行下方列出「当前筛选：类别：投诉 ✕　状态：未受理 ✕」，
   点 chip 去掉那一条 —— 避免「筛了什么看不见」。
5. **下拉改动自动检索**：改完条件立刻出结果，不必再点「检索」。
6. **「重置」补全**：原来漏了 `f-mailbox` / `f-scope` / `f-sort`。

### 9.28 小助手的端口要**能自己设**，而且**下载的包要跟设置同步**（2026-10-24 下午补）

**要求**（用户原话）：「小助手的网络端口建议可以自行设置；下载的 Agent 包与设置的网络接口同步；
对了，记得提醒改设置/重下包。」

#### 为什么这个端口不是「随便改个数」就行 —— 有三处必须一致

小助手跑在**成员自己的电脑**上，网页在**成员的浏览器**里，两者靠
`http://127.0.0.1:<端口>` 通信。而**启动包是服务端生成的**。
所以同一个端口至少出现在三个地方：

| # | 位置 | 谁写 | 什么时候生效 |
|---|---|---|---|
| ① | 成员本机助手的监听端口 | 包里的 `helper-port.txt` / `启动助手.cmd` | 成员改完重启助手 |
| ② | 网页呼叫助手的端口 | 浏览器 localStorage（成员自设）→ 服务端默认 | 刷新页面 |
| ③ | **服务端默认**（决定**新下载的包**用哪个端口） | `程序/data/helper-port.txt` | 管理员在网页上改 |

★ 少一个就会出「网页叫不到助手」——而这个症状**看起来**像「助手没起」，
很容易把组员引到错误的方向（去折腾 Edge 权限、反复重下包）。

#### 落法

1. **服务端可设**：`GET/POST /api/agent/helper-port`
   （读=成员可读；改=**管理员专属**，成员改返回 403），值落在 `程序/data/helper-port.txt`。
2. **包与设置同步**：打包时把端口写进 **三处** ——
   `启动助手.cmd` 的 `--port N`、`helper-port.txt` 的第一行、`说明.txt`。
3. **成员本地可改**：助手启动时**优先读同目录的 `helper-port.txt`**
   （其次命令行 `--port`，再次默认 8766）
   → 成员改端口**只改一个文件**，不用改 cmd、不用重下包。
4. **网页端可改**：「成员端工具」里加「小助手端口」输入框 + 两个按钮：
   - **保存到本机**（只改这台机器的网页，存 localStorage）
   - **设为服务器默认**（管理员，影响以后新下载的包）
5. **对不上要能发现**：网页叫不到助手时，**先去别的端口探一遍**
   （服务端默认 / 8766 / 8767 / 8765 / 8080），
   找到就明确告诉成员「你的助手在 8766、网页在 8767」，并给出两个改法。
6. **提醒重下包**：管理员改完服务端默认，返回值与界面都写明
   「**已经下载过包的成员需要重新下载一次**」——
   这是**提醒**，不是强制：老包仍能用（它自己的 `helper-port.txt` 说了算），
   只要成员把网页端口改成一样的即可。

#### 实测（2026-10-24 下午）

| 项 | 结果 |
|---|---|
| 成员读端口 | `{"port": 8766, "default": 8766}` ✓ |
| 管理员改成 8790 | 返回 `{"ok":true,"port":8790,"message":"…已经下载过包的成员需要**重新下载一次**才能对上。"}` ✓ |
| 成员改成 8791 | **403**（管理员专属）✓ |
| 设成 8790 后下载的包 | `启动助手.cmd` 带 `--port 8790`；`helper-port.txt` 首行 `8790`；`说明.txt` 写 `127.0.0.1:8790` ✓ |
| 改回 8766 后下载的包 | `--port 8766` ✓ |
| 改包里的 `helper-port.txt` 成 8801 | 助手与自检**读到 8801**（文件优先于命令行）✓ |

**浏览器实看**：把网页端口改成 8767（助手在 8766）→ 点「启动本机 agent」→ 页面明确提示：

> 端口对不上：检测到本机助手在跑，但端口是 8766，而网页这边用的是 8767 —— 对不上。
> 二选一：① 把上面「小助手端口」改成 8766 并「保存到本机」；
> ② 改包里的 helper-port.txt 成 8767（或重新下载一次启动包）。

改回 8766 后 → 「本机 agent 已经在跑了」✓

#### 回归

新增 `_tools/test_helper_port.py`（**15 项**）：接口权限、端口随包同步、
`helper-port.txt` 优先于命令行、cmd 里仍无 `->`（防闪退）。

**现象**（用户截图）：组员在「采集作业」里点「开始采集」→ **什么也没发生**。

| # | 毛病 | 后果 |
|---|---|---|
| ① | 旧逻辑要求成员**先手动点一次「启动本机 agent」**，再回来点「开始采集」；agent 没跑时 `startLocalCollect` 直接 `return` | 成员看到的就是「点了没反应」 |

1. **点一下就自动把 agent 起来**：助手 `/start` 本来就支持带 `token + sources + pages`，
   网页把当前 JWT 递过去 → agent 用 `--token` 起来，成员**不用再手动点一次、也不用输密码**。
2. **反馈写在按钮旁边**（新增 `#j-msg` / `#dd-msg`），并沿用 `‹›` 强调约定
   （直接写两个星号会被 `esc()` 变成字面星号 —— 同一个坑，已经错过一次）。
3. **本机 agent 单独一块**：新增「本机 agent（在你自己的电脑上采集）」卡片，
   带状态行 + **实时日志**；轮询时同一份状态与日志**同时**写进这块
   （成员不必往上翻到「成员端工具」那张卡）。管理员看不到这块（他自己就是那台机器）。
4. **盯到 agent 退出为止**（`watchLocalStart`，最多 60 秒）：
   还在跑 → 「正在跑」；退出来了 → 把日志里的原因翻译成人话：
   - 「已采完 / 没活可采」→ 换个源，或到「协作采集」领活（那边有活）
   - 「失败 / 中断」→ 指去看日志
5. **成员视角的「任务运行情况」空态**改成说明白：
   「服务器上还没有任务 —— 这本来就应该有：你的采集跑在自己电脑上的 agent 里」。

### 9.30 检索的「部门」筛选取不了 + 筛选器要**能打字**（2026-10-24 晚上补）

**现象**（用户截图两条）：
① 选一个部门 → 页面只显示「**检索失败：**」（连错误信息都是空的）；
② 部门下拉框里 109 项混在一起（区县市和银行、税务…挨着排），
   要找「宁波税务」只能慢慢滚 —— 而站方那个
   「107家部门与企事业单位在线」的搜索框是**能打字的**：
   「输入部门名称、拼音或首字母」。

#### 病根①：SQL 的占位符与参数个数对不上 → 接口 500

```python
ph = ",".join("?" * len(ids))          # n 个占位
where.append(f"t.dept_id IN ({ph}) OR ... LIKE '%{','.join(ids)}%'")
args += [",".join(ids)] + [...]         # ← 却只给 1 个参数（把 "556,737" 当一个值）
```

`IN (?,?)` 要两个值，代码却绑了一个 `"556,737"` 字符串
→ sqlite3 抛「Incorrect number of bindings」→ 500 → 页面「检索失败：」。

★ 顺带发现：这个分支**从来没被真正测过** —— 部门筛选一选就崩，
所以既没进过正常用例，也没被回归覆盖。

**修法**（一条帖可能带**多个部门**：`dept_id` + `extra_dept_ids` 逗号分隔，
所以每个 id 要判两次：主部门是它，或副部门里含它）：

```python
parts = []
for i in ids:
    parts.append("(t.dept_id = ? OR "
                 "(','||COALESCE(t.extra_dept_ids,'')||',') LIKE ?)")
    args += [i, f"%,{i},%"]
where.append("(" + " OR ".join(parts) + ")")
```

#### 病根②：原生 `<select>` 不能输入

改成一个**可输入的 combobox**：保留原 `<select>`（值仍从它取，检索参数一行都不用改），
外面套一层 input + 浮层列表；输入即过滤。

| 能力 | 判据 |
|---|---|
| 名称子串 | 「银行」→ 中国光大银行宁波分行、中国农业银行宁波分行… |
| **拼音首字母** | 「NBSW」→ 宁波税务（`NBSW` = 宁波税务的拼音首字母） |
| typeid | 「556」→ 宁波税务 |
| 分组表头 | 列表按站方那 5 列的分组给表头（职能部门和群团组织 / 区（县、市）及开发园区 / 民生企事业单位 / 其他） |

★ **七个筛选器全部适用**（用户：「其他标签同理」）：
类别 / 受理状态 / 留言箱 / 时效灯 / 分组 / 区县市 / 部门。

### 9.31 日志一多就**卡**：限 500 行 + 分页 + 不再整块重绘（2026-10-24 晚上补）

**现象**（用户反馈）：「在采集作业日志过多的情况下具有一定的卡顿问题，
需要对于日志做一定的简略工作，例如仅仅显示500条，分页日志等等措施」。

#### 原来的三个毛病

| # | 毛病 | 为什么卡 |
|---|---|---|
| ① | 本机 agent 日志**每 3 秒**把整块日志 `innerHTML` 重写一遍（还写两份：成员端工具卡 + 本机 agent 卡） | DOM 节点多 + 反复重建 |
| ② | 采集日志（SSE）每来一条就 `appendChild` + `removeChild(firstChild)` | DOM 里常驻 600 个节点，且每条都触发一次布局 |
| ③ | 任务日志一次 400 行整块重绘 | 同 ① |

★ 还有一处**白费力气**：状态条里的「已领 N 帖 / 已完成 N 帖」每 3 秒都在变，
但它跟正文写在一起 → **正文那 100 行也被连带重绘**，而正文其实没变。

#### 现在的做法

1. **统一的日志视图组件** `makeLogView()`，三个日志框都用：
   - 内存里保留**全部**行（上限 2000，多的丢最旧 —— 与助手缓冲区一致）
   - **DOM 里最多渲染 500 行**（用户要求），并且**分页**：每页 100 行
   - 分页条：`‹ 上一页 ｜ 第 N / M 页 · 共 X 行 ｜ 下一页 › ｜ 跳到最新`
   - **翻到旧页就不自动跳回最新**（否则用户正在看历史时被拽走）
2. **状态条与正文分开**：状态条单独一个框 → 数字变了只重绘 1 个节点，正文不动
3. **正文没变就不重绘**（签名比对：行数 + 最后一行）
4. **页面不可见时不轮询**（切到别的页签就停，别在后台空转）
5. 助手侧：日志缓冲 400 → **2000** 行，`/status` 一次给 **500 行**（原来是 80）

#### 实测（2026-10-24 晚上，浏览器里实点）

| 观察点 | 结果 |
|---|---|
| 本机 agent 在采（已领 300 帖）时，日志行数 | 一路涨到 **500 行**（助手给的上限） |
| 分页条 | 「第 3 / 5 页 · 共 500 行」✓ |
| 点「上一页」 | 翻到第 3 页 ✓ |
| 等一个轮询周期（日志 352→445 行、4→5 页） | **仍停在第 3 页**，没被拽回最新 ✓ |
| DOM 里的日志节点数 | **每页 100 行**（不是 500/600 个节点常驻） |

#### 回归

新增 `_tools/test_log_paging.py`（**22 项**）：三个日志框都用了组件、
DOM 上限 500 / 每页 100 / 内存 2000、旧的「整块重绘」与「appendChild+removeChild」
写法都没了、状态条与正文分开、页面不可见时暂停轮询、助手一次给 500 行。

### 9.32 置顶帖与全局公告帖**从来没被采到过**（2026-10-24 晚上补）

**现象**（用户反馈）：「类似于置顶，会有漏采的情况，需要补采……
另外包括 `tid=7342780`、`tid=7342697` 需要收录」。

#### 先说结论：漏的不止「置顶」，是**两类帖**

| 类型 | 站方把它放在哪 | 旧解析器看没看 |
|---|---|---|
| 置顶帖 | `tbody[id^=stickthread_]` | 没有 —— 只扫 `tbody[id^=normalthread_]` |
| 全局公告 | `#msbgt` 里的一串**裸链接** | 没有 —— 它压根不是帖子行 |

实测库里 `tid=6177045 / 7342780 / 7342697 / 8333204 / 8333106 / 8228673`
**一条都没有**（`threads` 0 条、`posts` 0 楼）。也就是说：**全站历史上的置顶帖与公告帖，
从来没有进过库** —— 不是这一次漏了，是一直漏。

#### 真因不止一个：五个坑叠在一起

1. **列表解析器只扫普通帖行** → 置顶帖从来没被看过。
2. **全局公告是裸链接** → 旧解析器连这个区块都没找过。
3. **详情页的楼层清单只认 `postmsg_`** —— 而站方**偶尔不给某一层生成 `postmsg_` 容器**。
   少一个 pid → 触发「pid 集合精确相等」校验失败 → 整帖卡在半截（6177045 卡在第 3 页）。
4. **单帖页数上限 50 页**，而盖楼活动置顶帖站方自己标的是 **81 页** → 卡在一半，
   而且**断点续传也接不上**：续传从 `pages_done+1` 起算，一样落在 50 之外。
5. **公告行会把帖行的真值覆盖成空** —— 这是修完前四个坑之后**自己冒出来的副作用**，
   详见下面「第五个坑」。

第 4 条最隐蔽：它让「断点续传」这个本该兜底的功能，在长帖上**完全失效**。

#### 顺带排除掉一个**伪线索**

用户提到的 URL 形态 `…&extra=page%3D1&page=X`：**不是病根**。
实测 tid=6177045 不带 `extra` 也能正确翻满 6 页、第 7 页才回绕，
两种 URL 形态翻出来的页**完全相同** —— 分页 URL 形态无罪。
（先排除它，才没把时间花在改 URL 上。）

#### 第三个坑的现场证据：pid=108201995

采集 6177045 第 4 页时，ajax 返回 15 个楼层，而页面的 `postmsg_` 锚点只有 14 个，
差的那个叫 `108201995`。逐项核对后确认：**这一层在页面上是完整的**
（`post_108201995` 容器、`favatar108201995`、`postnum108201995`、`authorposton108201995`
齐全，楼层号 51 也读得到，站方自己的 `fixed_avatar([...108201995...])` 列表里也有它），
只是**站方没给它生成 ajax 注入目标**，而 `ajax_getpost` 照样返回了它的正文。

于是「楼层清单」少了一个 → 精确相等校验失败 → 整帖停在第 3 页。

**改法**：楼层清单改用外层容器 `post_{pid}`（它是全集），`postmsg_` 只作兜底。
改之前先批量验证了不变式（5 个帖共 15 页全过）：

- `postmsg_ ⊆ post_` —— 不会因为换口径而漏层
- `post_ == ajax 返回集合`（精确相等）—— 不会放宽防串帖的那道校验

#### 查漏：109 个部门页全扫过，**漏采 0 帖**

置顶帖恒定钉在列表顶部、公告区也只在第 1 页出现 → **只扫第 1 页就能覆盖全部**，
不必翻 500 页。扫了 109 个部门与区县市列表页（第 1 页），结果：

| 观察点 | 结果 |
|---|---|
| 公告区 | **每个部门页都有**同样 3 条（6177045 / 7342697 / 7342780） |
| 置顶帖 | 只有「宁波日报报业集团」（typeid=972）下有 1 条 = 6177045；其余部门页均为 0 |
| 取页失败 | 0 个源 |
| 与库比对 | 漏采 **0** 帖，采了但没完成 **0** 帖 |

（另外 3 个盖楼活动置顶帖只在主板块 `fid=1176` 出现，不在部门页 —— 也已收录。）

### 9.33 「历史帖子仅限作者本人查看」：分界探测与统一批量标注（2026-10-25 补）

**用户原话**：

> 民生e网通似乎对于在一段时间以前的帖子设定了「仅限作者本人观看」，
> 这种帖子的规模不小，可能是某个时间之前，不过置顶的帖子除外。
> 请帮忙进行探测工作，为一次历史帖子仅限作者本人查看的统一批量标注做好准备。

> 另外，一日 36000 篇，可能还是有些慢了。

两个诉求：**把站方限制的帖统一标出来**（数据正确性），以及**别再为它们白跑**（速度）。

#### 探测结论：分界在 **2023-12-31**

站方的限制是**一刀切的时间线**，不是一个模糊的「很久以前」：

| 抽样区间 | 样本数 | 结果 |
|---|---|---|
| 2013-09 ～ 2016-01 | 70 | **全部受限** |
| 2016 ～ 2022（按年） | 21 | **全部受限** |
| 2023-01 ～ 2023-11（逐月） | 33 | **全部受限** |
| **2023-12-01 ～ 12-30（逐日，每天 2 个）** | **60** | **全部受限，零例外** |
| **2023-12-31** | 2 | **可见** |
| 2024 / 2025 / 2026 | 9 | **全部可见** |

tid 边界同样干净：最后一个受限的是 `tid=8074223`，第一个可见的是 `tid=8074340`
（**边界 ≈ 8074300**，与此前独立测得的边界吻合，两次独立测量互相印证）。

#### 例外：**置顶的老帖**（用户直觉是对的）

实测 `tid=6177045`（2013-08-30 11:54 的置顶帖）→ **77 楼全部采到**；
而**同一天发的另外 13 个帖，全部受限**。

→ 站方对历史帖只给作者本人看，但**它自己主动置顶的帖保留可见**。
这类帖对舆情分析恰恰最重要（版规、公告、长期活动），**批量标注时必须豁免**。

#### 顺带查出的一个 bug：受限帖被**反复重采**，白占四成产能

排查「一日 36,000 篇」时发现的：

- 详情队列里 `pending` 有 **602,881** 条
- 其中 **14,910** 条对应的帖**早就被标成 `restricted`** 了
- 原因：`mark_restricted()` 只写 `posts` 与 `threads`，**没碰 `detail_queue`**
  → 受限帖在队列里仍是 `pending` → `claim_next_detail` 会**一遍遍把它捡起来重采**，
  每次都白跑一个详情页请求 + 一轮限速等待

按单线程 1.5 秒/帖算，这 14,910 个帖就在**白占约 41% 的产能**。
（单线程理论上限 57,600 帖/天，扣掉空转后 ≈ 34,000 —— 与实测的 36,000 几乎吻合。）

**修法**：`mark_restricted()` 里把队列行一并置为终态 `restricted`。
站方限制是「**采不到**」，不是「还没采」，不该再进队列。

#### 批量标注：判据与豁免

阈值之前的老帖有 **39.9 万**个量级。逐个去撞站方限制要 **6.7 天**纯浪费，
所以要**先按判据批量标**。判据（**保守：宁可少标，不可错标**）：

```
候选 = pub_ts > 0
     AND pub_ts < 2023-12-31
     AND detail_state NOT IN ('done','restricted')
     AND 库里没有真实楼层（pid>0）        ← 已有正文的帖绝不能被覆盖
     AND 不在豁免名单里
```

**豁免名单有两类，缺一不可**：

| 类别 | 为什么必须豁免 | 怎么识别 |
|---|---|---|
| **置顶帖** | 站方主动保留的老帖，实际可见 | 列表页的 `tbody[id^=stickthread_]` |
| **公告帖** | 站方公告区的链接**没有发帖时间**（库里 `pub_ts=0` → 1970）→ 会被时间判据当成「很老的帖」而误判，但它们**实际可见** | 列表页 `#msbgt` 里的链接 |

★ 第二类是**探测过程中实测踩到的**：只豁免置顶帖，会把两个公告帖
（`tid=7342780` / `7342697`）误标成受限。

为此新增了 `thread_list_forms` 表，记录「这个 tid 在列表页里**以什么形态出现过**」
（`row` 普通帖行 / `stick` 置顶帖行 / `announce` 站方公告区），
由列表采集**顺带**记下（批量入库，一次事务，不拖慢列表采集）——
站方每天会换置顶，所以这个名单必须**持续累积**。

#### 抽样验证（判据准不准，90 个样本）

| 组 | 样本 | 实测结果 |
|---|---|---|
| 候选组（阈值前、判为受限） | 45 | **45/45 确为受限**，误标 **0** |
| 对照组（阈值后、判为可见） | 45 | **45/45 确为可见**，异常 **0** |

#### 实际执行（2026-10-25）

39.9 万个帖的批量标注，**分批 2 万、一次事务，用时 64 秒**：

| 指标 | 标注前 | 标注后 |
|---|---|---|
| `restricted`（站方限制） | 19,006 | **418,440** |
| `pending`（待采） | 573,429 | **173,652** |
| 详情队列 `pending` | 602,881 | **203,447** |
| 详情队列 `restricted` | 0 | **399,434** |

★ 队列里剩下的 20.3 万条**全是真正能采到正文的** —— 不再有「白跑一趟才发现看不到」的帖。

标注后的复核（**零误伤**）：

| 复核项 | 结果 |
|---|---|
| 豁免名单（置顶 4 + 公告 3，共 6 个 tid）被误标 | **0** ✓ |
| 已采到正文的帖被误标 | **0** ✓ |
| 库里已有真实楼层的帖被误标 | **0** ✓ |
| 阈值之后的帖被误标 | **0** ✓ |
| 随机抽 20 个「已标受限」→ 实测站方 | **20/20 确为受限** ✓ |
| 随机抽 20 个「未标且在阈值后」→ 实测站方 | **20/20 确为可见** ✓ |

#### 提速账

### 9.34 并发采集：先测站方能承受多少，再放开（2026-10-25 补）

**用户原话**：「并发采集可以设计，并且同步到组员Agent端，现在可以慢慢测试到实现为止。」

#### 先测，再决定并发度

并发不是拍脑袋定的 —— 站方可能限速、可能 403/429、可能响应变慢。
所以先做**逐级加压**（每档之间歇 20 秒，不给站方累积惩罚的机会），
用真实的「详情页 → 紧跟 ajax」请求对（和真采集同节奏），只测不写库：

| 并发 | 请求/秒 | 详情页 P50 | P95 | 异常 | 实测日产能 |
|---|---|---|---|---|---|
| 1 路 | 1.44 | 0.69s | 0.78s | 0 | ≈ 61,700 |
| 2 路 | 2.23 | 0.85s | 2.02s | 0 | ≈ 96,000 |
| **3 路** | **2.82** | **0.99s** | **1.28s** | **0** | **≈ 123,000（最优点）** |
| 5 路 | 2.46 | 1.30s | 1.44s | **1 次 network 错误** | ≈ 105,000（反而降） |

5 路时**吞吐反而下降**、并出现连接错误 → **3 路是安全档**，定为默认。
（站方是**按 IP 限流**的：管理员本机与各组员在不同 IP 上，互不影响；
但同一台机器上跑多个采集进程会互相挤占。）

#### 并发单位是「一帖」，不是「一个请求」

站方 token 有效期 **< 30 秒**：详情页取到 token 后，**紧接着的那次 ajax 请求
中间不得插入任何 sleep** → 同帖两个请求必须贴在一起 →
能并发的最小单位是「一帖」，把两个请求拆到不同线程必然踩 token 过期。

#### 三条并发安全的前提

| # | 前提 | 怎么保证 |
|---|---|---|
| ① | **领活互斥** | `claim_next_detail()` 在**进程级共享**写锁里 → 两个 worker 领不到同一条 |
| ② | **写库串行** | 所有写操作走同一把共享锁 → 不会出现 "database is locked" |
| ③ | **每 worker 自己的连接与客户端** | sqlite3 连接**不能跨线程**（`check_same_thread`）；`requests.Session` 不是线程安全的；而且限速状态是**实例级**的 → 共用会让限速被绕过 |

#### ★★ 并发下暴露的一个**致命** bug：领活会抢到「正在采」的帖

`claim_next_detail()` 原来的 WHERE 是 `q.state IN ('pending','running')` ——
把**正在采**（running）的帖也当成可领的活！

串行时看不出问题（采完就变 done），但**并发时三个 worker 领到了同一个 tid**：

```
[领活] 线程=detail-1 → tid=8324409
[领活] 线程=detail-3 → tid=8324409    ← 重复
[领活] 线程=detail-2 → tid=8324409    ← 重复
```

后果：同一帖被采 3 遍（3 倍站方请求、限流风险），
另外 4 个帖**根本没被领到**（6 帖的限额只采出 2 帖）。

**修法**：
① 只领 `state='pending'`；`running` 的残留（进程被杀留下的）由
`reset_stale_running()` 在每次采集任务开始时统一归位（断点续传靠它，不靠这里）。
② **双保险**：UPDATE 带 `AND state='pending'` 条件并检查 rowcount ——
即使锁失效也抢不到重复的活。

#### ★ 另一个配套修复：受限判定要**复验**，还要**留证**

站方会**间歇性**返回「提示信息」页（密集访问时出现，同样的帖单独再请求又正常）。
而「站方限制」是**终态**（队列里摘出去 + 正文写标记 + 不计入已采详情帖）——
一次瞬时异常 = **永久误标** = 数据污染。

**修法**：判受限时**再请求一次**同 URL；复验能拿到楼层/token → 判为临时故障
（不算受限），并把提示页的特征（字节数 / 标题 / 楼层锚点数 / 复验结论）
**记进 `fetch_log`**，事后可查。

实测：留证机制抓到 12 次受限判定（tid=2903367 等 2013 年的老帖），
**复验仍是提示页 → 判定正确**（这些帖本来就该受限），零误伤。

### 9.35 采集并发数：**可设置**，并且**提示推荐值**（2026-10-25 补）

**用户原话**：「抓取并行需要可以设置并且提示推荐设置」。

#### 为什么必须能设

并发度不是「越大越好」：站方**按 IP 限流**，一路最稳、三路最快、五路反而更慢
（§9.34 的实测表）。而各家成员家的网速、带宽、公司网络策略都不一样 ——
「管理员机器上合适的数」不一定适合组员。

#### 三处要知道同一个值（照搬「小助手端口」那套一致性思路）

| # | 位置 | 作用 |
|---|---|---|
| ① | **成员本机** `workers.txt`（包根目录） | 这台机器实际用几路 —— 各人各设 |
| ② | **服务器默认** `程序/data/detail-workers.txt` | 管理员设；没自设的人用这个 |
| ③ | **网页**「成员端工具」区 | 显示与设置，并给出推荐提示 |

优先级：**本机 > 服务器默认 > 推荐值 3**。

★ 与端口不一样的一点：**改并发度不用重下包** ——
助手每次起 agent 前都会去读服务器默认值，所以管理员改了之后，
成员下次点「开始采集」就自动用新值。

#### 推荐值与提示文案


### 9.36 并行之后**看不到日志**：两个问题叠在一起（2026-10-25 晚上补）

**用户反馈**：「并行之后我看不到日志」（截图：任务跑了 161 秒，网页上只有 2 行日志）。

#### 先排除「日志机制坏了」

最小复现（假 client 记录日志）跑 `_run_parallel`：**日志正常打出 4 条** →
说明 `self.client.log()` 这条链是通的（`_JobClient` → `job.logs`，deque + 锁，线程安全）。

★ 于是转向查「为什么 job.logs 真的只有 2 条」。查 fetch_log 发现
**worker 一直在采**（每 2 秒一条记录）—— 那就是**采完了没打日志**，
可 `collect_one` 有返回就该打…
★ 再看领到的帖：全是 **2011–2014 的老帖**。于是根因浮出来了。

#### 根因一：队列里挂着 **14,636 个「注定采不到」的孤儿活**

| 状态 | 数量 | 说明 |
|---|---|---|
| `threads` 已标 `restricted`，队列却还是 `pending` | **14,636** | 站方限制是**终态**，正文永远采不到 |
| `threads` 已 `done`，队列却还是 `pending` | **21,379** | 已经采完了，不该再排 |

★ 根源是 §9.33 那个 bug 的**历史遗留**：2026-10-23 标记时
`mark_restricted()` 只写 `threads`、**没碰 `detail_queue`**（今天已修好函数，旧数据要手动清一次）。

★ 为什么它会让「日志看不到」：
领活是**按 pub_ts 升序**的 → 这批 2011 年的孤儿**排在队首** →
worker 一上来就撞上它们 → 每帖要走「提示页 + 复验」两次请求、**注定失败** →
日志产出极慢、产能也被占满。

★ 顺带一个「看起来像日志坏了」的元凶：站方提示原文后面跟着**一整段站方的 JS**
（`if(history.length > (BROWSER.ie ? 0 : 1)){ document.write(...) }`），
几百个字符 —— **日志框被两行就占满**，看着就像「没日志」。

#### 根因二：日期阈值**漏了 12-31 一整天**

既然要给受限帖做终态标注，就要有精确的分界。原先用「pub_ts < 2023-12-31」这个**日期**阈值，
而实测分界是**按 tid**切的（把 8074200~8074360 这 161 个帖**逐个**实测）：

| | tid | 发帖时间 | 结果 |
|---|---|---|---|
| 最后受限 | **8074333** | 2023-12-31 23:36 | 受限 |
| 首个可见 | **8074334** | 2024-01-01 00:08 | 可见 |

分布核对：**2023-12-31 当天 102 个样本全部受限、2024-01-01 起 18 个全部可见**
→ 站方就是在这**一刻**收的口。

★ 所以「pub_ts < **12-31 零点**」这个阈值 = **把 12-31 一整天漏在外面**了
（实际它们全受限）→ **漏标 85 个**。
★ 早先担心的「误标」（把 12-31 里可见的误标成受限）**不存在** ——
12-31 当天根本没有可见的。
★ 修正：改用**精确 tid 判据**（tid ≤ 8074333）补标了这 85 个。

#### 修法

| 位置 | 改动 |
|---|---|
| 一次性清理 | `detail_queue` 里「受限却排队」14,636 条 → 置 `restricted`；「已采完却排队」21,379 条 → 置 `done`；队首随即从「2011 年注定失败的帖」变成「2024-01-01 的可见帖」 |
| `msyt/db.py` | 新增 `_clean_notice()`：把站方提示原文**洗成一句人话**（只留「历史帖子仅限作者本人查看」）；`mark_restricted()` / `mark_restricted_bulk()` 统一走它 |
| `msyt/detail.py` | 日志里的受限提示用清洗后的短句（`_short()` 兜底截断） |
| 库内数据 | 19,010 条超长的 `detail_warn` 与正文标记行一并洗短（否则检索结果被一堆 JS 污染） |
| `_tools/mark_restricted_bulk.py` | 判据改成**精确 tid**（`--max-tid`），日期口径保留以便复现 |

#### 效果（2026-10-25 实测）

```

[detail] tid=8074334 ✓ 1 页 / 6 楼 / 524 字
[detail] tid=8074335 ✓ 1 页 / 2 楼 / 414 字
[detail] tid=8074336 ✓ 1 页 / 3 楼 / 685 字
[detail] tid=8074337 ✓ 1 页 / 4 楼 / 629 字
[detail] tid=8074339 ✓ 1 页 / 2 楼 / 552 字

```

★ 6 帖全部采到正文、**4 秒**跑完、日志行短而可读。
★ 队列里「分界以内」的帖 = **0**；队首即分界后第一个可见帖。
