## 一、规则变更（重要，覆盖之前的实现）

### 1.1 成员回传的帖子：**不跳过，采取并覆盖**

**旧规则（今天实现的第一版，明天要改掉）**：
本地该帖已是 `done` → 整体跳过，不覆盖；只补本地缺失的楼层。
依据是用户当时说的「重复的以我们有的为准」。

**新规则（用户 10 22 晚间明确）**：

> 「组员传输的帖子如果涉及到相关帖子，不跳过，采取并覆盖」

→ `msyt/assist.py: AssistService.submit()` 的合并分支要改成：

| 情形 | 现在（要改） | 明天改成 |
|   |   |   |
| 本地 `done`，成员回传 | 整体跳过（`skipped/local_done`） | **合并写入并覆盖** |
| 本地有同 pid 楼层 | 保留本地版本（`kept_local`） | **用成员版本覆盖**（`overwritten`） |
| 成员多出来的楼层 | 补进去 | 补进去（不变） |
| 计数 `posts_n/chars/head/tail` | 本地已 done 就不动 | **一律现算**（合并后的真实值） |

  `assist_conflicts` 表结构**不用改**（`kind` 换成 `overwritten` / `merged_new` 之类即可），
  但「说明」文字要从「以本地为准，不覆盖」改成「按成员版覆盖」。
  覆盖时要记一笔：覆盖了哪些 pid、覆盖前后的字数。
  ★ 这一改同时解决了 1.2 的增量问题。

### 1.2 已经采集过的帖子**可能有增量**，要能识别并加入

站方会追加新回复，所以「上次采完的帖」过一段时间可能多出楼层。

**识别办法（已有数据就能做）**：
列表页的「回复数 + 1」= 应有楼层数；与本地实收楼层数对比：
`replies + 1 > posts_n` → **站方有增量**，本地少了楼层。

  这条现在是以**软警告**形式出现在体检里的：
  「列表页称应有 N 楼，实收 M（站方回复计数与实际楼层不自洽）」。
  明天要做的是：把它从「软警告」升级成**可操作的增量线索** ——
  体检结果里单列一栏「疑似有增量（站方又回复了）」，并给出批量重采入口。
  ⚠ 注意区分：站方自己的计数也可能不自洽（今天实测 #8332684：站方说 5+1，实收 5）。
  所以这一栏是**线索**，不是判据 —— 重采后以**实际楼层**为准。

### 1.3 体检不一致的帖子：**可以重跑**，重跑与自行清除都可以

体检页（管理员专属）要加两个动作：

| 动作 | 行为 | 实现位置 |
|   |   |   |
| **重跑** | 把选中的帖重置为待采 → 丢回 `detail_queue` → 下次详情采集自动重采 | 新端点 `POST /api/integrity/retry` |
| **自行清除** | 清空该帖的楼层/分页凭据/详情状态 → 从此可以重新采 | 新端点 `POST /api/integrity/purge` |

  「重跑」= 软失败（数据留着，只是重新采一遍；采完按合并规则覆盖）
  「清除」= 硬清空（posts / thread_pages / flows / detail_queue 那一行 + threads 的详情字段）
  两者都要**按批**做（勾选多条 → 一起重跑 / 一起清除），不能一帖一帖点。
  清除是破坏性操作 → 界面必须二次确认，并写明影响范围（删几层、几字）。
  权限：这两个端点必须 `require_admin`（体检是管理员专属）。

### 实现要点

**① 合并（覆盖）**
  同 pid → 成员版**覆盖**本地版；新 pid → **加进来**（= 增量）；
  本地有而成员没采到的 → **保留**（不因成员少采而丢数据）
  计数（楼层数/字数/头尾/页数）**一律现算**，不用成员报的数字
  留痕：`assist_conflicts.kind` = `overwritten` / `merged_new`（旧规则的
  `local_done` / `dup_pid` / `content_diff` 在界面上标为「旧规则遗留」）
  ★ 顺带修掉一个旧 bug：旧实现把**全部楼层**在每一页都写一遍，
  导致所有楼层的 `page_no` 被刷成最后一页。现在**按楼层自己的 page_no 分组**再写。

**② 增量识别**
  判据 = 列表页的「回复数」**比上次采集时变大**
  必须在 `upsert_threads` **之前**比（否则回复数已被覆盖）
  **只有变大才判**（变小可能是删楼/解析抖动，宁可漏报也不能误重跑）
  命中 → `detail_state='stale'` + 丢回 `detail_queue`（pending, attempts 归零）
  实测（真实链路）：重采 `dept:1098` 打出
  `↻ 1 帖站方有新回复（#7477636 2→4）→ 已标记待重采`

**③ 重跑 / 清除**
  重跑（软失败）：数据保留，丢回队列；清除（硬清空）：楼层/分页凭据/流程/队列项全删
  都按批做（体检页勾选）；端点 `require_admin`（成员 → 403 实测）
  「清除」界面二次确认，并显示「删了多少楼层、多少页凭据、多少条流程」

### 一个重要的语义澄清（别再混）

「站方称 N+1 楼、本地实收 N 楼」是**站方自己的计数不自洽**（常见，差 1），
既不算我们漏采，也**不算增量** —— 体检页把它放在**软警告**栏。
「已识别的增量」栏只放**回复数两次快照确实变大了**的帖（即 `stale`）。
