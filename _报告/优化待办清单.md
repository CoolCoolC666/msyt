- [x] **存量回填工具** `_tools/backfill_post_time.py`：只抓详情页、只补 `post_time`/`post_ts`，不碰正文
- [~] **跑回填**（后台进程，断点续跑；当前 pid 见 `_备份/post_time_backfill.pid`）

**验收判据**：新正则对 `2025-5-23` / `2026-9-2` / `2026-10-29` / 带秒 全部命中；
补零后输出格式与存量格式一致（`YYYY-MM-DD HH:MM`）；回填后全库空时间比例显著下降。

**实测结果**：
- 闸 `test_post_time.py` **25 项全绿**（含反向验证：旧正则在 6 个真实写法上失效 5 个）
- 小批量实测（500 帖 / 516 页）：**补 1,792 条时间，错误 0，4.2 分钟**（2.05 页/秒）
- 公式修正后的三个帖：`8236013 0/41→41/41`、`8294530 0/34→34/34`、`8333204 3/34→34/34`
- 存量格式已核对：`post_time` 全部 77,933 条**长度 16**（零补零、无秒）→ 新输出与之一致
- 全量后台回填：剩 **137,551 页**，约 **24 小时**（并发 2 路，给正常采集留余量）
  - 进度文件 `_备份/post_time_backfill.done`；日志 `_备份/post_time_backfill.log`
  - 停止：`Stop-Process -Id (Get-Content _备份\post_time_backfill.pid)`
  - ⚠ 后台进程**被外部杀死过一次**（无 traceback）→ 断点续跑兜住，重启即可

⚠ **回填工具踩过的三个坑（都已修，闸里也记了）**：
1. 进度文件**提前标记**（在抓到之前就记「已完成」）→ 中途被 kill 会永久跳过 → 改成**先提交、后记进度**
2. worker 用 `q.get_nowait()`，队列空就 `return` → **worker 在主线程入队前就退出**，一页没翻 → 改成阻塞等
3. worker 里直接用主线程的 sqlite 连接 → 违反「连接不能跨线程」→ 改成 worker 只抓网络、**写库回主线程**

### P1-1 词表（关键词设计）—— 补上「查询词」这条可追溯链

- [x] **建表** `keywords`（word UNIQUE / kind / parent / enabled / note / created_at）
  + `keyword_hits`（keyword_id / tid / post_count / first_hit_at）
- [x] **DB 接口**：`add_keyword` / `list_keywords` / `delete_keyword` / `set_keyword_enabled`
  / `scan_keywords` / `keyword_hits` / `keyword_hit_words`
- [x] **扫描器**：**一次全表扫描 + 多词判定**（不是 N 次查询）；**排除词是「减」的**
- [x] **API**（写操作**管理员专属**，成员只读）：
  `GET/POST /api/keywords`、`POST /api/keywords/{id}/enabled`、
  `DELETE /api/keywords/{id}`、`POST /api/keywords/scan`（后台任务）、`GET /api/keywords/{id}/hits`
- [x] **界面**：新增「词表」页签（加词/停用/删词/扫描/看命中，分页）
- [x] **样例词表**：`_报告/样例词表.csv`（唯一事实源，40 词）+ `样例词表.md`（口径说明）
  + `_tools/load_sample_keywords.py`（灌库脚本）
- [x] **导出加列**：「词表命中」→ 导出共 **29 列**
- [x] **补闸** `_tools/test_keywords.py`（单元）+ `_tools/audit_keyword_api.py`（接口冒烟）

**验收判据**：五类词齐全；排除词真扣减；停用不参与扫描；成员调写接口 403；
命中能落到导出的「词表命中」列。

**实测结果**：
- 单元闸 **全绿**（含反向验证：排除词改成普通词后命中数必须变回去 → 证明扣减不是空转）
- 接口闸 **全绿**（含反向验证：没令牌 401、成员加词 403、成员触发扫描 403、成员**能看**）
- **真库扫描**：560,199 层 / **3.6 秒** / 命中 **172,093** 条
- **真库导出**：607,034 行 / 522.3 MB / 18.8 秒 / **29 列**
- ⚠ 闸里暴露的真 bug：排除词在样本正文里**一次都没出现** → 扣减是空转 → 改的是**测试数据**，不是实现
- ⚠ 闸里暴露的真 bug：`add_keyword` 返回的字典**没有 `kind_cn`** → 接口 500 → 修在 DB 层

**顺带修掉的真问题（不在原报告里，但同一根因）**：
后台回填进程**长时间占着库写锁**（每 100 帖才提交一次 → 事务一直开着），
导致服务端任何写操作 `busy_timeout` 等 30 秒也拿不到锁 → **实测写操作直接失败**。
改成**每帖一提交**后，回填照跑的同时写操作实测 **0.03 秒**返回。

### P1-3 裁决 80,701 条协作冲突 —— 给「合并痕迹」补结论

- [x] **先摸清底数**（不是想当然批量裁决）：
  `merged_new` 80,523 条里 **80,502 条是「本地 0 楼 → 成员回传 N 楼」的新帖首次入库**，
  只有 **21 条**是真正的「站方追加回复」；`empty` 161 条（118 条后来被补采成 done、
  41 条站方限制）；`overwritten` 14 条覆盖前后**字数完全相同**；`local_done` 3 条以本地为准。
  → 结论：**数据早就按「不跳过、并覆盖」处理对了，缺的只是裁决留痕**（`resolved` 原本全 0）。
- [x] **表加三个字段**：`resolved_at` / `resolved_note` / `resolved_by`（轻量迁移，不重建表）
- [x] **DB 接口**：`conflict_counts` / `resolve_conflicts` / `reopen_conflicts`
- [x] **API**（**管理员专属**）：`POST /api/assist/conflicts/resolve`、`POST /api/assist/conflicts/reopen`
- [x] **界面**：冲突卡上加「按类批量裁决 + 撤销」，表里加「裁决」列
- [x] **补闸** `_tools/test_conflict_adjudication.py`

**用户拍板的两条口径（2026-11-05）**：
1. **只写 `assist_conflicts` 留痕，不动 `sample_review`** ——
   这批是「合并痕迹」，不是「对样本的人工核验结论」；8 万条机器裁决写进人工台账，
   会把真正的人工核验记录淹掉。
2. **裁决人（`resolved_by`）留空** —— 人工签署位，服务端不代填人名、不填占位符。

**验收判据**：按类批量裁决只动该类未裁决的；说明必填；裁决人恒真空；
`sample_review` 行数不受影响；撤销留痕不删数据。

**实测结果**：闸 **全绿**（6 节 18 项，含反向验证：空说明被拒 / 裁决不存在的类 0 条 /
已裁决的不重复动 / 撤销后旧说明保留并标「（已撤销）」 / `sample_review` 仍是 0 行）。
接口层：无令牌 **401**、成员 **403**、非法类型 **400**（真库实测，**未在真库上写入任何裁决**）。
