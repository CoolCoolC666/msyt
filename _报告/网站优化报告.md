## 摘要

方法课把「高质量搜集」的标准定成一句话：**不是"数据多"，而是"结论可追溯"**，
并给出「每条正式样本应包含 6 个字段」的硬规格。

按这条规格逐项审计我们系统的**数据库字段**与**导出 CSV**（用户真正拿到手的东西），
结论是：**6 个字段里，完整达标的 0 个，部分达标 2 个，完全缺失 4 个**。

| 课件要求的样本字段 | 库里有吗 | 导出里有吗 | 判定 |
|---|---|---|---|
| ① 发布/显示时间与发现时间 | 帖级有；**楼层级 86.1% 缺失** | 发布时间有；**发现时间无** | 部分达标 |
| ② 来源平台、版块和观察单位 | 版块 ✔ 观察单位 ✔；**来源平台未记录** | 版块 ✔ 观察单位 ✔；**平台无** | 部分达标 |
| ③ 查询词/规则版本与进入候选池的路径 | **全库零关键词表**；路径只有部门编号 | **无** | **缺失** |
| ④ 原文摘要、链接及必要互动字段 | 链接 ✔ 互动 ✔；**摘要字段不存在** | 链接 ✔ 互动 ✔；只有全文，无摘要 | 部分达标 |
| ⑤ 纳入、排除或待核验的理由 | 只有系统诊断口径（非人工核验结论） | **无** | **缺失** |
| ⑥ AI 初筛结果与人工复核结果 | **无任何相关字段** | **无** | **缺失** |

**三条必须做的（能直接兑现"结论可追溯"）**

1. **修楼层发帖时间的正则**（一行改动）—— 站方日期不补零（`发表于 2025-5-23 19:55`），
   我们的正则要求两位数 → 全库 **482,266 个楼层（86.1%）** 的发帖时间被丢掉。
   【已验证】改一行后 3 个帖 109 个楼层从 **0/41、0/34、3/34** 变成 **41/41、34/34、34/34**。
2. **导出 CSV 补 4 列**：发现时间、摘要、核验结论、候选池路径 —— 否则「可追溯」在交付物上就不成立。
3. **建「核验台账」**（纳入/排除/待核验理由 + 人工签署位）—— 现有 `detail_warn` 是**系统诊断**
   （如「楼层号缺口」「计数核对」），不是**核验结论**；协作冲突 80,701 条 **100% 未裁决**。

**两个建议做的**

4. **建词表**（5 类词）—— 全库零关键词召回；实测中文检索受 trigram 分词器限制，
   **2 字词（地铁/公交/垃圾…）FTS 命中恒为 0**，20 词合计覆盖率仅 20.8%。
   走「一次扫描 + 多词判定」实测 **2.4 秒**，比 N 次查询快 5.6 倍。
5. **在界面上标注「结论边界」** —— 我们只有一个信源（天一论坛民生e点通），
   课件明确写着它**不宜直接推断**「一般社交讨论热度」；现在网站标题是「舆情采集系统」，
   总览摆着「站方自报留言 74.5 万」，很容易被读成「宁波舆情全貌」。

**一个别做的**

6. **不要为了凑"多源"急着接小红书/新闻**。课件给的是**证据分工**不是"多源就高级"：
   我们现在缺的不是信源数量，是**把单源用到底**（词表 + 核验 + 边界）。

## 一、优化依据：方法课的三条要求

### 1.1 人工核验、留痕与偏差说明

课件原文：

> 高质量搜集的标准，不是"数据多"，而是**"结论可追溯"**。
> 每条正式样本应包含以下字段：
> ① 发布/显示时间与发现时间　② 来源平台、版块和观察单位
> ③ 查询词/规则版本与进入候选池的路径　④ 原文摘要、链接及必要互动字段
> ⑤ 纳入、排除或待核验的理由　⑥ AI 初筛结果与人工复核结果

这六项是**样本级台账**，不是报表统计口径。

### 1.2 信息源与证据分工

课件给出两层分工：

**分类角度 → 决定采集设计**

| 分类角度 | 示例问题 | 对采集设计的影响 |
|---|---|---|
| 内容/领域 | 是公共安全、民生服务、政务服务还是企业危机？ | 决定要抓哪些事实、主体和诉求材料 |
| 关系 | 是否涉及官民、企民、医患、师生等关系？ | 决定要关注哪些利益相关者的表达 |
| 性质/过程 | 是突发事件、持续议题、谣言传播还是风险信号？ | 决定时间窗、事件节点和核验要求 |
| 影响 | 是局部讨论、跨平台扩散，还是可能反复激活？ | 决定是否需要持续追踪与多来源观察 |

**来源类型 → 适合观察 / 不宜直接推断**

| 来源类型 | 适合观察 | 不宜直接推断 |
|---|---|---|
| 政务/机构公开信息 | 公开回应、政策、办理状态、事实时间线 | 所有公众的感受与评价 |
| 新闻媒体公开报道 | 事件进展、采访材料、跨地区传播线索 | 网民总体态度 |
| 小红书公开笔记 | 生活体验、消费感受、地点/服务表达 | 宁波居民总体意见比例 |
| 天一论坛民生e点通 | 民生诉求、类别、公开受理/回复状态 | 一般社交讨论热度 |

> 我们系统的唯一信源正是最后一行的「天一论坛民生e点通」。
> 这张表**不是**对我们「信源不够」的批评，而是它**同时划出了我们能说什么、不能说什么**。

### 1.3 建立「词表」，关键词设计

| 词类 | 作用 | 示例（仅作方法示范） |
|---|---|---|
| 核心词 | 锁定核心对象 | 「宁波公交」「宁波地铁」 |
| 主体词 | 锁定服务主体/地点 | 线路、站点、运营单位、区域名称 |
| 事件/问题词 | 锁定关注的服务情境 | 「换乘」「晚点」「拥挤」「无障碍」 |
| 扩展词 | 提高召回，发现不同表达 | 别称、简称、常见错别字、相关话题词 |
| 排除词 | 减少同名、广告或无关内容 | 非本地同名地名、招聘、营销等 |

> 课件还点明：**选题名称可由监测范围、关键词、服务对象和报告规格等构成** ——
> 这直接对应我们「选题/任务」缺少命名规范的问题（见 §四 P2-3）。

## 二、现状取证：六个字段逐条核对

### 2.1 字段① 发布/显示时间与发现时间 —— 部分达标，且踩到一个真 bug

**帖级没问题**：607,032 / 607,034 条帖有 `pub_time`（99.9997%），607,032 条有 `last_reply_time`。

**楼层级 86.1% 是空的**：`posts` 表 560,199 个真实楼层里，`post_time` 与 `post_ts`
**同时为空的有 482,266 条（86.1%）**；有值的只有 77,933 条。
空的时间**不是站方不给** —— 实测三个帖的详情页，站方每个楼层都渲染了时间元素：

```
tid=8236013 page=1  长度=135105
  authorposton 次数=16  '发表于' 次数=16  postnum 次数=16
  soup.select 取到 em 数 = 16
     id='authorposton113263783' text='发表于 2025-5-23 19:55来自浙江'
```

**根因是一个正则**（`程序/msyt/parsers.py:611`）：

```python
# 现状
mt2 = re.search(r"发表于\s*([0-9]{4}-[0-9]{2}-[0-9]{2}\s+[0-9]{2}:[0-9]{2}(?::[0-9]{2})?)", txt)
```

站方日期**不补零**（`2025-5-23`、`2026-9-2`），正则却要求月日各两位 → **匹配失败**。

**【已验证】修法与效果**（只验证，未改生产代码）：

| tid | 楼层数 | 旧正则命中 | 改后命中 | 补零后样例 |
|---|---|---|---|---|
| 8236013 | 41 | **0** | **41** | `2025-05-23 19:55` |
| 8294530 | 34 | **0** | **34** | `2026-03-11 18:10` |
| 8333204 | 34 | 3 | **34** | `2026-09-02 14:49` |

改后正则对全部真实写法都命中：`2025-5-23` / `2026-9-2` / `2026-10-29` / 带秒 / `2024-12-1` / `2013-8-30`。
**一行改动可恢复 86.1% 楼层的发帖时间**，而这正是课件字段①最直接的证据。

**「发现时间」是空的**：`threads.first_seen` **全库 0 条有值**；
只有楼层级 `posts.fetched_at`（560,199 条，100%）记着抓取时刻。
发现时间其实**不缺数据**，只是没被抬到帖级、也没进导出。

### 2.2 字段② 来源平台、版块和观察单位 —— 部分达标

| 子项 | 实测 | 判定 |
|---|---|---|
| 观察单位 | `tid` 即一条民生诉求 | ✔ |
| 版块 | `dept_name` 607,029 / 607,034（99.999%）、`dept_group`、`dept_district`、`category` 607,028 | ✔ |
| 来源平台 | `thread_sources` 706,937 行，取值全是 `dept:512` / `dept:736` / `global` 这类**采集通道**，**不记录内容来自哪个平台** | ✘ |

**平台信息其实隐含在系统里**（我们只采天一论坛民生e点通），但**没有作为字段落库**，
导出时也无从体现 —— 交付出去的文件无法自证"这批样本来自哪个平台"。

另有两个相关事实：
- `threads.mailbox_name` 只有 **87,284 / 607,034（14.4%）** 有值 —— 留言箱（部门专箱）维度覆盖不足；
- `state`（受理状态）**591,583 / 607,034（97.4%）** 有值，
  与课件"适合观察公开受理/回复状态"正对得上，是我们**最有价值、也最被低估的一列**。

### 2.3 字段③ 查询词/规则版本与进入候选池的路径 —— 缺失

**全库没有任何关键词表**：逐表扫过 `posts` / `threads` / `thread_sources` /
`thread_list_forms` / `list_changes` / `depts` / `integrity_items` / `assist_conflicts`，
列名里含 `keyword` / `term` / `vocab` / `wordlist` 的**一张都没有、一列都没有**。

原因不难理解：**我们不是按关键词采的，是按 109 个部门目录采的**。
`thread_sources.source` 记的是 `dept:512` 这样的**部门编号**，
它是"从哪个部门页进的"，不是"用什么查询词、什么规则版本筛的"。

**进入候选池的路径其实有留痕，只是没被当成样本字段**：

| 表 | 内容 | 条数 | 对应课件的哪一半 |
|---|---|---|---|
| `thread_list_forms` | `row` 9,877 / `announce` 328 / `stick` 5 —— 帖子以什么形态出现在列表页 | 10,210 | **候选池路径**（有） |
| `list_changes` | `new` 189,886 / `replies` 1,892 / `title` 1,809 / `state` 33 | 193,620 | **候选池路径**（有） |
| `fetch_log` | `done` 131,372 / `restricted` 44,193 / `warn` 31,505 / `gap_retry` 14,997 … | 231,492 | **规则版本**（半有：只记动作不记版本） |

**「规则版本」是真空的**：`fetch_log` 记了每次采集做了什么，但没记**当时用的是哪一版规则/词表**。
规则一改，历史样本就不可复现 —— 这正是课件反对的"结论不可追溯"。

### 2.4 字段④ 原文摘要、链接及必要互动字段 —— 部分达标

| 子项 | 实测 | 判定 |
|---|---|---|
| 链接 | `threads.url` 607,034 / 607,034（100%） | ✔ |
| 互动字段 | `replies`、`views` 100% 有值；楼层级 `images` 有图的 215,599 条（38.5%） | ✔ |
| 原文全文 | `posts.content` 560,179 / 560,199（99.996%）有正文 | ✔ |
| **摘要** | **`threads` 表里 `summary` / `abstract` 列一个都没有** | ✘ |

现状是"**只有全文，没有摘要**"。全文在库里对机器友好、对人不可读：
一条 1,203 楼的帖子全文 30,848 字，人没法从里面读出"这条诉求是什么"。

### 2.5 字段⑤ 纳入、排除或待核验的理由 —— 缺失

`threads.detail_warn` 有 **426,431 / 607,034（70.3%）** 条非空，看着像"有留痕"。
但它的内容是**系统诊断口径**，不是**核验结论**：

```
少贴：站方称应有 1207 楼，站方详情页实测 1203 楼，本地实收 1203 楼 —— 差额来自站方列表页计数未随删楼而减
楼层号缺口 [30]（站方删楼/置顶，非漏采；这类不补采——那楼已经不存在了）
```

这两条说的是"**系统为什么这样处理**"，不是"**人为什么纳入/排除这条样本**"。
课件要的"纳入、排除或待核验的理由"是**针对样本的人工判断**，两者不能混。

更刺眼的一处：**协作冲突 80,701 条，`resolved` 全部为 0 —— 100% 未裁决**。

| kind | 条数 | 含义 |
|---|---|---|
| `merged_new` | 80,523 | 成员回传覆盖了本地已有楼层 |
| `empty` | 161 | 成员回传为空 |
| `overwritten` | 14 | 被覆盖 |
| `local_done` | 3 | 本地已完成 |

★ 这正是课件说的"**留痕与偏差说明**"该管的事：**冲突发生了、留痕了，但没人裁决**。
它不会让数据算错（合并覆盖的语义是对的），但会让"这条样本到底该怎么用"永远悬着。

### 2.6 字段⑥ AI 初筛结果与人工复核结果 —— 完全缺失

`threads` 的 35 个列里，**没有任何**初筛、复核、摘要、审核类字段
（`ai_col_exists` 的 4 次命中是误报：命中的是 `mailbox_id`/`mailbox_name`/`detail_state`/`detail_warn`
里的字母 "ai"）。

**协作侧已经具备"人"这一环的基础设施**（成员领活 → 回传 → 冲突裁决 → 队列终态），
但**这些动作的结果没有落成样本级字段**：
成员回传的是**正文**，不是"我对这条的判断 + 判断依据"。

→ 要补的不是"再加一个采集器"，而是**让协作的产出从"正文"升级为"正文 + 判断"**。

### 2.7 差距总表

|---|---|---|---|---|

| ⑥ AI 初筛/人工复核 | 全无 | 全无 | **未做** | 中高（要改协作协议） |

我们对外的正式交付是**导出 CSV**（`/api/export`），当前 **23 列**：

逐条对课件规格：

| ① 发布/显示时间与发现时间 | **半有** | `pub_time` ✔；**发现时间完全没有** |
| ② 来源平台、版块和观察单位 | **半有** | `dept_name` ✔（版块）；**平台没有** |

★ **结论**：交付出去的 CSV **无法自证"结论可追溯"**。
拿这份文件去做复核的人，会发现既不知道样本什么时候被发现的，也不知道谁、凭什么判定它该纳入还是该排除。
**这是本次优化最该先修的地方** —— 因为它不改采集能力，只改交付形态，**代价最小、收益最直接**。

## 四、优化项清单（按「改一处就多兑现一个字段」排序）

### P0-1 修楼层发帖时间正则 ★ 一行，恢复 86.1% 楼层时间

**改哪里**：`程序/msyt/parsers.py:611`

```python
# 现状（要求月日各两位，站方不补零 → 匹配失败）
mt2 = re.search(r"发表于\s*([0-9]{4}-[0-9]{2}-[0-9]{2}\s+[0-9]{2}:[0-9]{2}(?::[0-9]{2})?)", txt)

# 改为（接受 1~2 位月日，输出补零）
mt2 = re.search(r"发表于\s*([0-9]{4})-([0-9]{1,2})-([0-9]{1,2})\s+([0-9]{1,2}):([0-9]{2})(?::([0-9]{2}))?", txt)
if mt2:
    y, mo, d, hh, mm, ss = mt2.groups()
    fm.post_time = "%s-%02d-%02d %02d:%02d" % (y, int(mo), int(d), int(hh), int(mm))
    fm.post_ts = to_ts(fm.post_time) or 0
```

**注意**：存量 482,266 条空楼层**不会自动回填** —— 需要一次按 tid 重采（走现成的

### P0-3 摘要：先做"抽取式"，AI 作为可选增强

课件要的是"原文摘要"。两条路：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **抽取式摘要（推荐先做）** | 本地规则：取正文前 N 句 + 抽取部门/类别/受理状态/时间锚点 | 零新依赖、**可复现**（同一份数据永远同一份摘要）、可入库可导出 | 表达力有限 |
| AI 摘要 | 用户自带 key（沿用既有约定：key 存浏览器、不落服务端）现算现用 | 表达力强 | **结果不可复现、不宜入库**（换模型就变了，与"可追溯"冲突） |

★ **取舍**：课件的第一目标是"结论可追溯"，不是"摘要好看"。
所以主口径应当是**抽取式摘要**（入库、可导出、可复现）；
AI 摘要只能作为**阅读辅助**，且必须标注"由哪个模型、什么时候生成"。

### P1-1 建词表（5 类词），并让检索页能按词表命中

**为什么现在做不了**：全库零关键词召回。我们按部门采，**采不到"跨部门的服务情境"**
（同一个「地铁晚点」如果出现在多个部门版块、或出现在还没归类的帖子里，按部门采集是看不见的）。

**落地的关键约束（实测）**：

| 检索词长 | 走哪条路 | 实测耗时 | 命中 |
|---|---|---|---|
| ≥3 字 | FTS5（trigram 分词器） | **12–24 ms** | 「无障碍」409、「停车场」8,086（100% 命中 LIKE） |
| **2 字** | trigram **匹配不到** → `search()` 兜底走 LIKE 全表扫 | **1.5–1.9 s/词** | 「地铁」12,427 → FTS **0** |

★ **trigram 分词器对 2 字中文词结构性失效**：15 个常见民生词实测，
2 字词 FTS 命中**恒为 0**（地铁 12,427 / 公交 21,833 / 垃圾 11,302 / 道路 30,596 …），
3 字词 100% 命中，**整体覆盖率仅 20.8%**。
而课件举的例子「换乘」「晚点」「拥挤」**全是 2 字** —— 也就是说，
**不做词表专用实现，课件的示例词一个都用不上**。

**推荐实现：一次扫描 + 多词判定**（不做 N 次查询）

| 方案 | 20 词耗时 | 加速 |
|---|---|---|
| A：N 次 LIKE 查询（现状 `search()` 兜底） | 13.3 s（纯 SQL）/ 35.2 s（含完整检索流程） | 1× |
| B：**一次全表扫描 + Python 端多词判定** | **2.4 s** | **5.6×** |
| C：一次 SQL 扫描（`sum(case when content like ? ...)`） | 4.7 s | 2.8× |

三种方案计数**完全一致**（地铁 12,427 / 公交 21,833 / 道路 30,596 …），互为交叉验证。
方案 B 最快，且**天然产出一张"词 × 命中"矩阵** —— 这正是词表该有的产出物。

词表表结构（概念设计）：

```
keywords(id, word, kind,        -- 核心/主体/事件问题/扩展/排除
         parent_id,             -- 扩展词归属哪个核心词
         enabled, note, created_at)
keyword_hits(keyword_id, tid, post_count, first_hit_at)   -- 命中台账
```

★ **排除词**要特别当心：它是"减"的，不是"加"的。
课件举的「非本地同名地名」在我们这儿是**真问题**（"宁波"三字的同名地点遍布全国），
所以排除词必须**按词组**（`宁波 + 外省地名`）而不是按单词建。

### ⚠ 闸里抓到的真 bug：`esc()` 从第一版起就没转义（2026-11-06 已修）

写上面那个闸时顺手加了一条「名称里的标签必须被转义」的断言，**当场报红**。
用**字符码**逐个核对源码后确认：`esc()` 的替换表把 `&` `<` `>` `"` **映射回自己**，
只有 `'` 转成了实体 —— 也就是说它**从来没转过义**。

- 影响面：`app.js` 里 **206 处** `esc()` 调用全部是「拼进 innerHTML」；
  站方标题、作者名、部门名、核验理由里只要出现 `<`，就会被浏览器当标签解析
  （既破坏显示，也是 XSS 隐患）
- 修法：换成真正的实体，并**用 \\u0026 转义写法**写在源码里 ——
  这样源码里不出现连续的 HTML 实体字面量，免得以后被复制粘贴或工具链**还原成裸字符**
  （这个坑正是当初写成自映射的同款成因）
- ★ **教训**：这类"看起来对"的 bug，**肉眼和 grep 都看不出来** ——
  工具输出层会把 HTML 实体解码显示，源码里明明写着 `&lt;`，屏幕上却是 `<`。
  唯一可靠的判据是**打印字符码**。

### P1-1 的关键设计（课件「关键词设计」那张表）：
- 五类词：核心 / 主体 / 事件问题 / 扩展 / **排除**；
- **排除词是「减」的**：命中排除词的帖子从其它词的命中里**扣掉**；
- 扫描是**一次全表扫描 + 多词判定**（不是 N 次查询），且**不走 FTS** ——
  所以**2 字中文词照样能命中**（FTS trigram 对 2 字词恒为 0，这是本项目最大的检索缺口）；
- 扩展词用 `parent` 指回主体词（「轨道交通」→父词「地铁」），命中台账里能看出同一件事的几种说法。

**P1-1 顺带挖出并修掉的一个真问题**（不在原报告清单里）：
后台回填进程**长时间占着库写锁**（每 100 帖才提交一次 → 事务一直开着），

| 三 AI 生成 | 概述/诉求焦点/诉求主体/情绪对抗性/涉稳要素/处置建议 | 模型 | 就是它产的 |
| 四 人工 | 风险等级/建议/概述/备注 | 人 | 人工可改并留痕 |

**风险等级是规则算的**：`card.level_of()` 是纯函数 —— 同样的事实 + 同样的信号 + 同样的
AI 三个标记，必得同样的等级。AI 只提供「事件性质 / 是否紧急」当输入，**不能直接给等级**
（闸里有一条专门盯这个）。四档判定：urgent → 紧急；性质属质量安全/涉稳风险且未闭环 → 预警；
命中 ≥2 个信号 → 预警；=1 → 关注；0 → 提示。

**时效性**：卡片记一份**数据快照指纹**（末楼层/末回复时间/状态/回复数/楼层数/时效灯/
详情态/受理末阶段一起哈希）。取卡时现算指纹比对 → 不一致就标「已过时」并给重生成按钮。
**过时不是存下来的数**（表里不存 status），是现算的。

**幂等 = 不烧额度**：批量生成时，已有卡片且指纹没变 → 直接跳过（不调模型）。
人工改过的卡片（`edited_by` 非空）→ 自动重新生成一律不覆盖，要人点「强制重生成」；
强制重生成之后**人工痕迹保留**，后续自动批量仍会跳过它。

**落地位置**：`程序/msyt/card.py`（事实/信号/等级/指纹/提示词/解析/服务）、
`db.py` 新表 `thread_opinion_cards`（facts/signals/ai/judge/advice 分列存，一眼看得见
哪层是谁算的）、`webapp.py` 5 个接口、`web/card.js` + `index.html` + `app.js` + `style.css`。

**账号系统做成「可开关的设施」**（这是最关键的一处设计）

账号系统**没有删**，改成配置开关 —— 服务器端行为**一行不变**，只有分发版把它关掉。

| 开关 | `config.json` | 行为 |
|---|---|---|
| **开**（服务器端默认） | 不写 `auth_enabled` 或 `true` | 照旧弹登录框、走令牌校验、`ensure_admin` 自举账号 |
| **关**（分发版） | `"auth_enabled": false` | **免登录直进主界面**，全部按管理员；**不建账号、不写 `data/admin-账号.txt`**；界面藏「改密码 / 退出登录」 |

落地要点：

- `_auth_enabled()` 读 `cfg.extra["auth_enabled"]`，**默认值 True**（未配置 = 开着）
- `require_auth()` 关掉时直接返回虚拟管理员 `{email:"local@msyt.local", role:"admin", node_id:"admin"}`
- `ensure_admin()` 关掉时**不建账号、不落口令文件**（分发包连「首次启动生成随机口令」这一步都没有）
- `/api/auth/config` 如实上报 `auth_enabled`，前端据此决定要不要弹登录框
- 前端读到 `auth_enabled === false` → 直接 `hideLogin()` + 进主界面，且**不会在恢复登录态时二次弹框**

★ 结论：**分发包不含任何可用的凭据，也不需要凭据** —— 打开就是管理员界面，
组员不用注册、不用记口令；同时服务器端该有的登录一道没少。
