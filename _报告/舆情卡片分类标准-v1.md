> 支持 AI 辅助生成 + 批量补齐已有详情页；结果存服务器；**注意时效性**）

## 一、这张卡片是给谁看的

民生e点通的详情页现在只有**事实**：原文楼层、受理流程、标签、核验结论。
研判的人（写报告的、做处置的）拿到一个帖，还要自己判断「这事要紧不要紧、谁来办、怎么办」。

**舆情卡片 = 把「事实 + 判断」并排放在详情页顶部**，让人 10 秒内知道这条要不要管。

所以卡片的分类标准要回答三个问题（按重要性）：

1. **是什么事**（事实层：程序能算的，绝不让 AI 编）
2. **要紧不要紧**（研判层：风险等级 + 异常信号）
3. **怎么办**（处置层：AI 建议 + 人工定稿）

## 二、两份参考各自贡献了什么

### 1. 网信办 cacx 的摘要生成（`01 …/方向-爬取工具的更新/cacx`）

贡献的是**工程骨架**，不是分类标准：

- AI 产物单独一张表 `ai_annotations(article_id, task, provider, model, result JSON, created_at)`，
  按 **(对象, 任务)** 唯一 —— 一篇一摘要，重复生成是覆盖
- 失败另存 `ai_failures`，并给失败**分类**（rate_limit / content_blocked / auth / network /
  bad_model / not_configured / server / retriable / other），每类配一句界面说明
- 批量：批量面板 + 失败可「补跑」+ 可**人工补录**（如实记 provider=manual，
  不假装是模型产的）
- 摘要输出是**严格 JSON**：`{summary, tags[], sentiment, entities[]}`，
  sentiment 用枚举 `neutral|positive|negative`
- 正文截断可配（`max_content_chars`，0=不截断），并写明「政务长文常超限，
  摘要只看得到前半段，结论容易偏」
- 行为埋点 `events(kind, article_id, …)`，含 `summarize` 事件

### 2. MiroFish（群体智能推演引擎）

贡献的是**研判视角**，不是字段清单。它把「一个真实事件」变成一张图：

种子材料 → 实体关系抽取 → 角色画像（persona）→ 群体立场分布 → 推演报告。
它的舆情演示（武大舆情推演）里，卡片式产物的骨架是：

**议题 / 关键实体 / 关系网络 / 角色立场 / 风险点 / 处置建议**

对我们最有用的两条：

- **实体与立场要能落到「谁」**（不是一个抽象的负面情绪，而是「诉求人 vs 某部门、
  诉求是个人还是一片区」）
- **研判结论要能指出「下一步看什么」**（MiroFish 的报告给的是「如果 X 则 Y」）

**注意别学过头**：MiroFish 是**推演**引擎（要造 Agent、跑仿真），我们的卡片是
**单帖事实卡**，不引入仿真。一个帖（几百字）撑不起关系图谱。

## 三、卡片字段：分三层，权限与责任不同

★ 这套分层是整个标准的核心：**谁的数据说了算**。

### 第一层：确定性字段（程序现算，AI 不得改写）

| 字段 | 口径 | 数据来源 |
|---|---|---|
| 类别 | 站方 9 类（投诉/咨询/建议/追问/求助/点赞/市民巡访/其他） | threads.category |
| 受理状态 | 已回复/已受理/未受理/（空） | threads.state |
| 办理部门 | 主办 + 协办 | dept_name / extra_dept_names |
| 留言箱 | 归口信箱 | mailbox_name |
| 发帖时间 | 楼层首个 post 的时间 | threads.pub_time |
| 首个回复时间 | 第一个**非楼主**楼层的时间 | posts |
| 首响间隔（天） | 首个回复 − 发帖；没有回复就写「无」（不写 0） | 程序算 |
| 末次回复时间 / 已历时（天） | 站方最后一次动静 | threads.last_reply_ts |
| 时效灯 | 站方 3 个工作日口径（绿/黄/灰/warn/无） | light_code |
| 楼层数 / 回复数 / 字数 | 互动强度 | posts_n / replies / chars |
| **追问轮次** | 楼主在同一帖内追加楼层的次数 | posts.author_uid 比对 |
| 三维标签 | **人工优先**，规则标签另列 | thread_anno_tags / thread_dim_tags |
| 词表命中 | 命中哪些词、几次 | keyword_hits |

### 第二层：研判信号（程序算的「异常」，是风险等级的输入）

| 信号 | 判据 | 库里实测条数 |
|---|---|---|
| 状态自相矛盾 | state=已回复 但 replies=0 且楼层有网友回复 | 有（AI 初注已自动抓到 3 条） |
| 长期未闭环 | 时效灯 warn/grey/none | 83,339 |
| 未受理 | state=未受理 或 空 | 17,177 |
| 跨部门 | extra_dept_ids 非空 | 289 |
| 站方有变动 | list_changes 记到「受理状态变了 / 回复数变了 / 标题改了」 | 193,620 条变更 |
| 高互动 | replies ≥ 5 | 77,733 |
| 涉稳措辞 | AI 判定（第二层），不靠规则 | — |

### 第三层：AI 生成（必须带依据 + 自动打疑点）

沿用刚做完的 AI 初注那一套纪律：**只在候选枚举里取值、疑点自动标、采纳必须人工确认**。

| 字段 | 内容 | 约束 |
|---|---|---|
| 一句话概述 | ≤ 80 字说清「谁对谁提了什么要求」 | 不得编造未出现的部门/时间 |
| 诉求焦点 | 诉求指向的**具体事项** | 必须是原文能指认的 |
| 诉求主体 | 个人 / 一家人 / 一片区 / 某单位 | 枚举 + 依据句 |
| 情绪与对抗性 | 不满程度 + 是否有质疑/对抗官方措辞 | 枚举（低/中/高） |
| 涉稳要素 | 是否群体性、串联、越级、极端表述 | 有则写依据；无则写「无」 |
| 处置建议 | 转办 / 催办 / 现场核实 / 口径回应 | 枚举 + 一句理由 |
| **研判提示** | 「建议人工复核的 N 个点」 | 自动打疑点标签 |

### 第四层：人工（可改 + 留痕；**但卡片不设「待确认」状态机**）

★ **拍板结论（2026-11-12）**：卡片**直接显示**，不要求人工确认才算数。
理由：卡片是**派生结论**（给人看的研判参考），不是权威台账 —— 强压一道「确认」
只会让人懒得用。作数的是人的地方是**核验台账**（sample_review），那里才走人工流程。

- **核验结论**：纳入 / 排除 / 待核验（已在 sample_review，字段⑤ 的载体，**人工流程在这里**）
- **风险等级复核**：人工可改规则算出来的档位
- **研判意见**：人工补一段处置意见
- 人工改过的字段要**标出是谁改的**（reviewed_by + 人工覆盖标记）
- **人工改过的卡片不被自动重新生成覆盖**（见第五节规则 3）

★ 与「AI 初注」的纪律差异（别混）：
AI 初注要**写入人工台账**（anno.submit）→ 那一步必须二次确认、疑点必须人工确认；
**卡片不写台账**，只是显示 → 所以 AI 的疑点在卡片上**只做提示**（⚠ 标出来），
不阻塞显示、不阻塞批量生成。

## 四、研判分类：正交于站方类别

站方「类别」是**诉求形态**（投诉/咨询/建议…），它回答不了「这事要不要管」。
所以要**另立一套研判分类**，与站方类别**正交**（一条帖同时有两个标签）：

### A. 事件性质（一帖一主类，AI 判定 + 候选枚举）

| 类 | 说明 | 典型处置 |
|---|---|---|
| 民生诉求 | 具体、可办理的事 | 转办 |
| 政策咨询 | 问政策/流程，非投诉 | 答复 |
| 处置争议 | 对已发生的具体处置不满 | 复核+说明 |
| 服务态度 | 窗口/服务人员态度 | 提醒+培训 |
| 质量安全 | 涉消防、危房、食品、燃气等 | 立即核实 |
| 涉稳风险 | 群体性、串联、越级、极端表述 | ★ 升级处置 |

### B. 办理状态（从 threads.state 映射，程序算）

`已闭环` / `办理中` / `推诿待转`（空态、未受理）/ `超期未回`

### C. 风险等级（四档，**规则算，不用 AI 主观**）

| 档 | 判据（命中即升档，取最高） | 处置 |
|---|---|---|
| 提示 | 无异常信号 | 归档 |
| 关注 | 命中 1 个一般信号（未闭环/矛盾/高互动） | 纳入日办 |
| 预警 | 命中 2 个以上，或（安全类/涉稳类 且 未闭环） | 指定专人盯 |
| 紧急 | 涉人身安全，或明确越级/群体聚集表述 | ★ 即时上报 |

★ 为什么等级要**规则算**：等级是**分发依据**，必须**可复算、可解释**；
AI 给的风险等级只能当「参考」，人工可改。

## 五、时效性：卡片必须绑定数据快照

★ 这是最容易出事的地方 —— **卡片是「过去某个时刻的判断」，帖子的状态会变**。

卡片生成时记一份**快照指纹**：

`based_on = {last_post_id, last_reply_ts, state, replies, detail_state, flows 末节点时间}`

进详情页时比对：

- 一致 → 卡片有效
- 不一致（站方又回复了 / 状态变了 / 多了楼层）→ 卡片**标「已过时」**并写明
  「站方在 X 之后有更新」，给一个「重新生成」按钮
- 站方详情页本身已是 stale 的 → 卡片直接标「正文也过时，卡片不可用」

三条硬规则：

1. **批量生成要幂等**：已有卡片且指纹没变 → 跳过，不重复烧额度
2. **每张卡片要留痕**：生成时间、模型、提示词版本、指纹、是否被人工改过
3. **人工改过的卡片不被自动覆盖**：重新生成前先提示「人工已改过，要覆盖吗」

## 七、这轮实测底数（决定标准能不能落地）

| 问的 | 答的 |
|---|---|
| 库里有啥 | threads 607,034 / posts 978,741 / 受理流程 flows / 三维标签 / 核验台账 5 条 / AI 初注 14 条 |
| 状态分布 | 已回复 581,441 ｜ 空 15,451 ｜ 已受理 8,416 ｜ 未受理 1,726 |
| 类别分布 | 投诉 250,005 ｜ 咨询 215,134 ｜ 建议 50,210 ｜ 追问 30,976 ｜ 其他 30,616 ｜ 求助 20,220 ｜ 市民巡访 6,347 ｜ 点赞 3,520 |
| 时效灯 | 绿 443,279 ｜ 黄 80,414 ｜ 灰 46,028 ｜ warn 19,765 ｜ 无 17,546 |
| **不能用的信号** | 浏览数 99.9% 的帖都 ≥1000 → **热度不能靠浏览数**；
| | 同一 uid 最多 160,518 帖 → **uid 不能当「同一诉求人」**（站方匿名映射）；|
| | 正文含「帖子编号」只有 95 帖 → **事件聚类信号极弱** |

→ 结论：**v1 只能做「单帖卡」**，事件级聚合（像 MiroFish 那样聚成一张图）
在这份数据上做不实 → 留到以后有可靠事件键再说。

## 八、拍板结果（2026-11-12）

| # | 问题 | 拍板 | 对实现的约束 |
|---|---|---|---|
| ① | 卡的粒度 | **单帖卡** | 一张卡只讲一条帖；不做事件聚合（数据也没有可靠事件键） |
| ② | 风险等级 | **进 v1，四档，规则算** | 等级由程序按信号算；AI 只能给参考；人工可改 |
| ③ | AI 字段 | **全 6 项** | 概述/诉求焦点/诉求主体/情绪对抗性/涉稳要素/处置建议，一次调用出全量 |
| ④ | 人工确认 | **不设「待确认」**，直接显示 | 卡片无状态机；人工可改并留痕；人工改过的不被自动覆盖 |

## 九、实现蓝图（下一步，等你放话再动手）

### 落库：一张新表

`thread_opinion_cards`（tid 主键）：

| 列 | 含义 |
|---|---|
| `tid` | 帖子 id |
| `facts_json` | 第一层确定性字段 + 第二层信号（程序算，随帖变） |
| `ai_json` | 第三层 AI 6 项 + 疑点 |
| `judge_json` | 事件性质/办理状态/**风险等级**（等级由程序算，可被人工覆盖） |
| `advice_json` | 处置建议（AI 给，人可改） |
| `based_on` | 指纹快照（见第五节） |
| `status` | fresh / stale（与站方 detail_state 联动） |
| `edited_by` / `edited_at` | 人工改过留痕（非空 = 不被自动覆盖） |
| `model` / `prompt_version` / `created_at` / `updated_at` | 可追溯 |

### 接口（5 个）

- `GET /api/thread/{tid}/card` —— 取卡（带 stale 判定）
- `POST /api/anno/card/generate` —— 单条生成（用**我的 API** 或服务器默认，同 AI 初注那套）
- `POST /api/jobs/card-batch` —— 批量（后台 job + 逐条进度，**复用刚做好的 ai_batch 机制**）
- `POST /api/anno/card/{tid}/edit` —— 人工改（写留痕）
- `GET /api/anno/card/stats` —— 覆盖率 / 失败清单（照 cacx 的口径）

### 界面

- 详情页抽屉**顶部**放卡片（在「基本信息」之上，人先看结论再看原文）
- 标注台里可对当前条目一键生成
- 检索列表可加一个风险等级角标（**待定**：要不要加，取决于列表的密度）

### 闸（先立后写）

`_tools/test_opinion_card.py`：

1. 三层字段各归各层（程序层不许被 AI 覆盖）
2. **风险等级是规则算的**：同一条数据两次算结果一致；改一个信号等级就变
3. **指纹比对**：站方状态变了 → 卡片变 stale；没变 → 不重复烧额度（幂等）
4. AI 字段必须在候选枚举内（事件性质/情绪等级/处置建议），候选外丢弃并标疑点
5. 人工改过的卡片不被批量覆盖
6. 真反向验证（把实现改坏 → 同批断言必须报红）

### 成本提醒

批量补齐 = 每条一次模型调用。**60 万条全量不现实**（就算 1 毛钱/次也是 60 万）；
实际做法应该是**按需 + 抽样**：研判重点（未受理/超期/高互动/新帖）+ 人工点名的批量补。
