# msyt —— 民生e网通「群众留言板」舆情采集器

> 目标站：中国宁波网 民生e点通 · 天一论坛 › **群众留言板**（`fid=1176`）
> `https://bbs.cnnb.com.cn/forum.php?mod=forumdisplay&fid=1176`

面向课程作业「02 民生e网通」的采集程序。**只读**：不注册账号、不做短信认证、不发任何写操作
（不发帖／不回复／不点赞／不收藏）。

## 一、两条独立链路

程序把采集拆成两个命令，因为二者的代价、频率、失败模式完全不同：

| | 链路 | 命令 | 每帖代价 | 产出 |
|---|---|---|---|---|
| 一 | **列表采集** | `msyt list` | 1 次请求 | 元数据 + 多维标签（类别/状态/部门/区县市/留言箱/时效灯/回复量） |
| 二 | **详情页采集** | `msyt detail` | **N×2 次请求**（N=帖的页数） | 楼层正文 + 受理流程时间线 |

详情链路比列表链路贵一个量级，所以默认**先扫完列表**，再按需补详情。

### 详情采集「先旧后新」

按**发帖时间升序**取帖（`detail_queue` 的 `ORDER BY COALESCE(t.pub_ts,0) ASC`）。

为什么不能拿「上次到第 N 页」当水位：列表页会随新帖插入而漂移，页码当水位必然漏采或重采。
**按时间排序才是稳的**，而且天然实现「存量先落袋」。

### 详情范围限制（水位线）

> 用户口径：**列表先看 500 页；早于第 500 页最早一贴的文章，先不采详情。**

水位线由全局视图采集完成后确定：

```
全局视图最后一页最早一贴的发帖时间  →  meta.detail_cutoff_ts
```

- 早于水位线的帖子 → 队列里标 `skipped`，**不采详情**，并记明原因
- 只有全局视图**真的采到了最后一页**才会设水位线。
  试采 5 页就设水位线的话，「目前最早的那一贴」会被误当成截止线，
  恰好把刚采到的数据判死 —— 所以 `set_cutoff_from_global()` 会检查
  `status=='done'` 且 `last_page >= max_page`，否则只提示「暂不设水位线」。

## 二、分类体系：既当采集源，也当标签

站方把同一批留言切成**六条正交的标签轴**（实测自页面 DOM，非自造）：

| 轴 | 取值 | 列表页参数 |
|---|---|---|
| 部门/单位 | 109 个 typeid | `filter=typeid&typeid={id}` |
| 部门分组 | 职能(64) / 区县市(14) / 民生企事业(25) / 其他(10) | 展开成各成员的 typeid |
| 区（县、市） | 10 个 | 展开成该区县的 typeid |
| 类别 | 投诉/建议/咨询/点赞/市民巡访/追问/求助/其他 | `filter=tieziclass&tieziclass={c}` |
| 受理状态 | 已回复/已受理/未受理 | `filter=govchecked&govchecked={c}` |
| 留言箱 | 市委书记(23)/市长(24) | `filter=sortid&sortid={c}` |
| 时效灯 | green/yellow/grey/warn | `filter=light&light={c}`（⚠ 见「已知局限」） |

这些轴**不互斥**：一条留言同时落在好几条轴上。程序因此做了两件事：

**① 作为采集源** —— 每个切片是一条**独立的分页列表**，有自己的 `list_watermark` 行，
所以断点续传是「按源」的：采到第 137 页断了，下次从 138 页接着来。

```bash
msyt list --sources global                # 全站视图（500 页顶）
msyt list --sources dept:495,737          # 市公安局 + 鄞州区
msyt list --sources group:func            # 职能部门和群团组织（展开 64 个）
msyt list --sources district:737          # 鄞州区
msyt list --sources category:1,state:2    # 类别=投诉 且 状态=已受理
msyt list --sources mailbox:23            # 市委书记留言箱
msyt list --sources dateline:2592000      # 最近 30 天（打破 500 页上限）
```

**② 作为标签** —— 入库即打上，`msyt search` 可任意切片：

```bash
msyt search "" --category 投诉 --state 已受理 --group district
msyt search "" --dept 737 --light green --date-from 2026-01-01
```

> 筛选参数**编号与名称都认**：`--category 1` 与 `--category 投诉` 等价。

## 三、完整性检验（四层）

用户要求：「详情页有一个头/尾才算完整」。落成：

**硬判据（不过 → 不标 done，帖子留在队列里）**

1. 每页的 AJAX `data` 键集合 **==** 该页 `postmsg_{pid}` 锚点集合（**精确相等**）
2. **头** = 楼主那一楼（`floor == 1`）在库
3. **尾** = 楼层号最大的那一楼在库（一帖 N 页时，头在第 1 页、尾在末页 → 必须跨页定义）
4. 该帖应有的页全部取到，且没有空正文的楼层

**软警告（记录但不否决）**

- 楼层号有缺口 → 站方删楼/置顶造成，是**站方的行为**，不是我们漏采
- 列表页的「回复数+1」与实收楼层对不上 → **站方自己的计数不自洽**
  （实测 tid=8332684：列表说 5 条回复，实际楼层标签最大是 `5#`，总共 5 楼）

两类必须分开：混在一起会让体检报告失去意义。

```bash
msyt integrity     # → {"checked":N, "ok":N, "problems":[], "warnings":[],"growth":[]}
```

### ★ 增量：站方会追加回复，已采过的帖可能**过时了**

站方不是静态的 —— 一帖采完之后它可能又被人回复，楼层数变多。
「上次采完就当采完了」是不成立的。

**判据是站方自己给的数字**：列表页每一行都带「回复数」。

| 环节 | 做法 |
|---|---|
| 识别 | 列表采集时，同一 tid 的 `replies` **比上次采集时变大** → 站方又回复了 |
| 标记 | `threads.detail_state='stale'`（待更新）＋ 丢回 `detail_queue`（`pending`，attempts 归零） |
| 补齐 | 下次详情采集自动捡走重采，新楼层按合并规则进来 |
| 可见 | 体检页「已识别的增量」栏列出，可勾选后一键「重跑所选」 |

> ⚠ 顺序不能反：**必须在 `upsert_threads` 之前比**，否则回复数已被覆盖成新值。
> ⚠ **只有变大才判**：变小可能是站方删楼，也可能是解析抖动 —— 宁可不报，
>   也不能把好数据误判成要重采（重跑是要花站方请求的）。

> ★ **别与「站方计数不自洽」混为一谈**：
> 「站方称 N+1 楼、本地实收 N 楼」是**站方自己的计数问题**（常见，差 1），
> 既不算我们漏采，也**不算增量**。体检页把两者分列在不同栏。

### ★ 体检页的两个动作：重跑 / 自行清除

| 动作 | 行为 | 端点 |
|---|---|---|
| **重跑** | 丢回队列重新采（**软失败**）—— 数据保留，采到的新楼层合并进来 | `POST /api/integrity/retry` |
| **自行清除** | 楼层 / 分页凭据 / 受理流程 / 队列项**全部删光**，计数归零 | `POST /api/integrity/purge` |

两者都按批做（勾选多条一起），端点都 `require_admin`；「清除」界面二次确认，
并显示「删了多少楼层、多少页凭据、多少条流程」。

### ★ 防「静默串帖」——本项目最危险的一个坑

`ajax_getpost.php` 的 **`tid` 参数完全不参与内容选择**，token 才是唯一钥匙。
用 A 帖的 token 配 B 帖的 tid、乃至不存在的 `tid=9999999`，
服务端一律返回 **A 帖的楼层**，且 `code=1`、楼层数与正文长度全部正常 —— **不报错**。

后果：舆情场景下「A 部门的回复被算到 B 部门头上」，结论失真且毫无察觉。

防御就是上面第 1 条：**同一次响应里自带校验凭据**（该页的 pid 锚点），
不匹配即判失败并留痕。**宁可少收，不可收错。**

## 四、断点续传

粒度是「**页**」，落库是「**每页一个事务**」。

```
进程被杀
  → 队列里那条是 running
  → 下次开机 reset_stale_running() 把它归位为 pending
  → 从 pages_done+1 继续
  → 已经写进去的楼层是校验过 pid 集合的正确数据，不用重采
  → 帖子在头/尾都齐了之前不标 done，所以「半截帖子」永远看得见
```

实测（强杀进程 PID 后重启）：

```
杀前：done=19  running=1(tid=8338102)  pending=479
重启：tid=8338102 ✓ 1 页 / 2 楼 / 71 字   ← 被杀的那帖第一个被捡起并补齐
全局：重复 pid=0   孤儿楼层=0
```

## 五、命令

```bash
python -m msyt doctor --with-db        # API 自检（含 pid 集合校验）
python -m msyt doctor --deep            # 把各维度筛选端点也探一遍
python -m msyt taxonomy                 # 抓部门目录/区县市/站方统计
python -m msyt list --sources global --pages 5
python -m msyt list --sources dept:495 --pages 500
python -m msyt list --sources "dept:495,972"    # 多值（修复前只会采到 495）
python -m msyt detail --limit 50        # 先旧后新
python -m msyt detail --tid 8339985     # 定点采集（调试/补采）
python -m msyt detail --retry-failed    # 把失败任务重置为待采
python -m msyt search "违停" --scope all
python -m msyt search "" --category 投诉 --state 已受理 --group district
python -m msyt stats
python -m msyt integrity
python -m msyt sources                  # 列出所有可用维度与取值
python -m msyt export --out threads.csv
python -m msyt web                      # 启动本地 Web 前端
```

`--scope`：`thread` 只搜标题与部门名；`post` 只搜楼层正文；`all` 两者并集（**帖级去重**）。

### 检索层

移植自 cacx（01 项目）的 `db.py`，**检索语义原样保留**：

- FTS5 外部内容表 + `trigram` 分词器 + 触发器 + `rebuild`
- **短词（< 3 字）整体退回 LIKE** —— trigram 索引里 2 字词查不到任何东西，
  也不能「一半走索引一半走扫描」，那会漏结果
- 返回 `{total, items, mode, took_ms, scope}`，`mode` 标明走的是 `fts` 还是 `like`

与 cacx 的差别都源于模型差异（两层 vs 一层）：

| | cacx | 本项目 |
|---|---|---|
| 索引 | `articles_fts(title, content_text)` 一张 | `threads_fts(title, dept_name)` + `posts_fts(content)` 两张 |
| 收敛层 | 文章即正文 | 正文分散在 N 个楼层 → 统一在**帖**这一层收敛 |
| 标签 | 无 | 六条正交标签轴 |

## 六、Web 前端（本地界面）

命令行能跑，但"自己翻数据"和"给小组看"需要界面。`msyt web` 起一个**本地**网页：

```bash
python -m msyt web                    # http://127.0.0.1:8765/
```

或双击薄壳（**手动启停，不注册开机自启**）：

| 文件 | 作用 |
|---|---|
| `启动-web.cmd` | 起服务 + 自动开浏览器；已在运行则直接开浏览器 |
| `停止-web.cmd` | 按 PID 文件停服务（**隧道也一起停**） |
| `web-status.cmd` | 看状态（PID / 端口 / 帖数 / 楼层数 / FTS） |

底层是 `web.ps1`（start / stop / status / restart）。**默认只监听 `127.0.0.1`** ——
这是本地工具，不该直接暴露到公网；要给成员用就走下面的隧道。

### 6.2 协作（Beta）：成员协助正文采集

**闭环**：

```
管理员                          控制面（管理员机器）                  成员设备
────                          ──────────────────                  ────────
发布协助请求（选部门）  →   assist_tasks + assist_picks
                            任务编号 A1 / A2 …
                            ├─ 成员 agent 领活 → 分到具体 tid（先旧后新）
                            ├─ 成员本地采集（内存 SQLite，不落盘）
                            └─ 回传 → 并入权威库（走同一套完整性判据）
                            实时日志 → 双方同看（带节点徽标 + 任务编号）
```

**★ 成员端怎么启动 —— 网站把命令传下来，成员运行开启**

成员的机器上**没有** `msyt` 这个包，直接敲 `python -m msyt agent …` 只会报
`No module named msyt`。所以走的是**下载**这条路：

```
网页（成员已登录）
   │  GET /api/agent/bundle.zip      ← 服务端**实时生成**这个 zip
   │     · --server 用的是**下载者此刻访问的地址**（网址是动态的）
   │     · 包里**没有密码**，只有一张限时一次性的票据
   ▼
msyt-成员端启动包.zip
   │  解压 → 双击「启动采集.cmd」
   │     · 自动装依赖（requests、beautifulsoup4）
   │     · 然后**只问邮箱和密码** → 就地开跑
   ▼
本机 agent → 领活 → 采集 → 回传
```

另一种玩法：双击「启动助手.cmd」→ 本机开一个 `127.0.0.1:8766` 的小助手，
之后回到网页点「启动本机 agent」即可（网页把当前 JWT 递给助手，**连密码都不用输**）。

> ★ 本地助手为什么允许跨域、而站方不允许：
> 助手只绑 127.0.0.1（外网访问不到），只接受本机的启动/停止/查状态，
> **不接受任何采集指令** —— 放行 CORS 没有风险。
> 而站方一个 CORS 头都不给，浏览器里的网页根本不能直接去采。

**★ 失联自动停止**：控制面是协作的**唯一出口**（领活要问它、回传要给它）。
agent 有后台心跳；连接连续失败达阈值（默认 3 次）即判定失联 →
不再领活、正在采的那帖**在下一个页的边界中止**、不回传半截数据、退出并汇报。

**★ 成员端的数据承诺**：agent 用**内存 SQLite**（`:memory:`）采集，
**整条链路不写任何磁盘文件**（不落帖、不落正文、不落临时目录），
回传成功后内存库与正文对象立即释放 —— **"传完即删"不是口号，是物理上没有可删的东西**。

**★ 为什么不让浏览器直接采**：实测站方**一个 CORS 头都不给**
（`Access-Control-Allow-Origin = None`，预检也没有），
浏览器普通跨域 fetch 直接 `Failed to fetch`，`no-cors` 只能拿到 **opaque** 响应读不出内容。
所以正文采集必须由**成员机器上的 agent** 发请求 ——
好处是站方看到的是**多个分散的普通用户**，而不是一台服务器在集中爬。

**★ 权限分层（两道都做）**：

| 层 | 做什么 | 效果 |
|---|---|---|
| **界面层** | 成员登录后只看得见「协作（Beta）」一个页签 | 采集作业 / 完整性体检 / 采集日志 / 发布协助请求 / 成员名单 **全部隐藏** |
| **接口层** | 所有管理类端点 `require_admin` | 即使手动构造请求，成员也拿到 **403** |

被管理员锁住的端点：`/api/members*`、`/api/jobs*`（含启动采集）、`POST /api/assist/task`（发布协助请求）。
成员**可以**用的：登录/注册/改自己密码、领活、回传、看协作任务、看自己节点的实时日志。

**★ 账号怎么来：自助注册 + 管理员审核**

```
成员在登录页点「没有账号？注册一个」→ 填邮箱密码 → 账号状态 pending
   ↓  注册后**立刻登不进去**（提示"账号待管理员审核"）
管理员在「协作（Beta）→ 成员名单」点「通过」→ 状态 active → 成员可登录
```

为什么不让注册即用：站点已经通过 Cloudflare 隧道暴露到公网，
若注册即可用，任何拿到域名的人都能开始打站方，把配额和风控预算烧掉。
**审核这一步就是管理员的控制点。**

想改成「注册即用」：在 `config.json` 里设 `"auto_approve_registration": true`。

**★ 管理员能做什么**（成员名单那一栏）：

| 按钮 | 作用 |
|---|---|
| **通过** | 审核通过一个待注册账号（pending → active） |
| **停用 / 启用** | 临时封禁或恢复某人（停用后立刻登不进去） |
| **配额** | 改这人单次最多领多少帖（默认 50） |
| **重置密码** | 生成新密码（**只显示这一次**） |
| **删除** | 删掉账号 |
| **改密码**（自己的） | 在「我的身份」卡里改自己的密码 |

**★ 管理员账号**（登录页也会显示这一行，免得试错）：

| | |
|---|---|
| 邮箱 | `admin@example.com` |
| 密码 | `msyt@change-me`（建议登录后在「协作」页改掉） |

账号密码也写在 `程序/data/admin-账号.txt`（**不要提交到仓库**）。

**★ 互斥域是（任务类型, 采集节点）**：同节点同类任务互斥（防误重复），
**跨节点并行**（这是协作 Beta 的基础，见《分布式抓取协作方案》§4.2）。

### 6.4 三个实现要点（改这个模块前先读）

### 分页漂移（"错位"）与三道防线

列表按时间倒序，而站方是**活的**：新帖、**被新回复顶起来的老帖**都会插到最前面 → 分页窗口整体后移。

**后果要分清**（常见误解：以为漂移会"中间漏一段"）：

| 后果 | 是否发生 | 对策 |
|---|---|---|
| 重复 | 会，但无害 | `tid` 幂等入库，重复只覆盖 |
| 头部漏 | 会 | **补漏回扫**：源采完后回扫前 2 页（2 次请求） |
| **尾部漏** | **只发生在被 500 页顶截断的源** | 回扫救不回来 → 需 `filter=dateline` 时间窗再往深取 |

程序里的三道防线：

1. **页边界连续性检测** —— 每页记首尾 `tid` 进 `list_watermark.last_tid`；
   续采时比对"本批首行 tid" vs "上批末行 tid"，接不上 → `drift_hits++` 并写日志。
   （正常插入**不会**触发，它抓的是更罕见的真异常。）
2. **补漏回扫** —— 源采完回扫前 2 页，补回条数记 `list_watermark.rescan_rows`。
3. **幂等入库** —— `tid` 主键，是前两条能成立的前提。

**实测（109 部门全量）**：重复发现率 **0.18%**；14 个源里 9 个采完（未触顶 → **不漏**），
只有 `dept:726`、`dept:736` 触顶，**它们的尾部最老一批是已知缺口**（用 dateline 补）。
探到最深：`dept:558` 最早 **2011-11-06**（按部门遍历远深于全站视图的 2025-11-19）。

离线验证脚本：`_tools\test_drift.py`（合成页面 + 临时库副本，不碰站方，三组用例全过）。

### 采集任务：同节点互斥、跨节点并行

互斥域是 **(任务类型, 采集节点)**：

- **同一节点**（本机 = `admin`）同类任务**互斥** —— 再点「开始采集」会被 409 拒掉。
  理由很实在：两个任务会重复请求同一批页、请求量翻倍，还互相踩水位线。
- **不同节点之间允许并行** —— 这是留给**小组成员通过域名服务协作采集**的 Beta 能力：
  各节点各采各的部门段，靠 `tid` 幂等去重汇总。

> 这个设计现在就要留：若把互斥域做成全局的，小组成员一接入就会被自己的管理员挡住。

### 采集范围选择器（全量采集用）

列表采集要按站方的 **109 个部门**逐个遍历。手打 `dept:495,972,...` 根本不现实，
所以网页端给了一个**分组勾选器**：

- 按站方 4 个分组展示（职能部门和群团组织 64 / 区（县、市）及开发园区 14 /
  民生企事业单位 25 / 其他 10），**条目数与站方 tab 完全一致**
- **全选 / 清空 / 反选** 三个快捷键 + 名称搜索（输入「银行」只留 12 个）
- 一个部门可同时属多个分组（`512 综合` 属 4 组、`1099 甬城泊车` 属 2 组），
  与站方行为一致 —— 列表里会出现两行，但按 typeid 去重后仍是 109 个
- 可另外勾选「同时采全站视图 global」（500 页顶）
- **实时工作量估算**：选了 N 个部门、每源最多 P 页 → 最坏 `N×P` 次请求 + 预计小时数，
  超过阈值自动标红，并在启动前弹确认
- 每个部门是**一条独立的分页列表**，各有自己的 `list_watermark` 行，
  所以断点是**按源**的：采到第 137 页断了，下次从 138 页接着来

「高级：直接写源描述」里仍可手写 `global / dept:495,972 / group:func / category:1 / dateline:2592000`，
与上面的勾选**叠加**使用。

> ⚠ 修掉的一个真 bug：`expand_sources("dept:495,972")` 原本**只会展开出 495** ——
> 旧实现先按逗号切整串，第二段 `972` 丢了维度归属，被 `dim not in _TEMPLATES` **静默丢弃**，
> 不报错、不采到、也没人发现。现已改为「先按项归属、再拆码表」，
> `dept:495,972` → 2 个源，`group:func,group:enterprise` → 87 个源（含重叠去重）。

### 详情采集的目标：与列表走同一个源

详情采集卡里也有一个**同样式**的部门选择器（与列表那个共用同一份部门字典，
但选中集合各自独立），目标有两种给法、可叠加：

| 给法 | 含义 |
|---|---|
| **直接填 tid** | 定点补采，逗号分隔多个 |
| **按部门选** | 选中部门下**所有还没采详情**的帖，按**先旧后新**采集 |

详情选择器上有「**沿用列表的选择**」一键把列表那边的勾选复制过来 —— 这就是
「定点 tid 与列表走同一个源」。选完部门后，界面会**实打实统计**：

> 所选 3 个部门下有 **450 帖**还没采详情，本次最多采 450 帖；每帖 N×2 次请求（N=页数），先旧后新。
> （全库还有 36,487 帖待采）

部门归属有两个来源，都算：`dept_id`（主部门）与 `extra_dept_ids`（多标签部门）。
后者是逗号串，**不能直接 `LIKE '%512%'`**（会误命中 1512），
所以两边都归一成「逗号包起来的串」再用 `instr` 精确找：

```sql
instr(',' || COALESCE(extra_dept_ids,'') || ',', ',512,') > 0
```

> ★ **旧进程降级**：服务端没重启到 1.0.2 时，前端会**探测版本号**并把详情选择器**禁用**，
> 明确提示「服务端尚未重启到支持『按部门采详情』的版本」。
> 绝不让新前端对旧后端发一个被 Pydantic **静默忽略**的 `dept_ids` ——
> 那会变成"看着选了部门、其实没按部门采"，是最难发现的错。

### 三个实现要点（改这个模块前先读）

1. **长任务不能阻塞 HTTP**。
   `msyt list --pages 500` 要跑几十分钟，不能在请求线程里同步跑。
   所以采集动作都走 `/api/jobs/*`：接口立刻返回 `job_id`，后台线程跑，
   前端轮询 `/api/jobs/{id}` 看进度与日志。
   任务状态机：`running → done / failed / stopped`。

2. **日志怎么捕获**。
   采集器的进度输出全走 `Client.log()`（不是裸 `print`），
   所以给 `Client` 套一个写进任务缓冲的子类就能拿到实时日志 ——
   **不必重定向 stdout**（重定向是全局的，多任务时会串）。

3. **SQLite 多线程**。
   `DB.__init__` 用的是 `sqlite3.connect(path, timeout=30)`，默认 `check_same_thread=True`，
   同一连接跨线程用会抛异常。所以 webapp 用**线程局部（threading.local）**给每个线程各开一个连接。
   库是 WAL 模式，读写可并发。

### 停止是怎么停的

`DetailCollector.run()` 与 `ListCollector.collect()` 都加了**可选**的 `should_stop` 回调
（默认 `None` = 原有行为不变，CLI 不受影响）。点「停止」后，采集器**在下一个页/帖的边界**停下：
当前这一帖会**采完整**再收尾，进度已落库，下次继续（断点续传）。

## 九、关键实测结论（规则从哪来）

站方**没有公开 API 文档**。本项目的解析规则是**用浏览器实地勘察页面 DOM** 得到的
（`#rankingwz` 的 5 个 tab、`.qxsa` 区县市网格、`tbody#normalthread_`、
`#postmsg_`、`ajax_getpost` 的 token 机制）。
规则一旦过时，`msyt doctor` 会立刻报出来 —— 这就是它存在的意义。

### 接口

```
列表（全局）    GET /forum.php?mod=forumdisplay&fid=1176&page={N}
列表（部门）    GET ...&filter=typeid&typeid={typeid}
列表（时间窗）  GET ...&dateline={秒}
列表（类别）    GET ...&filter=tieziclass&tieziclass={1..7,999}
列表（状态）    GET ...&filter=govchecked&govchecked={1,2,999}
列表（留言箱）  GET ...&filter=sortid&sortid={23,24}
详情            GET /forum.php?mod=viewthread&tid={tid}&page={N}
楼层正文        GET /ajax_getpost.php?token={token}&tid={tid}&src=pc
站方统计脚本    GET /html/yp/ms_sjszxsqtotal.js
```

全部响应需 `r.encoding = "utf-8"`。

### 三个必须记住的坑

1. **token 时效 < 30 秒**，不绑会话、不绑 Cookie、可复用。
   所以详情页取到 token 后，**紧接着的那次 ajax 请求中间不得插入任何 sleep**。
   `Client.get_nowait()` 就是为此存在（不限速、不重试 —— 重试会用同一个过期 token，必然还是失败）。

2. **Discuz 分页上限 500 页**，`page=501` 起回绕到第 1 页。
   列表页每页都要读出站方给的 `totalpage`，到顶即停。
   详情页同理：单页帖**根本没有分页块**，请求 `page=2` 会回绕返回第 1 页。

3. **区县市统计数字在 HTML 里是 `document.write(ms_hs);`** ——
   真数字在独立脚本 `html/yp/ms_sjszxsqtotal.js` 里，不取那个脚本采到的就是字面量。

### 站方自报的真实量级

```

ms_all_reply  = 740551   历史受理总量
ms_thisyear   =  49570   今年留言量

## 十、已知局限

1. **全局视图只有 500 页，够到的远不是全部** —— 全局视图末页最早一贴是 **2025-11-19**（约 5 万条），
   而站方自报历史留言 **744,636 条**（`ms_all`）。
   这**不是「数据不存在」，是「这个视图够不到」**。
   已实测的两条绕行手段（程序里都实现了）：
   - **按部门遍历**：每个 `typeid` 有自己的分页与自己的触达边界 ——
     宁波广电集团 11 页 → 最早 **2011-10-01**、宁波证监局 2 页 → **2014-12-22**、
     市住建局 157 页 → **2010-12-27**。
     **页数未满 500 的部门 = 其历史被完整覆盖**（Discuz 的 `totalpage` 是真实匹配数，
     只有超过 500 才被截断）；被截断的只有市公安局 / 鄞州区 / 综合这三个大部门 ——
     但市公安局那 500 页末页也已到 **2019-02-19**，比全局视图深 6 年多。
     **页数相同，跨度能差 7 倍**：全局视图按最近回复排序，5 万条正好覆盖最近 11 个月
     （站方自报今年就 49,570 条），而单个大部门 5 万条能摊到 7 年。
   - **`dateline` 时间窗**：`filter=dateline&dateline=2592000`（30 天）→ 63 页、
     90 天 → 175 页。与 `typeid` 可叠加：`filter=typeid&typeid=495&dateline=2592000`。
     ⚠ **必须带 `filter=` 前缀**，裸 `&dateline=N` 会被服务端忽略（返回仍是 500 页）。

   > ⚠ **要量「能触达多早」，必须取末页**（`totalpage` 那一页）的最早一贴。
   > 用第一页的日期范围去量，会得出偏晚且偏小的错数 —— 报告初稿就栽在这上面，
   > 两次把测量方法修正后才得到上面的数。

2. **`filter=light` 疑似未真正生效** —— 返回的页数与日期与未筛选一致。
   本程序**不使用**该参数，只把列表行里的时效灯**图标**作为标签采集（那个是可靠的）。

3. **`search.php` 是登录墙**（返回 0 行 + 登录提示），无法用它取更早的历史。

4. **正文里的图片**只记录真址（`zoomfile`），**不下载**。图片体积大，
   本作业的舆情分析用不到。

5. **时效灯只对已回复的帖存在** —— 已受理/未受理的帖在列表页没有图标。
   程序把这种情况显式记为 `none`（未点亮），不记空值，
   以免分不清「没点亮」和「解析失败」。

6. **站方回复计数可能不自洽**（实测 tid=8332684：说 5 条回复，实际 5 楼）。
   程序把它归为「警告」而不是「失败」，并保留在 `threads.detail_warn` 里。

7. 站点版权声明：「群众留言板」内容未经授权不得擅自使用或转载。
   本程序定位为**教学分析**，不转载；导出数据中的个人标识建议脱敏后再用。

### Windows 文本编码的三个坑（改脚本前先看）

`_tools/fix_text_encoding.py` 是为此写的（幂等，可重复跑）：

| 文件 | 规矩 | 原因 |
|---|---|---|

| `.py` / `.md` | UTF-8 **无 BOM** + CRLF | Python 源码带 BOM 会在第一行报 `SyntaxError: invalid non-printable character` |

```

### ★ 第四个坑：控制台打印能把**采集任务**打挂（2026-10-22 实测）

Windows 控制台默认编码是 **GBK**。采集日志里有「⚠」「≠」「✓」这些字符，
`print()` 直接抛 `UnicodeEncodeError: 'gbk' codec can't encode character '⚠'`。

**为什么严重**：那行 print 在**采集线程**里，一抛就把整个采集任务干掉 ——
实测漂移检测刚打出一条「⚠ 续采时页边界不连续」的警告（正是我们最想看到的诊断），
**整批列表采集就死在那儿**，后面的源一个没采。

**正确做法**（三处都改了）：

```python
# ① 启动时把标准输出换成 UTF-8（errors=replace：编不了的字显示成 ?，而不是崩）
for _stream in (sys.stdout, sys.stderr):
    try:
        _stream.reconfigure(encoding="utf-8", errors="replace")
    except Exception:
        pass

# ② 每一处 print 都要兜住异常 —— 日志打印失败绝不该影响采集
try:
    print(msg, flush=True)
except Exception:
    enc = getattr(sys.stdout, "encoding", None) or "ascii"
    print(msg.encode(enc, "replace").decode(enc, "replace"), flush=True)
```
